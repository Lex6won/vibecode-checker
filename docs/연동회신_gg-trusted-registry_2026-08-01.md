## 0. 결론 세 줄

1. **연동 방향을 수용합니다.** 역할 분리(관측 vs 판정), 환경변수 옵트인, fail-open, 미확인≠안전 — 저희 설계 원칙을 정확히 읽고 맞춰 오셨습니다.
2. **§10-2 verdict 2종 추가는 조건부 수용입니다.** 값 자체는 받되, `registry_approved` 부여 조건에 단서가 붙어야 합니다. 지금 설계 그대로면 §4.4에 쓰신 "`malicious`가 최상위" 문장이 **실효가 없습니다**(§2-1).
3. **착수 전 해소가 필요한 설계 문제 3건**과 **사실관계 정정 3건**을 아래에 적었습니다. 1건(§2-1)은 요청서 안에서 자기모순이라 스키마 확정 전에 정리돼야 합니다.

## 1. §10 확인 요청에 대한 답변

### 10-1. 환경변수 옵트인 방식이 gvskb의 범용성 원칙과 맞는가

**맞습니다.** 미설정 시 기존 경로와 100% 동일하게 동작한다는 전제를 지켜 주시면 저희 쪽 이견이 없습니다. 다른 형태를 요구할 계획이 없습니다.

다만 전제 하나가 바뀌었습니다. **2026-08-01 자로 라이선스를 MIT → PolyForm Noncommercial 1.0.0 으로 변경했습니다.** 귀 문서 §0-3·§2의 "범용 MIT 도구" 표현은 갱신이 필요합니다.

실질 영향은 없습니다. PolyForm NC는 "government institution" 사용을 재원과 무관하게 비상업 목적으로 **명시 허용**하므로, 경기도·산하기관의 사용과 레지스트리 연동에 제약이 생기지 않습니다. 막히는 것은 상업적 판매·납품입니다. 2026-08-01 이전 MIT 배포본에는 소급되지 않습니다.

### 10-2. verdict 2종 추가가 수용 가능한가 — **조건부 수용**

값 추가와 사다리 위치는 받습니다. 단 **`registry_approved` 부여 조건**에 단서가 필요합니다(§2-1). 요약하면:

- `APPROVED` 응답을 받아도 **로컬 인텔 캐시의 악성·KEV 대조는 수행**합니다(네트워크 불필요, 비용 사실상 0).
- 대조에 걸리면 `malicious`/`vulnerable`이 이깁니다.
- 걸리지 않을 때만 `registry_approved`를 부여합니다.
- 생략되는 것은 **원격 OSV 조회**뿐입니다.

이렇게 해야 §4.4의 "`malicious`가 최상위인 것은 유지 — 레지스트리 데이터가 로컬 탐지 위 아님"이 실제로 참이 됩니다. 지금 §4.1대로 즉시 반환하면 로컬 탐지를 아예 돌리지 않으므로 그 사다리가 적용될 일이 없습니다.

`REJECTED`의 즉시 반환은 그대로 수용합니다 — 차단이 더 강한 신호이고 추가 분석이 판정을 뒤집지 않습니다.

### 10-3. P0-1·P0-2 착수 일정

- **P0-2(감사로그)**: 외부 의존이 없어 저희 쪽에서 바로 착수 가능합니다.
- **P0-1(플러그인)**: 요청하신 대로 **구현은 보류**하고 스키마 합의만 먼저 진행합니다. `POST /packages/submit-check` 엔드포인트가 열린 뒤 착수합니다.
- **P1-4(락파일)**: 레지스트리와 무관하게 저희 도구 자체 가치가 크고 의존이 없어 **P0-2와 함께 앞으로 당길 것을 제안**합니다(§6).

구체적 일정은 저희 운영 사정에 달려 있어 별도로 알려 드리겠습니다.

### 10-4. `engine_version`에 커밋 SHA 포함

**`engine_version`에 붙이는 것은 곤란하고, `engine_commit` 별도 필드를 제안합니다.**

버전은 `src/gvskb/__init__.py`의 `__version__`이 단일 원천이고, CI 패키징 잡이 **"코드 버전 == 배포 메타데이터 버전"을 강제**합니다(과거 구버전 설치본이 현재 코드를 가려 사용자가 낡은 룰로 검사하던 실측 사고의 재발 방지 장치입니다). `engine_version`에 SHA를 덧붙이면 이 불변식과 충돌합니다.

재현성 요구는 이해하므로, 별도 필드로 SHA를 싣는 방식이면 양쪽 목적이 다 충족됩니다.

### 10-5. 인텔 번들 권장 반입 주기

현재 **매일 03:00 KST 자동 갱신**되며, 고정 URL로 배포합니다.

```
releases/download/intel-latest/gvskb-intel-bundle.zip
releases/download/intel-latest/gvskb-intel-bundle.zip.sha256
```

검증은 zip 내부 `manifest.json`(파일별 sha256) + 게시된 sha256 사이드카 이중으로 가능합니다. 망분리 반입 절차는 외부망 PC 다운로드 → sha256 확인 → USB 이동 → `gvskb intel-bundle import` → `gvskb doctor --offline` 입니다.

**주 1회 반입이면 실용적 최소선**으로 봅니다. 다만 KEV 신규 등재는 즉시성이 중요하므로, 레지스트리가 인텔 번들을 내부망에 미러링해 gvskb 클라이언트들이 매일 받게 하는 구조를 권합니다.

## 2. 착수 전 해소가 필요한 설계 문제 3건

### 2-1. `APPROVED` 즉시 반환 ↔ verdict 사다리 — 요청서 내부 모순 ★

§4.1은 `APPROVED`면 자체 분석을 생략하고 즉시 반환합니다. §4.4는 `malicious`가 최상위임을 유지한다고 씁니다. **두 문장이 양립하지 않습니다.** 즉시 반환하면 로컬 탐지가 실행되지 않아 사다리가 적용될 일이 없습니다.

구체적 실패 시나리오:

| 시점 | 사건 |
|---|---|
| 2026-07-15 | 레지스트리가 `X@1.2.3`을 승인 (`expires_at: 2026-10-13`) |
| 2026-07-20 | 같은 버전이 OSV 악성 목록에 등재 |
| 07-20 ~ 10-13 | **gvskb는 계속 "기관 승인됨"으로 통과** — 약 3개월간 악성 패키지에 초록불 |

승인은 시점의 판단이고 위협 정보는 그 뒤에도 갱신됩니다. 보안 도구에서 가장 위험한 것은 오탐이 아니라 **조용한 초록불**이라는 것이 저희가 이번 라운드에서 반복해 확인한 바입니다.

**해소안**: §10-2에 적은 대로, `APPROVED`여도 로컬 인텔 캐시 대조는 반드시 수행합니다. 이 대조는 이미 오프라인 경로에 구현돼 있어 추가 비용이 없습니다.

### 2-2. fail-open의 비대칭 — `REJECTED`가 집행되지 않음

§4.7의 fail-open은 **승인 조회**에 대해서는 옳습니다. 그러나 **차단 조회에 대해서는 fail-open이 곧 차단 무력화**입니다.

레지스트리가 유일한 판정 출처인 폐쇄망에서 조회가 실패하면, 기관이 명시적으로 막은 패키지가 통과합니다. 공격자 관점에서는 **레지스트리 도달을 방해하는 것만으로 차단을 우회**할 수 있습니다. 정책 파일 로드 실패(`vcps.py`)와 같은 처리라고 쓰셨지만 성격이 다릅니다 — 정책 로드 실패는 안전한 기본값으로 대체되지만, 차단 목록 조회 실패는 대체재가 없습니다.

**해소안 제안**:

1. 마지막 성공 응답을 로컬에 짧게 캐시(TTL 제안: 24시간). `REJECTED`는 캐시 만료 전까지 조회 실패와 무관하게 유지합니다.
2. 조회 실패를 `note` 한 줄이 아니라 **결과에 드러나는 열화 상태**로 남깁니다:

```python
requires_review: True
registry_status: "unreachable" | "unauthorized" | "ok" | "disabled"
```

3. 사용자 보고서에 "기관 레지스트리 조회 실패 — 차단 목록이 적용되지 않았습니다"를 표기합니다.

`unreachable`을 조용히 넘기면 "레지스트리가 승인했다"와 "레지스트리에 물어보지 못했다"가 사용자 화면에서 구분되지 않습니다.

### 2-3. `GVSKB_MODE=offline`에서의 네트워크 호출 — 사용자와의 계약 변경

"오프라인 모드면 외부로 나가지 않는다"가 현재 저희가 안내 문서·보고서·`doctor`에서 사용자에게 한 약속입니다. 레지스트리가 내부망이라도 offline 모드에서 HTTP를 켜는 것은 그 약속을 바꾸는 일이라 **묵시적으로 처리할 수 없습니다.**

코드 구조상으로도 offline 게이트가 `src/gvskb/tools/check_package.py:551`에서 조기 반환하므로, 플러그인을 그 앞단에 배치해야 합니다.

**해소안 제안**:

1. offline 모드에서의 레지스트리 사용은 **별도 명시 옵트인**으로 분리 (예: `GVSKB_REGISTRY_ALLOW_OFFLINE=1`). `GVSKB_REGISTRY_URL` 설정만으로 자동 활성화하지 않습니다.
2. `doctor`와 보고서에 **"오프라인 모드이나 레지스트리 `<host>`로 전송함"을 반드시 표기**합니다.

저희 도구는 남의 외부 전송을 지적하는 도구입니다. 자신이 무엇을 어디로 보내는지 밝히지 않으면 이중잣대가 됩니다.

## 3. 사실관계 정정 3건

귀 문서가 저희 코드를 인용한 부분 중 세 가지가 실제와 다릅니다. 스키마 설계에 영향이 있는 것은 3-1입니다.

### 3-1. `caller`는 `PackageCheckResult`의 필드가 아닙니다

§4.5는 "본문 = `PackageCheckResult.model_dump(mode="json")` **그대로**"라고 쓰고, 예시 JSON에 `"caller": "harness:auto"`를 포함했습니다. 그러나 `PackageCheckResult`의 필드 30개에 `caller`는 없습니다. MCP 서버가 `model_dump()` 이후 dict에 덧붙이는 값입니다(`src/gvskb/server.py:227`).

**제안**: `caller`를 모델 정식 필드로 올리기보다 **봉투(envelope) 방식**을 권합니다.

```json
{
  "result":       { ...PackageCheckResult.model_dump(mode="json") 그대로... },
  "caller":       "harness:auto",
  "submitted_at": "2026-08-01T05:00:00Z",
  "client":       "gvskb/0.3.0"
}
```

`result`는 변환 없이 그대로이므로 "변환 계층 불필요"라는 취지가 유지되고, 전송용 메타데이터가 판정 모델을 오염시키지 않습니다.

### 3-2. `VCPS-C4-CANONICAL`은 저희 `vcps-rules.yaml`에 없습니다

§8은 "`vcps-rules.yaml`의 규칙 중 유일한 미구현 항목"이라며 `- id: VCPS-C4-CANONICAL` 스니펫을 인용했습니다. 저희 `config/vcps-rules.yaml`은 **37줄이고 `rules:` 블록 자체가 없습니다** — `schema_version`, `doc_id`, `environments`, `default_env`, `license_allowlist`, `license_review_required` 뿐입니다.

C4는 상위 지침 문서 VCPS-2026-01 6장의 항목이지 저희 설정 파일의 항목이 아닙니다. 저희 파일은 그 지침의 **집행 가능한 부분만 발췌한 사본**입니다(파일 머리 주석에 명시).

요청 자체(정본 설치명령 대조)는 유효하므로 §5-P2-5에서 별도로 답합니다.

### 3-3. `record_scan` 호출 지점은 3곳입니다

§5는 `server.py:176`·`server.py:313` 두 곳으로 적으셨습니다. 실제로는 `detect_secrets_and_pii`(`server.py:195`)에도 있습니다. 또 `server.py:313`은 직접 호출이 아니라 `caller`를 스캐너로 전달하는 지점이고, 실제 기록은 `scanner.py:625`에서 일어납니다.

**결론(패키지 판정 계열에 감사 기록이 없다)은 정확합니다.** 요청은 그대로 유효합니다.

## 4. 추가로 정해야 할 사항

### 4-1. `expires_at` 검증 주체

§4.3 응답에 `expires_at`이 있으나 누가 검증하는지 정의되지 않았습니다. 응답이 `APPROVED`인데 `expires_at`이 과거인 경우가 문제입니다(캐시·시계 오차·레지스트리 버그).

**저희 제안**: gvskb가 `expires_at`을 확인해 **만료된 승인은 `UNDER_REVIEW`로 간주**합니다(안전한 쪽). 레지스트리가 만료 관리를 보증한다면 그 취지를 문서에 명문화해 주시면 저희 쪽 검증을 생략하겠습니다.

### 4-2. 토큰 위생

- `GVSKB_REGISTRY_TOKEN`이 `note`·감사로그·보고서·오류 메시지에 **절대 포함되지 않음**을 저희가 테스트로 고정하겠습니다.
- 역으로, `sk_ggtrust_` 접두사는 **저희 시크릿 탐지 룰로 추가할 가치**가 있습니다. 담당자가 스크립트에 하드코딩한 경우를 잡을 수 있습니다. 키 형식이 확정되면 정규식(접두사·길이·문자집합)을 알려 주십시오.
- §9-8의 `SUBMIT_ONLY` 스코프 분리에 동의합니다.

### 4-3. 전송 데이터의 개인정보성

`caller`에 사람·부서 식별자가 들어가면 개인정보가 됩니다. 감사 목적상 필요한 것은 이해하나, 값의 형식(예: 부서 코드까지만, 개인 식별자 금지)에 대한 기관 기준을 정해 주시면 저희가 그에 맞춰 안내하겠습니다.

### 4-4. verdict 열거형 확장의 파급 — 그리고 verdict 어휘가 둘이라는 점

값 추가의 파급 자체는 감당 가능한 규모입니다. 값을 **산출**하는 지점이 `check_package.py`에 11곳, 값을 읽어 **분기**하는 지점이 `cli.py:318`과 `report.py`의 5곳(1975·2002·2009·2030·2044)입니다. MCP 도구 설명문에도 값이 열거돼 있어 함께 갱신이 필요합니다. 저희가 전수 조사와 회귀 테스트를 선행하겠습니다.

**다만 연동 시 주의하실 점이 하나 있습니다. 저희 코드에는 `verdict`라는 이름의 필드가 두 종류 있습니다.**

| | `PackageCheckResult.verdict` | `audit_manifest()` 결과의 `verdict` |
|---|---|---|
| 대상 | 패키지 1건 | 매니페스트 1개(집계) |
| 값 | `malicious`·`not_found`·`vulnerable`·`cooldown_hold`·`checked_stale`·`checked_clean`·`unknown`·`error` (Literal 고정) | `blocked`·`review_required`·`ok`, 항목별로 `unparsed` |
| 타입 | Pydantic Literal | 평범한 dict 값 |

귀측이 확장을 요청하신 것은 **앞의 것**입니다. `unparsed`는 뒤쪽 어휘라 `PackageCheckResult`에 나타나지 않습니다 — §4.6에서 "`scan_dependencies` 결과는 제출하지 말라"고 쓰신 판단과 일치하며, 그 경로가 뒤쪽 어휘를 쓰는 경로입니다.

값 추가는 **스키마 확정 후 착수**해야 하므로 §2-1 결론이 먼저 필요합니다.

### P1-3 단서 — "목록이 크면 좋다"는 단순하지 않습니다

§6은 "50개로는 실무 패키지 대부분이 사각지대"라고 쓰셨습니다. 방향은 맞지만 **코퍼스가 커지면 오탐도 같이 커집니다.** 편집거리 임계값은 코퍼스 크기에 종속적이라, 50 → 500으로 늘리면 정상 패키지가 이웃을 갖게 되어 멀쩡한 패키지가 타이포스쿼팅으로 잡힙니다.

- 목록 크기와 임계값을 **함께** 조정하고, 그 근거를 저희 쪽 회귀 테스트로 고정하겠습니다.
- **임계값 정책은 gvskb가 계속 보유**하고, 외부화하는 것은 목록뿐으로 하겠습니다. 목록이 곧 탐지 정책이 되면 공급자가 탐지 범위를 쥐게 됩니다.
- 하드코딩 폴백은 유지합니다(귀측도 동의).
- 공급되는 목록의 **무결성 검증 수단**(서명 또는 sha256 사이드카)을 함께 제공해 주십시오. 인텔 번들과 같은 방식이면 됩니다.

### P2-5 축소판 제안

README 대조는 네트워크 접근과 HTML 파싱에 의존해 **오프라인에서 불가능**하고, 유지보수 부담이 큽니다(저희는 같은 이유로 상용툴 PDF 파싱 연동을 보류한 바 있습니다).

**대안**: 레지스트리 메타데이터의 정규 이름과 `project_urls`/`repository` 필드만 대조하는 축소판이면 이미 수집 중인 데이터로 가능하고 오프라인 캐시로도 동작합니다. `huggingface-cli` vs `huggingface_hub[cli]` 사례는 이 축소판으로도 잡힙니다. P2 유지에 동의합니다.

## 6. 착수 순서 제안

귀 문서 §0의 순서를 다음과 같이 조정할 것을 제안합니다.

| 순위 | 항목 | 근거 |
|---|---|---|
| 1 | **§2-1 verdict 부여 조건 합의** | 스키마가 여기에 걸려 있습니다. 이 문서 §1-10-2가 저희 답입니다 |
| 2 | **P0-2(감사로그) + P1-4(락파일)** | 둘 다 외부 의존 없음. P1-4는 레지스트리와 무관하게 저희 도구 가치가 크고, 락파일 지원이 없으면 레지스트리 저장 키(생태계·이름·버전)가 채워지지 않으므로 **연동의 선행 조건**이기도 합니다 |
| 3 | P1-3(코퍼스), P2-5(CANONICAL 축소판) | 독립 진행 |
| 4 | **P0-1(플러그인)** | 스키마 확정 + 엔드포인트 개설 후 |

P1-4를 앞으로 당기는 이유를 하나 더 붙이면, §7에서 지적하신 "전이 의존성이 매니페스트에 없다"가 맞고, 그 상태로 레지스트리에 제출하면 **저장되는 것이 실제 위험의 일부뿐**이기 때문입니다.
