# vibecode-checker(gvskb) ↔ gg-trusted-registry 연동 합의서

> **성격**: 두 시스템의 관계·경계·계약을 정의하는 **단일 원천 문서**.
> 라운드별 주고받은 문서는 근거 기록이고, **충돌하면 이 문서가 우선**합니다.
> **최종 개정**: 2026-08-02 (R8 구현 단계 반영 — §7-4 참조)
> **협상 기간**: 2026-07-31 ~ 2026-08-02, 총 5개 문서 왕복

---

## 1. 두 시스템은 무엇이고, 왜 나뉘어 있는가

| | **vibecode-checker (gvskb)** | **gg-trusted-registry** |
|---|---|---|
| 성격 | 범용 오픈 보안 점검 도구(MCP) | 경기도 기관 서비스 |
| 산출물 | `PackageCheckResult` — **관측** | `APPROVED`/`REJECTED` — **판정** |
| 뜻하는 바 | "지금 조회해 보니 이렇다" | "경기도가 이렇게 정했다" |
| 수명 | 1회성(검사 시점) | 승인 + 만료(`expires_at`) |
| 권한 | 승인 권한 **없음** | 승인·차단 권한 보유 |
| 보는 것 | 코드·패키지 메타데이터 | 패키지 이름·버전·판정 이력 |
| 배포 | 공개(PolyForm NC + 수급사업자 예외) | 기관 내부 |

**나눈 이유**: 관측은 누구나 재현할 수 있어야 하고, 판정은 기관이 책임져야 하기 때문입니다.
gvskb에 승인 권한을 넣으면 도구가 기관을 대신해 결정하게 되고, 레지스트리가 코드를
보게 하면 기관 서비스가 소스 코드 보관 책임을 지게 됩니다. 둘 다 피합니다.

## 2. 관계를 지배하는 5개 원칙

이 원칙들은 개별 스펙보다 상위입니다. 스펙이 원칙과 충돌하면 스펙을 고칩니다.

### 원칙 1 — 의존은 단방향이다

**레지스트리가 없어도, 죽어도, 느려도 gvskb는 온전히 동작합니다.**
연동은 `GVSKB_REGISTRY_URL` 환경변수 옵트인이며, 미설정 시 기존 경로와 100% 동일합니다.
gvskb는 범용 도구로 남고, 기관 전용 로직은 플러그인 경계 안에만 둡니다.

### 원칙 2 — 관측과 판정을 섞지 않는다

gvskb는 `requires_review`까지만 말하고 승인/거절을 말하지 않습니다.
레지스트리는 gvskb 결과를 **관측 데이터로** 받되, 그것을 근거로 한 판정은 자기 책임입니다.
그래서 gvskb가 만든 `registry_approved`/`registry_rejected`는 레지스트리에 저장되지
않습니다 — 자기가 준 답이 돌아온 것이라 관측이 아니기 때문입니다(§5-C).

### 원칙 3 — fail-open, 그러나 침묵은 금지

레지스트리 장애가 검사를 멈추게 해서는 안 됩니다. 동시에, 조회하지 못한 것이
"승인받았다"처럼 보여서도 안 됩니다. 두 요구를 함께 만족시키는 방법이 `registry_status`
필드와 보고서 배너입니다(§4-4).

### 원칙 4 — 로컬 탐지가 최종 안전망이다

**기관 승인도 로컬 악성·KEV 대조를 건너뛰지 못합니다.** 승인은 시점의 판단이고 위협
정보는 그 뒤에도 갱신됩니다. 승인된 버전이 나중에 악성으로 등재되면 승인이 그것을
가려서는 안 됩니다(§4-2).

### 원칙 5 — 알림 단위는 조치 단위를 따른다

시스템 수준 열화(레지스트리 도달 실패, 인텔 캐시 낡음)는 **보고서 배너 1개**로,
패키지 수준 판정만 패키지별로 알립니다. 같은 사유로 수백 줄이 뜨면 담당자는 그것을
무시하게 되고, 무시가 습관이 되면 그 사이의 진짜 위험도 함께 묻힙니다.
**경고 피로는 그 자체로 탐지력 저하입니다.**

## 3. 데이터 흐름 — 무엇이 오가고, 무엇이 절대 오가지 않는가

```
                    ┌─────────────────────────────────────┐
                    │  ① 조회                              │
   gvskb  ─────────▶│  패키지명 · 버전 · 생태계 · 환경등급  │──▶ registry
                    └─────────────────────────────────────┘
                    ┌─────────────────────────────────────┐
   gvskb  ◀─────────│  ② 판정                              │◀── registry
                    │  APPROVED / REJECTED /              │
                    │  UNDER_REVIEW / UNKNOWN + max_env   │
                    └─────────────────────────────────────┘
                    ┌─────────────────────────────────────┐
                    │  ③ 제출(관측 데이터)                 │
   gvskb  ─────────▶│  PackageCheckResult 원본 + 봉투     │──▶ registry
                    └─────────────────────────────────────┘
```

### 절대 전송하지 않는 것

| 항목 | 이유 |
|---|---|
| **소스 코드 · 코드 조각** | 검사 대상은 기관 내부 자산이다. 도구가 이를 외부로 보내면 도구 자체가 유출 경로가 된다 |
| **파일 경로** | 기관 내부 구조가 드러난다 |
| **개인 식별자** (이름·이메일·사번·PC명·IP) | 감사에 필요한 것은 "무엇이 호출했는가"이지 "누가"가 아니다 |

`caller` 값 규칙: `<출처>:<모드>[:부서코드]` — 예 `harness:auto`, `cli:manual`.
부서코드는 **선택 항목**입니다. 소규모 부서에서는 부서코드 + 시각 + 패키지 조합이
개인으로 좁혀질 수 있기 때문입니다.

## 4. 판정 규칙 (확정)

### 4-1. verdict 사다리

```
malicious > registry_rejected > not_found > vulnerable > cooldown_hold
          > checked_stale > registry_approved > checked_clean > unknown > error
```

- `malicious`가 최상위 — 로컬 탐지가 기관 판정보다 위(원칙 4)
- `registry_rejected`가 `not_found`보다 위 — 기관의 명시적 차단이 더 강한 신호
- `registry_approved`가 `checked_clean`보다 위 — 사람이 확인한 것이 자동 판정보다 강함

### 4-2. `registry_approved` 부여 3분기 ★

```
레지스트리 APPROVED 응답
 ├ 인텔 캐시 신선 + 악성·KEV 미적중
 │    → registry_approved / checked=True  / requires_review=False
 │
 ├ 인텔 캐시 신선 + 적중
 │    → malicious · vulnerable 이 이김
 │
 ├ 인텔 캐시 **낡음**(있으나 오래됨)
 │    → registry_approved / checked=False / requires_review=False
 │      + 보고서 배너 "인텔 캐시 N일 경과 — 번들 반입 필요"
 │      + cache_stale_sources 에 근거 기록
 │      + 경과 30일 초과 시 requires_review=True
 │
 └ 인텔 캐시 **없음**(한 번도 대조한 적 없음)
      → registry_approved / checked=False / **requires_review=True**
```

**'낡음'과 '없음'을 반드시 구분한다.** 캐시가 아예 없으면 로컬 악성 대조를 한
번도 못 한 상태이고, 이는 특히 **첫 배포일에 자연스럽게 발생**한다 — 캐시 0,
로컬 검증 0, 승인 건은 전부 통과. 원칙 4가 정확히 무력화되는 구간이라 배너로
넘기지 않고 검토로 올린다. 캐시 없음은 초기 1회만 발생하므로 경고 피로를
일으키지 않으며, 오히려 "번들을 반입하라"는 신호가 되어 목적에 맞는다.

**생략되는 것은 원격 OSV 조회뿐입니다.** 로컬 인텔 캐시 대조는 어떤 경로에서도
생략하지 않습니다.

세 번째 분기가 원칙 4와 원칙 5의 절충점입니다. 캐시가 낡은 것은 **번들 반입 한 번으로
풀리는 시스템 문제**라 패키지 수백 건을 개인 검토로 올릴 일이 아닙니다. 대신
`checked=False`로 정직하게 표시하고, 무한정 봐주지 않도록 30일 상한을 둡니다.

> 30일은 양측이 우연히 같은 값을 씁니다(레지스트리 `rescan_stale_days`). 다만
> **서로 독립적인 기준**입니다 — gvskb는 인텔 캐시 신선도, 레지스트리는 판정 신선도.
> 한쪽이 바뀌어도 다른 쪽을 맞출 필요가 없습니다.

### 4-3. `checked` 의미

`checked`는 "이번에 취약점 검사를 실제로 수행했는가"입니다. 3분기 규칙에 따라
캐시가 신선하면 `True`, 아니면 `False`입니다. **`False`는 '안전'이 아니라 '판정 못 함'입니다.**

레지스트리 측에 `checked`를 조건으로 쓰는 로직은 없습니다(자동 승인 판정은
`verdict`·`cooldown.ok`·`max_cve`·`in_kev`·`exists`·`license_verdict`·`install_scripts`·
`deprecated`·타이포스쿼팅·`env_grade`를 봅니다). 저장만 합니다.

### 4-4. 열화 신호의 계층

| 열화 | 표시 방법 | `requires_review` |
|---|---|---|
| 레지스트리 도달 실패 | **보고서 배너 1개** + `registry_status` | 승격 **안 함** |
| 인텔 캐시 낡음 | **보고서 배너 1개** + `checked=False` | 승격 **안 함**(30일 초과 시 예외) |
| 개별 패키지 판정 불가 | 패키지별 표시 | **승격함** — 진짜 패키지 문제 |

`registry_status`: `ok` | `unreachable` | `unauthorized` | `disabled`

### 4-5. 캐시 TTL

| 상태 | TTL | 만료 시 |
|---|---|---|
| `REJECTED` | **7일** | **삭제하지 않고 '낡은 차단'으로 강등해 계속 표시** |
| `APPROVED` | 1시간 | 삭제 (철회 전파 지연 최소화) |
| `UNDER_REVIEW` / `UNKNOWN` | 캐시 안 함 | — |

**만료 = 삭제가 아니라 강등**이 `REJECTED`의 핵심입니다. 차단 사실이 사라지는 것과
오래된 것은 다릅니다. 그렇지 않으면 조회를 방해하는 것만으로 차단을 우회할 수 있습니다.

### 4-6. `expires_at` — 양쪽 다 검사

- **레지스트리(서버)**: 만료된 승인은 `APPROVED`로 응답하지 않습니다.
- **gvskb(클라이언트)**: 그래도 검사합니다. 만료된 승인은 `UNDER_REVIEW`로 취급합니다.

중복이지만 유지합니다 — 시계 오차·캐시·서버 버그에 대한 안전망이고 비용이 없습니다.

## 5. API 계약 (확정)

### 5-A. 조회

```http
POST /api/v1/packages/check-bulk     # 최대 200건 — 기본 경로
GET  /api/v1/packages/check          # 단건 — check_package 단건 호출에만
Authorization: Bearer sk_ggtrust_...
```

- `env_grade`는 **요청 단위**(항목별 아님). 매니페스트 하나는 보통 한 환경에서 쓰임
- 응답은 요청 순서와 무관하게 **`purl`로 대조**
- **부분 실패 허용** — 일부 실패해도 나머지 반환

### 5-B. 제출

```http
POST /api/v1/packages/submit-batch   # 최대 200건, 부분 실패 허용 — 기본 경로
POST /api/v1/packages/submit-check   # 단건
```

봉투(envelope) 최종형:

```json
{
  "result":        { "...PackageCheckResult.model_dump(mode=\"json\") 원본 그대로..." },
  "caller":        "harness:auto",
  "submitted_at":  "2026-08-01T05:00:00Z",
  "client":        "gvskb/0.3.0",
  "engine_commit": "a1b2c3d4",
  "source_scope":  "lockfile"
}
```

`result`는 변환 없는 원본입니다. 전송용 메타데이터는 봉투에만 둡니다 — 판정 모델을
전송 사정으로 오염시키지 않기 위해서입니다.

`engine_commit`은 **`null` 허용**입니다. 배포본에는 git 메타데이터가 없어 대부분
`null`이 됩니다. 재현성 근거로는 `engine_version` + `threat_intel_snapshot_at` +
`checked_at`이 이미 있으므로 감사 요건에 걸리지 않습니다. **가짜 값을 채우느니
`null`이 낫습니다.**

### 5-C. `source_scope` — 심사 대기열 보호

| 값 | 관측 저장 | 심사 대기열 |
|---|---|---|
| `single` (기본값) | ○ | **올림** |
| `manifest` | ○ | 올림 |
| `lockfile` | ○ | **올리지 않음** |
| `installed` | ○ | **올리지 않음** |

셋 다 관측으로 저장됩니다. 다른 것은 사람의 심사 대기열에 올리는지뿐입니다.
락파일은 한 번에 수백~수천 건이라, 큐에 그대로 쌓이면 레지스트리 도입 목적
("N명이 같은 패키지를 재심사하지 않게 한다")과 정반대가 됩니다.

### 5-D. 제출하지 않는 것 (gvskb 측 필터)

| 조건 | 이유 |
|---|---|
| `verdict in (unknown, error)` | 판정이 아니라 "판정 못 함". 일시적 장애가 영구 기록으로 굳는다 |
| `version is None` | 특정 버전의 사실이 아니다 |
| **`verdict in (registry_approved, registry_rejected)`** | **레지스트리가 준 답이 되돌아온 것 — 관측이 아니다** |

레지스트리는 마지막 항목을 받아도 `200 OK` + `action: IGNORED_REGISTRY_ECHO`로
안전하게 무시하지만, **애초에 보내지 않는 것이 맞습니다.**

### 5-E. `action` 응답값

| 값 | 의미 |
|---|---|
| `REGISTERED` / `UPDATED` | 저장됨 |
| `SKIPPED_COOLDOWN` | 24시간 내 재제출 |
| `IGNORED_NON_VERDICT` | `unknown`/`error` |
| `IGNORED_NO_VERSION` | 버전 미지정 |
| `IGNORED_REGISTRY_ECHO` | 레지스트리 자신의 판정이 되돌아옴 |

전부 HTTP 200입니다.

### 5-F. 부하 — 권고값 (서버 강제 없음)

| 항목 | 권고 |
|---|---|
| 클라이언트 1대당 동시 요청 | **8** |
| 배치 vs 단건 | 단건 200회보다 **배치 1회** |
| 배치 크기 | 조회·제출 모두 200건 |
| 재시도 | 지수 백오프, 최초 대기 1초 이상 |

레지스트리에 rate limit 미들웨어가 아직 없습니다(설정 화면의 값은 저장만 되고
집행되지 않음). 이는 의도가 아니라 구멍이며, 레지스트리 과제로 등록돼 있습니다.
**값을 먼저 정해 걸면 워커나 플러그인이 알고 있는 사이 막힐 수 있어**, 관측 후
결정하는 순서를 택했습니다.

## 6. 실행 환경 계약

### 6-1. 환경변수

| 변수 | 필수 | 효과 |
|---|---|---|
| `GVSKB_REGISTRY_URL` | — | **미설정 시 플러그인 전체 비활성**(기존 동작 100% 동일) |
| `GVSKB_REGISTRY_TOKEN` | 설정 시 필수 | `sk_ggtrust_[A-Za-z0-9]{32}` (총 43자) |
| `GVSKB_REGISTRY_TIMEOUT` | — | 초. 기본 3.0 |
| `GVSKB_REGISTRY_SUBMIT` | — | `0`이면 조회만. 기본 `1` |
| `GVSKB_REGISTRY_ALLOW_OFFLINE` | — | **오프라인 모드에서 레지스트리 사용을 별도 옵트인** |

### 6-2. 오프라인 모드

`GVSKB_MODE=offline`은 사용자에게 "외부로 나가지 않는다"고 약속한 상태입니다.
레지스트리가 내부망이라도 그 약속을 조용히 바꿀 수 없습니다.

- 별도 옵트인(`GVSKB_REGISTRY_ALLOW_OFFLINE=1`)이 있어야 동작
- `doctor`와 보고서에 **"오프라인 모드이나 레지스트리 `<host>`로 전송함"** 표기

### 6-3. 성능

조회와 자체 분석을 **병렬**로 실행합니다. 직렬이면 지연이 둘의 합이 되어
"조회가 자체 분석보다 느리면 의미 없다"는 전제에 어긋납니다.
`APPROVED`가 오면 **원격 OSV 결과만 버리고 로컬 대조는 유지**합니다.

## 7. 결정 연혁 — 무엇이 언제 왜 바뀌었는가

문서 왕복 순서: **R1**(요청서 v1) → **R2**(회신) → **R3**(답신 v2) → **R4**(회신 r3) → **R5**(답신 v3) → **R6**(최종 회신 r4).

### 7-1. 설계 결정 변경

| 라운드 | 항목 | 이전 | 이후 | 제기 | 근거 |
|---|---|---|---|---|---|
| R2→R3 | `APPROVED` 처리 | 즉시 반환, 자체 분석 생략 | **로컬 인텔 대조는 항상 수행** | gvskb | 요청서 내부 모순. 즉시 반환하면 "malicious 최상위"가 실효 없음. 승인 후 악성 등재 시 만료까지 초록불 |
| R2→R3 | 조회 실패 | fail-open만 | **+ TTL 캐시 + `registry_status` + 보고서 표기** | gvskb | fail-open이 차단 방향에서는 차단 무력화. 조회 방해만으로 우회 가능 |
| R2→R3 | 오프라인 모드 | "offline이어도 조회" | **별도 옵트인 + 표기** | gvskb | 사용자와의 약속 변경을 묵시적으로 할 수 없음 |
| R3 | `caller` 위치 | `result` 최상위 | **봉투로 분리** | gvskb | `PackageCheckResult` 필드가 아님(사실 오류) |
| R3 | `engine_version` | SHA 포함 요청 | **`engine_commit` 별도 필드** | gvskb | "코드 버전 == 배포 메타데이터" 불변식과 충돌 |
| R4→R5 | 조회 실패 표시 | 패키지마다 `requires_review=True` | **보고서 배너 1개** | gvskb **자진 수정** | 락파일 800건이면 검토 항목 800개. 경고 피로 = 탐지력 저하 |
| R4→R5 | `registry_approved` 조건 | "로컬 대조 통과" | **"신선한 캐시로 대조 통과"** 3분기 | gvskb | 캐시가 비면 '통과'가 아니라 '판정 불가'. 조건이 공허해짐 |
| R4→R5 | `checked` 값 | `registry_approved`면 `False` 고정 | **캐시 신선도에 따라 True/False** | gvskb | 로컬 대조를 실제로 수행하므로 고정값이 사실과 다름 |
| R4→R5 | `REJECTED` TTL | 24시간 | **7일 + 만료는 강등** | gvskb | 24시간 넘긴 장애에서 차단이 조용히 풀림 |
| R4→R5 | `source_scope` | (없음) | **신설**, `lockfile`은 큐 미투입 | gvskb | 락파일 대량 제출이 담당자 심사 큐를 덮음 |
| R5 | `engine_commit` 위치 | `result` 안 | **봉투로 이동** | registry **자진 수정** | `result`는 원본이라는 자기 원칙과 모순 |
| R5 | 조회 배치 상한 | 100건 | **200건** | registry | gvskb 제안 수용 |
| R5 | `manifest` 큐 투입 | "정책에 따라"(미정) | **올림** | registry | `scan_dependencies`는 기본 20·상한 100이라 큐가 감당 |
| R6 | 라이선스 | PolyForm NC 원문 | **+ 수급사업자 사용 추가 허가** | registry가 제기, gvskb가 조치 | PolyForm NC는 기관 자신의 사용만 허용. 공공사업 용역사 경로가 통째로 막힘 |

### 7-2. 상호 검토로 드러난 결함

| 발견 | 어느 쪽 | 내용 | 처리 |
|---|---|---|---|
| R3 | **registry 자진 보고** | `expires_at`을 응답에 싣기만 하고 검사하지 않음 | 서버 수정 + 클라이언트 검사도 유지 |
| R3 | **registry 자진 보고** | 승인 후 악성 판정된 패키지의 **철회(revocation) 경로 부재** | 레지스트리 별도 과제 |
| R5 | **registry 자진 보고** | 합의한 verdict 2종을 자기 enum에 넣지 않아 **422로 거부 중이었음** | 수정 + `IGNORED_REGISTRY_ECHO` |
| R5 | **registry 자진 보고** | rate limit 미들웨어 부재(설정값은 저장만 됨) | 관측 후 값 결정 |
| R5 | **registry 자진 보고** | v1 문서에서 `check-bulk` 존재를 누락해 gvskb가 "신규 요구"로 설계 | 문서 정정 |
| R4 | **gvskb 자체 발견** | `sk-`(하이픈)만 마스킹해 `sk_ggtrust_…` 토큰이 **로그·보고서에 그대로 노출** | `sk[-_]`로 일반화 |
| R4 | **gvskb 자체 발견** | 패키지 판정 계열 도구에 **감사 기록이 아예 없음** | `package_check` 이벤트 추가 |
| R4 | **gvskb 자체 발견** | PolyForm NC가 라이선스 목록에 없어 `unknown` 판정 | `license_review_required` 등재 |
| R7 | **registry 자진 보고** | 배치 API가 **부분 실패를 허용하지 않았음**(항목 1건 오류 → 200건 전체 422). 합의 §5-A·§5-B 위반 | 수정 진행 중 |
| R7 | **registry 자진 보고** | `caller` 개인식별자 규칙이 서버에서 강제되지 않음 | 서버 검증 추가 |
| R7 | **gvskb 자체 발견** | 같은 규칙이 **우리 쪽에도 없었음** — `caller` 는 우리 감사로그에도 들어가므로 개인식별자가 섞이면 감사 기록이 오염된다 | 클라이언트 검증 추가 |
| R7 | **gvskb 자체 발견** | `lookup_batch` 가 모든 실패를 `except Exception` 으로 뭉개어 422(재시도 무의미)와 연결 실패(재시도 유효)를 구분하지 못함 | 분리 |
| R7 | **gvskb 자체 발견** | `apply_registry_decision` 이 `stale` 표식을 읽지 않아 낡은 차단과 신선한 차단의 안내가 같음(판정은 옳으나 표시 부족) | 표시 보완 |
| R8 | 구현 진행 상황 공유 | — | P1-4 완료를 알리지 않아 상대가 "미완성" 전제로 반입 스크립트 설계 중이었음 |

### 7-4. R7 이후 결정 (구현 단계)

설계 협상은 R6 로 종료됐으나, 구현 중 **스키마에 영향을 주는 결정**이 나왔다.
합의서 개정이 필요한 항목만 기록한다.

| 라운드 | 항목 | 결정 | 근거 |
|---|---|---|---|
| R8 | `source_scope` 에 **`installed` 추가** | 설치본 인벤토리 경로도 플러그인을 타므로 4번째 값이 필요. 심사 큐 정책은 `lockfile` 과 동일 | 값이 없으면 enum 검증에 걸려 배치 전체가 422 — 상대가 R5 에서 자백한 실패를 반대 방향에서 반복하게 된다 |
| R8 | **반입 번들** 신설 | `--registry-bundle` + `.check-reports/` 사이드카(+`.sha256`). 봉투 형식 그대로, `findings`·경로·코드 일체 제외 | 리포트 전체를 올리면 코드 조각과 파일 경로가 레지스트리를 거친다(§3 위반). **무엇을 보내도 되는지 판단하는 주체가 소비자가 아니라 생산자여야 한다** |
| R8 | §4-2 세 번째 분기 **문서 정정** | "캐시 낡음·없음"을 **낡음**과 **없음**으로 분리 표기 | 코드는 이미 구분하고 있었고 문서만 뭉뚱그렸다. 상대가 코드보다 덜 정확한 문서를 읽고 지적 |
| R8 | **§10 하네스 집행계약 신설** | 별도 문서(`하네스_집행계약.md`)로 작성해 편입 | 두 시스템이 판정을 만들고 저장하지만 실제로 막는 곳이 계약에 없었다 |
| R8 | 카탈로그 **불변식** 확정 | 로컬 카탈로그는 레지스트리의 `REJECTED` 를 덮을 수 없다(형식 무관) | 카탈로그는 파일이고 레지스트리는 사람이 관리하는 최신 판정. 카탈로그 항목은 한 번 적히면 지워지지 않아, 과거 한 줄이 현재의 차단을 무력화한다 |
| R8 | **하네스 운영 정책 4/5 확정** | MONITOR 시작 · `unknown` 비율 10%(직접 의존성) 3주 연속 시 ENFORCE · 카탈로그 §6-3 | 기관 결정(2026-08-02) |
| R8 | **`unknown` 차단을 직접 의존성에만 적용** | 전이 의존성은 "미등록"만으로는 차단하지 않음(절대 규칙은 그대로 적용) | 전이까지 등록을 요구하면 심사 큐가 감당 못 하고, 이는 §5-C(락파일은 큐에 안 올림)와 정면으로 어긋난다. 이 구분이 없으면 ENFORCE 전환 기준이 영원히 충족되지 않는다 |
| R8 | **우회 시 레지스트리 통보 경로 부재 발견** | 봉투에 `override` 필드 제안 + §5-D 예외 필요 | 기관이 차단한 패키지가 우회로 설치된 사실은 심사 대기열의 어떤 항목보다 우선하는 정보인데 알릴 방법이 없었다 |
| R8 | 타이포스쿼팅 차단 수위 | 상대 제안(전 모드 차단)을 **채택하지 않음** — ENFORCE 에서만 차단 | `not_found` 는 조회로 확정되는 **사실**이지만 타이포스쿼팅은 편집거리 **휴리스틱**이라 오탐이 실재한다. MONITOR 구간에서 휴리스틱 차단은 "하네스는 멀쩡한 걸 막는다"는 인상을 먼저 만들고, 그러면 진짜 차단도 우회 대상이 된다 |

> **원본 확인 표시**: registry 측 결함 5건은 모두 **그쪽 보고**입니다. gvskb 개발자는
> 해당 저장소에 접근할 수 없어 검증하지 않았으며, 검증한 사실로 기록하지 않습니다.
> gvskb 측 결함 3건은 원본 코드에서 재현·확인했습니다.
