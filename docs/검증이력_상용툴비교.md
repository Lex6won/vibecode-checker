### 3.3 라운드 2에서 새로 발견 — BOM 결함 (자체 발견)

**증상**: BOM(`U+FEFF`)으로 시작하는 Python 파일은 **AST 분석이 통째로 건너뛰어짐**.

```
app.py           → BOM 있음 → ast.parse 실패(invalid non-printable character U+FEFF)
app_20260607.py  → BOM 있음 → 동일
결과: AST 정밀 판정(SQL 테인트·무한루프)이 적용되지 않고 regex로만 검사됨
```

- 원인: `scanner.py`가 `encoding="utf-8"`로 읽어 BOM이 문자로 남음 (`utf-8-sig`면 정상 파싱)
- 영향 범위: **Windows·한글 환경에서 매우 흔함**. 이 프로젝트의 가장 큰 두 파일(138KB·136KB)이 해당
- 결과: §2.4의 남은 critical 2건이 바로 이 때문. 즉 **P0 수정이 정작 대상 파일에 적용되지 않았음**
- 예상 수정: `read_text(encoding="utf-8-sig")` 1줄 + 회귀 테스트

> 이 결함은 "조용한 성능 저하"라 가장 위험한 유형입니다. 도구는 정상 동작한 것처럼 보이지만 정밀 엔진이 꺼집니다.

`dependency_audit` 는 리포트의 부가 필드일 뿐 `summary` 에 합류하지 않았고,
`_deploy_status()` 는 소스 발견만 봤습니다. 깨끗한 소스 1개 + `pillow==12.2.0` 만으로 재현:

```
## 결론
> ### 배포 승인 가능          ← 초록불
## 의존성(패키지) 취약점 검사
> 취약·악성 1건 · **차단 권고**   ← 같은 문서가 스스로 모순
```

응소ON 은 소스 차단 2건이 있어 우연히 빨간불이 떴을 뿐, **소스가 깨끗하고 패키지만
위험한 프로젝트는 초록불**을 받았습니다. 담당자가 가장 먼저 읽는 곳이라 원칙 4 의
정확한 사례입니다. 인계 문서의 "0113 회차 22건 판정 불가" 우려도 이 결함의 한 증상입니다.

*조치*: `_dep_risk()`·`_dep_verdict_clause()` 신설, `_deploy_status()`/`_deploy_verdict()`
가 의존성을 함께 판정 — 차단 패키지→빨강, 취약·미존재·판정불가→주황, 전부 이상 없음→초록 유지.

**② `.min.` 제외 규칙이 진짜 취약 컴포넌트를 가림**

`_looks_like_build_artifact_name()` 이 파일명에 `.min.` 만 있으면 '빌드 산출물'로
제외했습니다. 그러나 `static/` 에 직접 떨궈진 `*.min.js` 는 빌드 출력이 아니라
**벤더링된 서드파티 라이브러리**입니다. 이 프로젝트에는 `package.json`·락파일·
`node_modules` 가 **하나도 없어**(확인함) 매니페스트 SCA 도, 설치본 npm 경로도
발동하지 않았습니다 — **이중 사각지대**로 아무도 그 파일을 보지 않았습니다.

라운드 2 §3.1-5 는 "SCA/라이선스 범위(wheel·venv·**min.js**)"를 백로그로 잡았지만,
wheel·venv 만 연결하고 닫혔습니다. **복합 항목을 한 줄로 닫으면 남은 절반이 사라진다** —
그 절반이 위 CVE 2건이었습니다.

*조치*: `.min.js` 를 빌드 산출물에서 분리해 `VENDOR_BUNDLE_SKIP_REASON` +
`report.vendor_bundles` 로 라우팅(소스 룰 검사는 계속 제외 — 오탐 방지 원래 의도 유지),
`tools/vendor_bundle.py` 신설, CLI·MCP 배선.

버전 식별의 핵심은 **이름 토큰이 인접한 `.version=` 대입만 채택**하는 것입니다.
`xlsx.full.min.js` 에는 `.version=` 이 3개(0.18.5·1.2.0·1.2.1) 있고 뒤 둘은 번들된
하위 라이브러리(SSF·CFB)입니다. 근거가 없으면 **추측하지 않고** `version=None` →
판정 불가로 남깁니다(`qrcode.min.js` 가 이 경우 — 스패로우는 여기서 9개 버전을 지어냈습니다).

> **범위를 넓힌 지점** — CLI 만 배선하면 MCP(IDE)로 쓰는 담당자에게 수정이 닿지 않아
> 에이전트가 없는 단계를 스스로 만들어내야 했습니다. `scan_vendor_bundles` MCP 도구와
> 서버 지침 2-1 을 함께 넣었습니다. **안 쓰이는 보안 도구는 보안 효과가 0입니다.**

### 4.7.7 남은 개선 여지 (다음 라운드 후보)

| 관찰 | 내용 | 우선순위 |
|---|---|---|
| 동일 컴포넌트 중복 계상 | 응소ON 리포트 "취약 패키지 3건" = pillow(매니페스트) + pillow(설치본) + pip. **고유 취약 컴포넌트는 2종**인데 알림은 3건 — 조치 단위와 알림 단위 불일치(원칙 6). 스패로우가 같은 오류를 3배(pillow 106건)로 저지른 것과 **종류가 같다**. `(생태계, 정규화 이름, 버전)` 으로 병합하고 출처를 한 행에 나열할 것 | 중 |
| 내용 기준 미니파이드 `.js` | 파일명에 `.min.` 이 없지만 내용이 미니파이드인 `.js` 는 여전히 '빌드 산출물'로 조용히 제외됨 — 개선 2 의 남은 절반 | 중 |
| 미사용 벤더 파일 | `static/qrcode.min.js` 는 **어떤 템플릿도 로드하지 않음**(QR 은 서버에서 python `qrcode` 8.2 로 생성). 죽은 벤더 파일은 공격면만 늘림 — 응소ON 쪽 정리 사항이나 "참조되지 않는 벤더 자산" 신호는 검토 가치 있음 | 낮음 |
| 0113 회차 리포트 부재 | `.check-reports/` 에 `0113` 파일이 없어 "설치본 22건 판정 불가"를 원본으로 재확인하지 못했습니다. **인계 기록으로만 둡니다**(원칙 1). 다만 그 우려가 가리키던 구조적 결함은 §4.7.4① 에서 독립적으로 재현·수정 | 기록 |

> **작업 메모** — 스패로우 PDF 는 라벨 안에 NUL 바이트가 박혀 있습니다
> (`컴포넌트\x00이름`, 총 58,700개). ripgrep 이 바이너리로 보고 **조용히 0건**을
> 반환하므로, 같은 PDF 를 다시 다룰 때는 NUL 제거 후 검색해야 합니다.
