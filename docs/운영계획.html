VIBECODE-CHECKER · 운영 부속 문서

향후 운영 계획 — 최신성과 점검 품질을 지속 유지하는 방법

보안 도구는 만든 날이 아니라 운영하는 동안 가치가 결정됩니다. 이 문서는 vibecode-checker가 시간이 지나도 ① 최신 위협을 반영하고 ② 의미 있는(믿을 수 있는) 점검 결과를 내도록 유지하는 주기·역할·절차를 정의합니다.

01운영의 3층 구조 — 무엇을 누가 갱신하나

갱신 대상을 세 층으로 나누면 운영이 단순해집니다. 층마다 갱신 주체와 주기가 다르며, 아래층일수록 자동화 비중이 높습니다.

층내용갱신 주체·주기방치되면?
① 데이터층
전자동		 위협 인텔 캐시(OSV 악성·CISA KEV·NVD·EPSS) — 패키지 판정·점수 병기의 근거 GitHub Actions
매일 03:00 자동		 30일 초과 시 도구가 스스로 '이상 없음'을 판정 보류로 강등 — 거짓 안심 없음
② 지식층
사람 게이트		 보안 룰 216장(탐지 패턴+지침) — 검사의 내용. KEV 초안 룰 PR + 출처 가이드 개정 반영 유지관리자·기여자
주간(PR)·반기(개정)		 기존 룰은 계속 유효하게 동작. 새 위협 유형만 미커버 — review_due로 재검토 시점 관리
③ 품질층
회귀 자동		 테스트 471개·독립 벤치마크(30시드+경계 프로브)·룰 예제 메타테스트 — 점검이 '의미있게' 유지되는 장치 CI(push·PR마다 자동)
벤치마크는 릴리스 전 필수		 CI가 룰·코드 변경을 막아줌 — 품질 저하 커밋은 병합 불가

실패-안전(fail-safe) 원칙 — 이미 내장됨

운영이 잠시 끊겨도 도구는 거짓말하지 않습니다: 캐시가 오래되면 checked_stale, 없으면 unknown(exit≠0), 리포트에는 기준일이 자동 표기됩니다. 운영의 목표는 "끊기지 않게"가 아니라 "판단 보류 상태를 빨리 해소하게"입니다.

04"의미 있는 점검"을 유지하는 품질 원칙

최신성보다 어려운 것이 점검 결과에 대한 신뢰 유지입니다. 오탐이 쌓이면 경고가 무시되고(양치기 소년), 미탐이 숨으면 거짓 안심이 생깁니다. 다음 4개 원칙을 모든 변경에 적용합니다.

원칙 1 — 오탐 0 게이트: 모든 룰은 자기 반례를 갖는다

룰마다 examples.positive(잡아야 할 코드)와 examples.negative(잡으면 안 되는 안전한 코드)가 필수이며, 메타테스트가 전 룰을 자동 검증합니다. negative를 깨뜨리는 패턴 변경은 CI에서 병합이 차단됩니다.

원칙 2 — 정밀화 ≠ 민감도 낮추기

오탐을 줄일 때 룰을 끄거나 느슨하게 만들지 않습니다. 대신 더 정밀한 엔진 (AST taint 등)으로 옮기고, 독립 벤치마크로 미탐이 늘지 않았음(recall 유지)을 확인한 뒤에만 반영합니다. 완화가 필요한 개별 사례는 룰 수정이 아니라 승인된 예외(사유·승인자·만료 필수)로 처리해 기록을 남깁니다.

원칙 3 — 현장 신고를 회귀 자산으로 전환

기관에서 오탐·미탐이 신고되면 일회성 수정으로 끝내지 않습니다:

  1. 신고 코드를 익명화·최소화(기관 정보·실데이터 제거)
  2. 미탐이면 벤치마크 시드로 추가(manifest 라벨링), 오탐이면 해당 룰의 negative 예제로 추가
  3. 룰·엔진 수정 → 전체 테스트+벤치마크 통과 확인 → 병합

이렇게 하면 같은 문제가 영구히 재발 방지되고, 벤치마크가 실제 공공 코드 분포를 점점 닮아가 측정의 의미가 커집니다.

원칙 4 — 측정의 정직성: 좋은 숫자와 나쁜 숫자를 함께 공개

recall 100%(30시드)와 함께 경계 프로브 4/9(난독화·별칭 미탐)를 항상 같이 공개합니다. 벤치마크가 쉬워져서 좋아 보이는 것을 막기 위해, 시드를 추가할 때는 탐지 가능 경계 밖의 hard 케이스도 함께 추가합니다(프로브가 전부 잡히면 더 어려운 프로브를 보충).

# 릴리스 전 필수 3종 세트 — 어느 하나라도 나빠지면 릴리스 보류
pytest -q                                          # 회귀 471개

GVSKB_MODE=offline PYTHONPATH=src python scripts/run_benchmark.py   # recall·FP·프로브

05버전·릴리스 정책 — 기관의 변경 통제

  • SemVer — 패치(버그·룰 정밀화) / 마이너(새 탐지·기능) / 메이저(호환성 변경). 모든 변경은 CHANGELOG에 한국어로 기록.
  • 태그 고정 설치 — 기관은 pip install git+https://…@v0.2.1처럼 태그를 고정해 설치하고, 업그레이드는 CHANGELOG 검토 후 반입 담당이 수행. main 추적 설치는 개발용입니다.
  • 데이터와 코드의 분리 배포 — 인텔 번들(intel-latest)은 매일 갱신돼도 도구 버전은 그대로입니다. 기관은 "데이터는 자주, 코드는 신중히"를 자연스럽게 실행하게 됩니다.
  • PyPI 미배포 유지 — 공급망 단순화를 위해 GitHub 소스 설치 단일 경로를 유지(변경 시 CHANGELOG 공지).

06위험 시나리오와 대응

시나리오영향대응
GitHub Actions 장기 중단번들·초안 룰 갱신 정지릴리스에 마지막 성공본 유지 — 반입은 계속 가능. 30일 넘으면 도구가 자동으로 보류 승격. 수동 대안: 아무 외부망 PC에서 update-intel --all + export.
피드 API 사양 변경(OSV·KEV 등)해당 소스 수집 실패워크플로는 continue-on-error — 다른 소스는 계속 갱신. 어댑터(intel/sources/*.py) 1파일 수정으로 복구. 실패는 Actions 로그로 즉시 확인.
출처 가이드 대개정(KISA 등)룰-조항 매핑 어긋남룰의 sources 필드로 영향 룰을 기계적으로 추출 → 대조표 만들어 반기 개정 작업. 개정 전까지 기존 룰은 기술적으로 계속 유효.
proposed PR 방치(검토 인력 부족)초안 룰 적체위험하지 않음 — proposed는 어차피 집행되지 않음. 적체 시 KEV는 데이터(캐시)로는 이미 반영되어 있으므로 판정 공백 없음.
유지관리자 교체운영 연속성이 문서 + CONTRIBUTING + 기술설명서로 인수인계. 모든 검증이 명령 1줄로 재현되므로 "현재 상태가 정상인지"를 신임자가 즉시 확인 가능.
