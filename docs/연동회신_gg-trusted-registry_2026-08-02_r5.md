## 1. ⚠ `source_scope` 에 `installed` 를 추가해 주십시오 — 가장 시급

`scan_installed_packages`(설치본 인벤토리) 경로도 플러그인을 탑니다. 그런데 합의
§5-C 의 `source_scope` 는 `single|manifest|lockfile` 3종이라 **이 경로에 해당하는
값이 없습니다.**

`installed` 를 추가하겠습니다. 성격은 락파일과 같으므로(버전 정확·전이 의존성 포함)
**심사 큐 정책도 `lockfile` 과 동일하게** 다뤄 주십시오.

### 이걸 먼저 말씀드리는 이유

귀측 서버가 enum 을 검증하면 모르는 값은 422 입니다. 그리고 **§1-1 에서 밝히신
대로 부분 실패가 아직 수정 전이라 200건 배치 전체가 유실**됩니다. 저희는
fail-open 이라 조용히 넘어갑니다.

이건 귀측이 R5 §4 에서 자진 보고하신 상황(verdict 2종이 enum 에 없어 422)과
**정확히 같은 실패를 반대 방향에서 반복**하는 것입니다. 한 번 겪은 실수라
미리 알립니다.

**enum 반영 완료를 알려 주시면 그때 보내겠습니다.** 그전까지는 `installed` 유래
결과를 제출하지 않겠습니다.

## 2. P1-4 락파일 파싱이 완료됐습니다 — 귀측 §3 전제가 바뀝니다

귀측 §3 은 "P1-4 가 완성될 때까지 `--include-installed` 가 유일한 경로"를 전제로
쓰셨습니다. **2026-08-01 자로 완료했습니다.**

지원 형식: `package-lock.json`(v1 중첩 트리·v2/v3 평면 경로) · `poetry.lock` ·
`uv.lock` · `pnpm-lock.yaml`(v6 슬래시·v9 @ 표기) · `yarn.lock`(클래식·berry YAML)

### 귀측 §3 질문에 대한 답

> "플러그인이 설치본 인벤토리를 쓰는가?"

**두 경로 모두 씁니다.**

| 경로 | 버전 | 전이 의존성 | 플러그인 |
|---|---|---|---|
| 매니페스트(`requirements.txt`·`package.json`) | 미확정 | ✗ | 탐(단 제출 필터에 걸림) |
| **락파일** | 확정 | ✓ | **탐** |
| **설치본**(`--include-installed`) | 확정 | ✓ | **탐** |

`scan_installed_packages` 는 내부적으로 `audit_manifest` 를 호출하므로 조회·제출
경로를 그대로 탑니다.

부수 사항 하나: 같은 디렉터리에 매니페스트와 락파일이 둘 다 있으면 **락파일만**
검사합니다(상위 집합이므로 중복 조회를 피합니다). 따라서 락파일이 있는 프로젝트의
제출 데이터는 `source_scope=lockfile` 로 옵니다.

## 3. 반입 번들 — 수용합니다

### 3-1. 판단

귀측 논리에 동의합니다. 리포트 전체를 올리면 `findings[].evidence`(코드 조각)와
`scanned_files`(파일 경로)가 레지스트리를 거치며, 이는 합의 §3 이 **절대 전송
금지**로 정한 것입니다. 서버가 파싱 범위를 좁혀도 업로드 시점에 이미 지나갑니다.

특히 이 문장이 결정적입니다.

> 무엇을 보내도 되는지 판단하는 주체가 **소비자**가 아니라 **생산자**여야 한다

브라우저 추출이 CLI·자동화 경로를 보호하지 못한다는 지적도 맞습니다.

### 3-2. 명세

```bash
gvskb scan <경로> --check-deps --include-installed --registry-bundle bundle.json
```

리포트 저장 시 `.check-reports/` 에 사이드카로도 자동 생성합니다(인텔 번들과 동일
방식으로 `.sha256` 동봉).

```json
{
  "schema": "gvskb-registry-bundle/1",
  "generated_at": "2026-08-02T05:00:00Z",
  "client": "gvskb/0.3.0",
  "engine_commit": null,
  "items": [
    {
      "result":       { "...PackageCheckResult 원본 그대로..." },
      "caller":       "cli:manual",
      "source_scope": "lockfile"
    }
  ]
}
```

**담기는 것**: 합의 §5-B 봉투 형식 그대로. 제출 필터(§5-D)를 통과한 항목만.
**담기지 않는 것**: 코드 조각 · 파일 경로 · 개인 식별자 · `findings` 일체 ·
`scanned_files` · `target`.

번들 자체도 정보라는 점을 문서에 명시하겠습니다 — 어떤 기관이 어떤 패키지를
쓰는지가 드러나므로 반출 심사 대상입니다. 무엇이 들어가는지 명시해야 심사가
가능합니다.

## 4. 귀측 §4 — 지적은 옳고, 코드는 이미 그렇습니다. **문서가 틀렸습니다**

> "5일 지난 데이터"와 "데이터가 아예 없음"은 다르다. 첫 배포일에는 캐시 0,
> 로컬 검증 0, 승인 건은 전부 통과 — 원칙 4가 무력화되는 구간이다.

**지적 자체는 정확합니다.** 그리고 확인해 보니 **구현은 이미 그렇게 돼 있습니다.**

캐시가 아예 없으면 경과일을 알 수 없고, 그 경우 `requires_review=True` 로 올립니다.
회귀 테스트 `test_approved_with_no_cache_at_all_requires_review` 가 이를 고정하고
있습니다.

```
캐시 낡음(있으나 오래됨)  → requires_review=False + 배너 (30일 초과 시 True)
캐시 없음(한 번도 없음)   → requires_review=True
```

**틀린 것은 합의서 §4-2 표입니다.** 세 번째 분기를 "낡음·없음"으로 묶어 적어
그 구분이 문서에서 사라졌습니다. 귀측은 코드보다 덜 정확한 문서를 읽고 지적하신
것이고, 문서를 고치겠습니다.

지적해 주시지 않았으면 문서와 코드가 어긋난 채로 남았을 것입니다.

## 5. 귀측 §5 하네스 공백 — 별도 문서로 답합니다

제기가 정확합니다. 두 시스템이 계약을 다듬었지만 **집행 지점이 비어 있었습니다.**
`하네스_집행계약.md` 를 작성했으며 합의서 §10 으로 편입합니다.

### 귀측이 물으신 세 가지에 대한 답

**(a) `REJECTED` 강등을 하네스가 차단으로 다루는가** → **차단입니다.**

근거 셋을 명시했습니다. ① 차단은 패키지에 대한 진술이지 네트워크에 대한 진술이
아니다 — 레지스트리에 닿지 못한다고 패키지가 안전해진 것이 아니다. ② 차단이
풀리는 일은 드물고 잘못 통과시킨 비용은 크다. ③ 경고로 떨어뜨리면 §4-5 가
무의미해진다 — 지적하신 대로 7일 뒤 우회가 그대로 성립합니다.

**(b) `UNKNOWN` 처리** → 단계적 진입(MONITOR → WARN → ENFORCE) 제안을 채택했습니다.
다만 **전환 기준을 숫자로 정할 것**을 덧붙였습니다. MONITOR 구간에서 `unknown`
비율을 실측하고 그것이 충분히 떨어졌을 때 올립니다. 숫자 없이 ENFORCE 를 켜면
우회 문화가 먼저 생기고, 우회가 습관이 되면 하네스 전체가 무력해집니다.

이 항목은 **보안 정책이지 기술 설계가 아니므로** 최종 결정은 기관 몫입니다.
저희 문서는 선택지와 근거만 제시합니다.

**한 가지는 다르게 판단했습니다** — 타이포스쿼팅 의심을 전 모드 차단으로
제안하셨는데 동의하지 않습니다. `not_found`(실재하지 않음)는 조회로 확정되는
**사실**이라 절대 규칙에 넣었지만, 타이포스쿼팅은 편집거리 **휴리스틱**이고
오탐이 실재합니다. 특히 기준 코퍼스를 키우면 오탐도 함께 커집니다(정상 패키지끼리
이웃이 됨). MONITOR 구간에서 휴리스틱으로 차단하면 "하네스는 멀쩡한 걸 막는다"는
인상이 먼저 생기고, 그 뒤로는 진짜 차단도 우회 대상이 됩니다.

다만 **둘이 겹치면 확정**입니다 — 실재하지 않으면서 유명 패키지와 이름이
비슷하면 이미 `not_found` 절대 규칙에 걸립니다.

**(c) 기존 카탈로그와의 우선순위** → 아래 §6.

## 6. 귀측에게 필요한 보장 하나 — 카탈로그가 `REJECTED` 를 덮지 않습니다

귀측 §5-2(c) 가 물으신 것에 대한 계약 수준의 답입니다.

> **로컬 카탈로그는 레지스트리의 `REJECTED` 를 덮을 수 없습니다.**
> 카탈로그가 허용목록이든 차단목록이든, 어떤 항목에 무엇이 적혀 있든 예외 없습니다.

근거: 카탈로그는 파일이고 레지스트리는 사람이 관리하는 최신 판정입니다. 카탈로그
항목은 한 번 적히면 아무도 지우지 않는 경향이 있어, 이 불변식이 없으면 **과거에
허용했던 파일 한 줄이 현재의 기관 차단을 무력화**합니다.

허용 방향은 형식에 따라 갈리며 하네스 집행계약 §6-1(차단목록)·§6-2(허용목록)·
§6-3(혼재)에 세 경우를 모두 명세했습니다. 요점만 옮기면, 허용목록인 경우
**레지스트리를 카탈로그의 대체가 아니라 확장으로** 다룹니다 — "카탈로그에 없음"을
곧바로 차단으로 보면 도입 즉시 ENFORCE 가 되어 개발이 멈추기 때문입니다.

### 귀측 §1 자진 보고에 대하여

**§1-2(`caller` 검증)는 저희에게도 해당했습니다.** 규칙을 제안한 것은 저희인데
**저희 쪽에도 검증이 없었습니다.** `caller` 는 저희 감사로그에도 그대로 들어가므로
개인 식별자가 섞이면 저희 감사 기록도 오염됩니다. 클라이언트 검증을 추가합니다.

"규칙을 지킬 주체와 강제하는 주체가 같으면 안 된다"는 문장은 저희에게도 그대로
적용되는 말이었습니다.

**§1-1(부분 실패)** 은 저희 쪽에도 침묵이 있었습니다. `lookup_batch` 가 모든
실패를 `except Exception` 으로 뭉개어, 422(스키마 거부 — 재시도 무의미)와 연결
실패(재시도 유효)를 구분하지 못했습니다. 조치가 다른 두 상황이므로 나눕니다.
