# A. 귀측이 알아야 할 것

## A-1. ⚠ `in_kev` 판단 규칙이 그 경우를 놓칩니다 — 가장 중요

귀측 §4 와 집행계약 §2-1 의 규칙입니다.

> `cache_sources_used` 가 **비어 있으면** `in_kev=false` 는 '대조 못 함'

**규칙의 의도는 옳지만 술어가 틀렸습니다.** 저희 오프라인 경로는 소스마다 따로
붙입니다.

```python
if osv_entry is not None:  cache_sources_used.append("osv-malicious")
if kev_entry is not None:  cache_sources_used.append("cisa-kev")
```

즉 **`["osv-malicious"]` — 비어 있지 않은데 KEV 대조는 되지 않은 상태**가 있습니다.
악성 피드는 반입했고 KEV 캐시는 아직 없는 경우이고, 망분리에서 인텔 번들을 부분
반입하면 드물지 않습니다. 이때 귀측 규칙은 `in_kev=false` 를 **사실로 저장**합니다.

정확한 술어는 `"cisa-kev" in cache_sources_used` 입니다. 추론을 안 하셔도 되도록
`kev_checked` 를 실었습니다(B-3).

## A-2. ⚠ 항목 단위 실패 — 귀측 §2 수정이 새 침묵을 만들었습니다

배치 부분 실패를 허용하신 것은 옳은 방향입니다. 그런데 그 결과 **실패가 HTTP
상태가 아니라 항목 단위로** 옵니다.

저희 `lookup_batch` 는 HTTP 상태만 봤습니다. 그래서 답을 받지 못한 항목이
`registry_status="ok"` 로 표시됐습니다 — **"조회했고 이상 없음"과 "판정을 못 받음"이
화면에서 같아졌습니다.** 저희가 배치 전체 실패를 고치면서 항목 단위를 남겨 뒀고,
귀측 수정이 그 구멍을 실제 경로로 만들었습니다. 고쳤습니다(B-4).

**서로의 수정이 맞물려 새 결함을 만든 사례라 기록해 둡니다.** 한쪽만 보면 둘 다
개선인데 합치면 후퇴였습니다.

## A-3. `installed` 유래가 이번 번들부터 나갑니다

r5 §1 에서 "enum 반영 확인 전까지 보내지 않겠다"고 약속했고 이제 풉니다.
전이 의존성까지 포함되므로 **건수가 이전 예상보다 큽니다**(락파일 규모).
심사 큐에는 올리지 않는 값이지만 저장량은 늘어납니다.

보류 장치 자체는 코드에 남겨 뒀습니다 — 같은 상황(저희가 값을 늘렸는데 그쪽이
아직 모름)이 다시 생길 때 쓸 자리입니다.

## A-4. 저희가 보내는 건수가 **줄어드는** 변경도 있습니다

경계값 버전(`requests>=2.28` 의 2.28)을 더 이상 제출하지 않습니다(B-1). 지금까지
받으신 데이터 중 **매니페스트 유래로 `>=`·`~=`·`^` 였던 것은 실제로 쓰이는 버전이
아닐 수 있습니다.** 귀측 DB 가 0건이라 정정할 과거 데이터는 없다고 이해하지만,
혹시 시험 데이터를 쌓으셨다면 이 점을 감안해 주십시오.

# B. 저희가 고친 것

## B-1. 매니페스트 제약 연산자를 버리고 있었습니다 (귀측 §3 확인 중 발견)

귀측 §3-1 표는 이렇게 적혀 있습니다.

> 매니페스트 항목 `requests>=2.28` → 버전 미확정 → 합의 §5-D 로 제출 자체가 절단

**저희 구현에서는 그렇지 않았습니다.** 실측입니다.

```
requests>=2.28    -> version='2.28'     제출대상=True
requests==2.31.0  -> version='2.31.0'   제출대상=True
requests          -> version=None       제출대상=False   ← 이것만 걸립니다
```

버전 표기가 **아예 없는 것**만 걸렸습니다. 따라서 "양쪽 다 도달하지 못한다"는
진단은 정확하지 않고, 심사 대기열이 구조적으로 비어 있던 것도 아닙니다.

**대신 더 나쁜 것이 있었습니다.** 파서 정규식이 연산자를 버렸습니다.

```python
m = re.match(r"([A-Za-z0-9_.-]+)\s*(==|>=|<=|~=|>|<)?\s*([A-Za-z0-9_.!*+-]+)?", line)
packages.append({"name": m.group(1), "version": m.group(3)})   # group(2)=연산자, 버려짐
```

`requests>=2.28` 인 프로젝트에 실제로는 2.31.0 이 깔려 있어도 **2.28 기준으로
판정**했습니다. 2.28 의 취약점이 2.30 에서 고쳐졌다면 그대로 오탐이고, 더 나쁜 것은
**그 오탐이 귀측 DB 에 "2.28 에 대한 관측 사실"로 저장**된다는 점입니다.
npm `^4.17.0` 도 `lstrip("^~")` 로 같은 처리를 받았습니다.

즉 저희는 큐가 빈 것이 아니라 **틀린 것을 채우고 있었습니다.** 귀측이 든 근거보다
이쪽이 더 강합니다.

**조치**: `version_exact` 를 판정에 실었고 제출 필터(§5-D)가 이를 봅니다. 경계값
판정은 화면에는 남되(그 제약이 취약한 버전을 허용한다는 것도 실제 신호입니다)
귀측으로는 가지 않습니다.

## B-2. 귀측 §3 요청 — 이름과 버전을 합쳤습니다

```
설치 흔적 중 매니페스트에 이름이 있는 것 → source_scope = manifest   (심사 큐)
그 밖의 전이 의존성                      → source_scope = installed  (관측만)
```

`source_scope` 판정을 **감사 단위에서 항목 단위로** 바꿨습니다. 설치본 인벤토리
안에 직접·전이가 섞여 있어 감사 단위로는 나눌 수 없습니다.

실측입니다 — `requirements.txt` 에 `requests>=2.28` 만 있고 `.venv` 에
requests 2.31.0 · urllib3 2.2.1 이 설치된 프로젝트:

```
requests   2.31.0   scope=manifest    ← 이름은 매니페스트, 버전은 설치본
urllib3    2.2.1    scope=installed   ← 끌려온 전이 의존성
```

번들 어디에도 `2.28` 은 없습니다. 귀측 §3-2 의 "직접 의존성 + 정확한 버전"이
그대로 나갑니다.

부수 조치 둘:

- **중복 제거** — 같은 패키지가 매니페스트와 설치본 양쪽에서 잡히면 한 번만
  보냅니다. 남기는 쪽은 `manifest` 입니다(강등되면 심사 큐에서 사라지므로).
- **락파일에 가려 검사에서 건너뛴 매니페스트도 이름 목록으로는 읽습니다** —
  락파일은 직접·전이를 구분하지 않고 평면으로 담기 때문입니다.

## B-3. 귀측 §4 요청 — 이미 보내고 있었고, 추론이 필요 없게 만들었습니다

`cache_sources_used` 는 저희 봉투의 `result` 에 이미 들어 있습니다. 저희는
`PackageCheckResult` 스키마 필드를 **허용목록**으로 담는데 이 필드가 거기 있습니다.

```json
"cache_sources_used": ["osv-malicious", "cisa-kev"],
"cache_freshness":    {"osv-malicious": "2026-07-30T...", "cisa-kev": "2026-07-30T..."}
```

못 받으신 것은 저희가 안 보내서가 아니라 **`CheckerResultPayload` 가 버리기**
때문입니다.

여기에 더해 귀측 (b) 안을 넣었습니다.

```json
"in_kev": false,
"kev_checked": false     // ← false 면 '악용 없음'이 아니라 '대조 못 함'
```

| 상황 | `kev_checked` |
|---|---|
| KEV 캐시를 실제로 읽음(신선·낡음 무관) | `true` |
| KEV 캐시 없음 | **`false`** |
| 취약점 0건이라 대조할 대상이 없었음 | `true` — KEV 는 CVE 기반이라 `in_kev=false` 가 사실로 성립합니다 |

낡음 여부는 `cache_stale_sources` 에 따로 있습니다. **판단은 `kev_checked` 로**
하십시오.

## B-4. 항목 단위 실패를 통과로 읽지 않습니다 (A-2 조치)

아는 판정(`APPROVED`·`REJECTED`·`UNDER_REVIEW`·`UNKNOWN`)이 아니면
`registry_status="item_failed"` 로 두고 보고서 배너로 알립니다.

모르는 값을 통과로 읽으면 **귀측이 상태를 하나 늘릴 때마다 저희 쪽에 조용한
초록불이 하나씩 생깁니다.** 귀측이 §2 에서 "모르는 `source_scope` 를 거부하지 않고
가장 보수적인 쪽으로 떨어뜨린다"고 하신 것과 같은 처리입니다.

## B-5. `--include-installed` 의 npm 경로가 통째로 깨져 있었습니다

귀측 §3 을 확인하다 찾았습니다. 설치 목록을 `express==4.17.0`(requirements 형식)으로
만들어 놓고 npm(JSON)으로 파싱하려다 실패해 `verdict="unparsed"`, `parsed_count=0`
을 냈습니다.

**즉 node_modules 에서 수집한 전이 의존성이 한 건도 검사되지 않았습니다.**
`--include-installed` 의 존재 이유가 전이 의존성인데 npm 쪽은 비어 있었습니다.

`unparsed` 로 검토 대상에는 올라갔으니 완전한 침묵은 아니었지만, 화면에는
"형식·ecosystem을 확인하세요"라고만 나와 **저희 결함이 사용자 입력 문제처럼**
보였습니다.

**귀측에 대한 함의**: 지금까지 저희가 보낸(또는 보낼 예정이던) npm 데이터에는
전이 의존성이 없었습니다. 앞으로 npm 프로젝트의 제출 건수가 늘어납니다.

## B-6. 귀측 §5 — 동의합니다. 그리고 저희 문서가 틀렸습니다

> 느슨해지는 방향에는 신선도를 요구하고, 엄격해지는 방향에는 요구하지 않는다

이 문장에 그대로 동의합니다. 그리고 **저희 코드는 처음부터 그랬습니다** —
`_TTL_SECONDS` 가 `APPROVED` 1시간(만료 시 삭제) · `REJECTED` 7일(만료돼도
삭제하지 않고 `stale` 로 강등)입니다. 2026-08-02 자로 `stale` 차단의 안내 문구도
분리해, 판정은 그대로 차단이되 "최근 재확인하지 못했다"가 화면에 남게 했습니다.

**틀린 것은 `3자구조_체커-레지스트리-하네스.md` §8-1** 입니다. 통과·차단을 구분하지
않고 "1시간 이내의 것만 쓴다"고만 적어 충돌로 읽히게 했습니다. 비대칭 표로
고쳤습니다. **집행계약 §3-2 가 우선합니다.**

r5 §4 와 같은 패턴입니다 — 코드는 맞고 문서가 덜 정확했고, 귀측이 문서를 읽고
지적해 주셔서 드러났습니다.

## B-7. 반입 번들 — 생성됩니다 (귀측 §9-1)

```bash
gvskb scan <경로> --check-deps --include-installed --registry-bundle bundle.json
```

리포트를 파일로 저장하면 `<리포트명>.registry-bundle.json` 사이드카로도 생깁니다.
둘 다 `.sha256` 이 동봉됩니다. 화면 출력만 한 실행은 파일을 남기지 않습니다 —
반출 심사 대상이 담당자 모르게 디스크에 생기면 안 되기 때문입니다.

**sha256 형식**은 `<64자 hex><공백 2개><파일명>` + **LF** 입니다. 처음에 Windows
기본값으로 써서 CRLF 가 되었고, 파일명 끝에 CR 이 붙어 `sha256sum -c` 가 "그런
파일 없음"으로 실패했습니다 — 검증하라고 동봉한 파일이 검증을 막고 있었습니다.

**담기지 않는 것**: 코드 조각 · 파일 경로 · `findings` 일체 · `scanned_files` ·
`target` · 매니페스트 파일명 · 개인 식별자. `result` 는 스키마 필드만 **허용목록**
으로 담습니다 — 제외 목록은 새 필드가 생길 때마다 뒤처지지만 허용목록은 자동으로
막습니다.

## B-8. 귀측 §7 `override` — 형식 그대로 받겠습니다

```jsonc
"override": {
  "reason_code": "EMERGENCY_PATCH",
  "approval_ref": "보안-2026-0173",
  "mode": "ENFORCE"
}
```

`caller` 와 같은 문제라는 진단에 동의합니다. 자유 문자열이면 "보안팀 ◯◯◯ 과장
승인"이 들어오고, 받은 뒤 개인정보만 골라내려 하면 탐지 규칙과의 술래잡기가 됩니다.
**문법으로 막는 편이 확실합니다.**

저희도 `caller` 를 같은 방식으로 처리했습니다 — `<출처>:<모드>[:부서코드]` 에 맞지
않으면 `unknown:invalid` 로 대체하고, 부서코드만 어긋나면 그 자리만 버립니다.
**거부한 값은 경고에도 싣지 않습니다**(검증이 유출 경로가 되면 안 되므로).

`reason_code` 목록을 주시면 같은 허용목록 검증을 넣겠습니다. 다만 `override` 를
채우는 주체는 하네스이므로 **3자 확정이 먼저**입니다.

## B-9. 귀측 §8 — 구분 유지해 주십시오

> 락파일은 *선언된* 사실, 설치 흔적은 *관측된* 사실이라 서로 어긋날 수 있다

정확히 그 의도입니다. **둘이 어긋나는 것 자체가 신호입니다** — 락파일에 없는 것이
설치돼 있으면 수동 설치나 공급망 개입을 의심할 근거가 되고, 그 판단은 두 값이
따로 남아 있어야 가능합니다. 심사 큐 정책이 같다고 합치면 그 질문을 못 하게 됩니다.

## B-10. 귀측 §1 문서 대조에 대하여

서로의 문서를 보지 않은 상태에서 핵심 3건이 일치했다는 점에 저희도 같은 무게를
둡니다. 그리고 이 지적을 받아들입니다.

> "하네스가 레지스트리를 직접 조회하지 않는 이유"로 gvskb 는 토큰 유출면·중복
> 로직만 적었는데, 귀측은 **"레지스트리 승인만 보고 설치하면 로컬 악성·KEV 대조가
> 생략된다"** 를 첫 번째로 들었다

맞습니다. 저희가 든 것은 부수 효과이고 **원칙 4(로컬 탐지가 최종 안전망)를 우회
불가능하게 만드는 것**이 이 구조의 목적입니다. 저희 문서를 그렇게 고치겠습니다.

# C. 귀측이 고쳐야 할 것

## C-1. ★ 집행계약 §2-1 의 `in_kev` 판단 규칙 (A-1)

```diff
- in_kev | bool | 단 `cache_sources_used` 가 비어 있으면 `false` 는 '대조 못 함'
+ in_kev | bool | 단 `kev_checked=false` 면 `false` 는 '악용 없음'이 아니라 '대조 못 함'
```

**필드만 받으시고 이 규칙을 안 고치시면, 값은 있는데 판단은 여전히 틀립니다.**
1번보다 2번이 중요합니다.

## C-2. `CheckerResultPayload` 에 필드 추가

| 필드 | 타입 | 용도 |
|---|---|---|
| `cache_sources_used` | `list[str]` | 어떤 인텔 캐시를 실제로 대조했는가 |
| `kev_checked` | `bool` | `in_kev=false` 를 사실로 읽어도 되는가 |
| `version_exact` | `bool` | 이 버전이 관측인가 매니페스트 경계값인가 |

`version_exact` 는 저희가 걸러서 보내므로 받는 것은 항상 `true` 입니다. 그래도
받아 두시면 나중에 정책이 바뀌어도 구분이 남습니다.

## C-3. 번들 최상위 `excluded` 수용 여부

회신 §3-2 명세에 없던 필드입니다.

```jsonc
{
  "schema": "gvskb-registry-bundle/1",
  "items": [ ... ],
  "excluded": {                        // ← 규격 외. 거부하시면 빼겠습니다
    "installed_pending_enum": 0,       // 보류 건수(지금은 0 — §2 로 해제)
    "submit_filtered": 2,              // §5-D 로 걸린 건수(경계값 포함)
    "duplicates": 0                    // 두 경로로 잡혀 합친 건수
  }
}
```

번들이 **'전부'가 아니라는 것**을 받는 쪽이 알아야 한다고 판단했습니다. 조용히
빠지면 그 패키지를 저희가 쓰지 않는 것으로 읽히는데, **'없음'과 '안 보냄'은
다릅니다.** 반출 심사자에게도 필요한 값입니다.

파서가 미지의 최상위 키를 거부하면 알려 주십시오. 다만 §2 에서 "모르는 값은
거부하지 않는다"로 가셨으니 통과할 것으로 봅니다.

## C-4. 질의 — 항목 실패를 응답에서 어떻게 표기하십니까

B-4 는 방어적 처리입니다. 정확히 읽으려면 형식을 알아야 합니다.

1. `check-bulk` 응답에서 판정 못 한 항목은 **`results` 에서 빠집니까**, 아니면
   상태 표식과 함께 **포함**됩니까?
2. 포함된다면 필드 이름과 값은 무엇입니까(`status: "FAILED"`? `error`?)
3. `submit-batch` 의 항목별 `FAILED` 는 응답 어디에 실립니까? 그것을 보고 재제출
   대상을 고를 수 있으면 좋겠습니다.
