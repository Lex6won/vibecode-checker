vibecode-checker 운영 구조 통합 안내

AI로 만든 공공업무 코드를 배포 전에 점검하는 한국형 보안 게이트 — 무엇이 어떻게 돌아가고, 누가 무엇을 하는지 한 곳에 정리했습니다.

문서 버전 1.0 기준일 2026-07-31 엔진 v0.3.0 테스트 544건 통과 이슈 정리될 때마다 갱신

이 도구는 무엇인가

vibecode-checker(내부 이름 gvskb)는 공무원이 AI 코딩 도구로 만든 코드에 숨은 개인정보 노출·API 키·SQL 삽입·위험한 명령 실행·취약 패키지·AI 프롬프트 위험을 찾아 한국어 보고서로 알려주는 도구입니다. 코드를 외부로 보내지 않고 내 PC에서 검사합니다.

핵심 원칙 세 가지 ① 코드는 PC를 떠나지 않는다  ·  ② 판정 불가는 '안전'이 아니다  ·  ③ 공식 보안적합성 검토를 대체하지 않는다

공무원용 — 이것만 알면 됩니다

결론부터 설치는 AI 에이전트에게 시키면 되고, 최신 위협 정보 갱신은 이제 자동입니다. 평소엔 "이 폴더 보안 검사 해줘"라고 말만 하면 됩니다.

1. 설치 — AI에게 시키기

Claude Code·Cursor·Codex 같은 코딩 에이전트를 쓰고 있다면, 채팅창에 이렇게 말하세요:

https://github.com/Lex6won/vibecode-checker 를 설치하고 내 MCP 설정에 등록해줘

에이전트가 설치 → 설정 파일 수정 → 확인까지 대신 해줍니다. 설정 파일을 고칠 때 변경 내용 승인을 물어보면 확인 후 승인하시면 됩니다.

주의 — 채팅 전용 앱은 설치를 못 합니다 Claude Desktop·ChatGPT 데스크톱은 보안상 내 PC에서 명령을 실행할 권한이 없습니다. 설치를 대신해 줄 수 있는 것은 코딩 에이전트뿐입니다.

2. 사용 — 그냥 말하면 됩니다

이렇게 말하면이런 일이 일어납니다
"이 폴더 보안 점검해줘"폴더 전체를 검사하고 한국어 보고서 생성
"이 코드 안전한지 확인해줘"붙여넣은 코드 조각 검사
"이 패키지 설치해도 돼?"실재 여부·취약점·발행 경과일 확인
"보안 점검 보고서 만들어줘"인쇄해서 결재에 쓸 수 있는 HTML 보고서

터미널이 익숙하면 명령 한 줄도 됩니다: gvskb scan ./내프로젝트 --check-deps

3. 결과를 읽는 법 — 이것만 기억하세요

표시뜻무엇을 해야 하나
저장소에 없음AI가 지어낸 가짜 패키지일 가능성이 높음설치하지 마세요. 공식 문서에서 정확한 이름 확인
악성 의심알려진 악성 패키지절대 설치 금지, 보안담당자 보고
취약점 N건알려진 보안 결함 존재조치된 최신 버전으로 올리기
발행 직후 — 대기 권고너무 최근에 나온 버전며칠 기다렸다 설치 (아래 설명)
판정 불가검사를 못 했음'안전'이 아닙니다. 인터넷 연결 확인 후 재검사
이상 없음검사 시점 기준 문제 없음사용 가능 (단, 공식 검토를 대체하진 않음)
왜 "발행 직후"는 기다려야 하나요? 해커가 유명 패키지 계정을 탈취해 악성 버전을 올리는 사고가 최근 크게 늘었습니다. 이런 오염 버전은 대부분 몇 시간~며칠 안에 발각·삭제됩니다. 즉 며칠만 기다렸다 설치하면 통째로 피할 수 있습니다. 이것이 가장 효과 좋은 예방책입니다.

기본 대기 기준: 개인PC 일회성 3일 · 개인PC 반복 사용 7일 · 내부서버 공용 14일

4. 보고서는 어디에 저장되나요

검사한 프로젝트 폴더 안에 자동 저장됩니다 내프로젝트\.check-reports\2026-07-31_1530_보안점검.html

검사할 때마다 날짜·시각 이름으로 쌓이므로 조치 전후를 비교할 수 있고, HTML 파일을 열어 인쇄하면 그대로 PDF 결재 문서가 됩니다. 같은 이름의 .md(텍스트)와 .json(원본 데이터)도 함께 만들어집니다.
  • AI 에이전트에게 시킬 때는 "보고서 저장해줘"라고 하면 이 위치에 저장하고 경로를 알려줍니다.
  • 터미널에서는 gvskb scan ./내프로젝트 만 실행하면 자동 저장됩니다(경로 지정 불필요).
  • 깃 저장소를 쓴다면 .gitignore 에 .check-reports/ 한 줄을 추가하세요.

5. 최신 정보 갱신 — 신경 쓰지 않아도 됩니다

악성 패키지 목록은 매일 갱신되는데, 이제 gvskb가 알아서 받아옵니다(하루 1회 자동 확인). 뭔가 이상하면 아래 명령으로 상태를 볼 수 있습니다:

gvskb intel-sync --status     # 최신인지 확인
gvskb intel-sync              # 지금 바로 갱신
gvskb doctor                  # 전체 환경 진단
이 도구가 하지 않는 것 이 점검은 공식 보안적합성 검토를 대체하지 않습니다. 특히 대민 서비스·개인정보 처리 시스템은 바이브 코딩 결과물을 그대로 올리면 안 되고, 정식 정보화사업 절차로 이관해야 합니다.

3. 망분리 환경 운영 절차

초기 구축 (1회)

  1. 인터넷망 PC에서 번들 다운로드: github.com/Lex6won/vibecode-checker/releases/tag/intel-latest
  2. 게시된 sha256 값과 파일 해시 대조
  3. 승인된 반입 절차로 내부망 공유폴더에 배치 (예: \\파일서버\gvskb\)
  4. 각 PC 환경변수 설정 (아래 표) — 배포 스크립트나 그룹정책으로 일괄 적용 권장

정기 운영 (주 1회 권장)

  1. 인터넷망에서 새 번들 다운로드 + 해시 확인
  2. 공유폴더의 기존 파일 교체
  3. 끝. 각 PC는 다음 검사 때 자동 반영합니다 (사용자 조작 0회)

5. 기관 정책팩 — 쿨다운·라이선스 기준 조정

기관이 자체 기준을 쓰려면 아래 형식의 YAML을 만들어 GVSKB_VCPS_RULES로 지정합니다. 기본값은 config/vcps-rules.yaml에 있습니다.

environments:
  E0: { label: "개인PC 일회성",   cooldown_days: 3 }
  E1: { label: "개인PC 반복도구", cooldown_days: 7 }
  E2: { label: "내부서버 공용",   cooldown_days: 14 }
default_env: E1
license_allowlist: [MIT, Apache-2.0, BSD-3-Clause, ISC, MPL-2.0]
license_review_required: [GPL-3.0, AGPL-3.0, SSPL-1.0]
E3(대민·개인정보)가 없는 이유 의도적으로 없습니다. 대민 서비스·개인정보 처리는 바이브 코딩 대상이 아니며, 정식 정보화사업 절차로 이관해야 한다는 정책을 코드로 표현한 것입니다.

6. 승인 예외(bypass) 관리 규율

위험을 수용하고 게이트를 통과시키려면 .gvskb-exceptions.yaml을 씁니다.

exceptions:
  - rule_id: GOV-FLASK-DEBUG-001
    file: app.py
    reason: 내부 개발서버 전용 스크립트 — 외부 노출 없음
    approved_by: 김보안(정보보안담당관)
    expires: 2026-12-31
  • 사유·승인자·만료일이 전부 없으면 무효 (방치 방지)
  • 예외 적용된 발견도 보고서에서 사라지지 않음 — "무엇이 왜 면제됐나"가 항상 보임
  • 만료되면 자동 무효화되어 다시 게이트를 막음
  • 중앙 배포 시 GVSKB_EXCEPTIONS_DIR에 두면 전체 PC 일괄 적용 (출처가 보고서에 표시됨)
중앙 배포 시 필수 보안 요건 예외 파일은 사실상 게이트 통과권입니다. 다운로드 방식으로 운영하는 순간 sha256·서명 검증이 반드시 필요합니다. (레지스트리 배포 설계 시 확정 예정 — ⑤번 탭 참조)

3. 주요 개념의 구현 위치

패키지 판정 사다리 (우선순위 순)

판정뜻심각도
malicious악성 advisory 존재high (차단)
not_found공식 저장소에 없음 — 슬롭스쿼팅 의심high (차단)
vulnerable알려진 취약점. KEV 일치 또는 High/Critical이면 차단급high/medium
cooldown_hold발행 직후 — 위험 확정이 아닌 대기 권고medium
checked_stale낡은 캐시 기준의 '이상 없음'검토 필요
checked_clean검사 시점 기준 이상 없음info
unknown / error판정 불가 — '안전'이 아님검토 필요

인텔 소스 우선순위 (autopull.py)

  1. GVSKB_INTEL_DIR 폴더의 최신 zip — 망분리 1순위
  2. GVSKB_INTEL_URL — 기관 레지스트리 엔드포인트
  3. DEFAULT_BUNDLE_URL — 공개 GitHub 릴리스

오프라인 모드에서는 1번만 시도합니다(외부 통신 금지 원칙). 어느 경로든 번들 manifest sha256 전수 검증 + 로드 시 envelope 재검증을 통과해야만 반영됩니다.

4. 작업 절차

# 1) 수정 후 반드시 전체 테스트
PYTHONPATH=src ~/miniconda3/python.exe -m pytest -q

# 2) 린트
~/miniconda3/python.exe -m ruff check src/gvskb/ tests/

# 3) 실동작 확인 (예: 가짜 패키지가 차단되는지)
PYTHONPATH=src python -m gvskb.cli check-package 가짜패키지명 --ecosystem pypi

# 4) 커밋 (푸시는 명시적 요청 시에만)
git add -A && git commit -m "..."
테스트 작성 원칙 네트워크에 의존하지 않게 monkeypatch로 고정합니다. 특히 온라인 폴백이 실제 GitHub을 호출하므로, 폴더 소스 테스트는 GVSKB_MODE=offline을 설정하거나 _pull_from_url을 모의해야 합니다.

5. 자동화 파이프라인 (GitHub Actions)

워크플로주기하는 일
.github/workflows/update-intel.yml매일 03:00 KST OSV·KEV·NVD·EPSS 수집 → 번들 게시(intel-latest) + KEV→proposed 룰 PR 자동 병합
.github/workflows/test.ymlPR·푸시pytest 전체 실행
.github/workflows/intel-digest.yml매월 1일검토 후보 다이제스트 이슈 생성
중요 이 파이프라인은 GitHub 클라우드에서만 돌고 로컬을 갱신하지 않습니다. 로컬 룰 갱신은 git pull, 로컬 인텔 갱신은 자동 당김(또는 gvskb intel-sync)입니다.

남은 과제와 담당

1. gvskb MCP (이 프로젝트)

과제상태내용
번들 규격 확정다음 레지스트리 팀에 줄 "배포 계약서". 인텔 + 예외 + 차단목록 슬롯 정의. 레지스트리 완성 전에 확정 가능
기관 차단 목록 반입미설계 인텔 캐시 신규 소스(org-blocklist)로 추가 — 기존 캐시 인프라 재사용
번들 서명 검증미설계 다기관 배포 시 필수. 특히 예외 파일(게이트 통과권)에 필수
설치 마법사(gvskb setup)설계완료 읽기 전용(스니펫 출력만) + llms-install.md — 파일 쓰기는 에이전트 승인 게이트에 위임
탐지력 프로파일 표시제안 보고서 첫머리에 집행 룰 수·semgrep 가동·인텔 기준일 박제 (기관 간 결과 비교 전제)
비동기 job 패턴후순위벌크·전체 감사용. 단건은 동기 유지
행동 기반 탐지장기Socket.dev 방법론 참고 — 라이선스 조사 선행 필요

2. 신뢰 레지스트리 (별도 프로젝트)

과제내용
파일 배포 기능API와 별개로 번들 export 필수 — 망 경계를 넘는 유일한 방법
판정 어휘 매핑ALLOW/CONDITIONAL/HOLD/BLOCK ↔ gvskb 판정 사다리 대응표 확정
스캔 결과 저장엔진 버전·인텔 스냅샷 필드 포함 (재현성 확보)
request_type 기록gvskb의 caller 값을 AUTO/MANUAL로 매핑

3. 하네스 (vibe_harness)

  • 조회 우선(registry-mcp) → 없으면 검사(gvskb) 순서 구현
  • 최종 설치 허용/차단 집행 — gvskb·레지스트리는 "의견"만 제공
  • 호출 시 caller 파라미터로 자기 신원 신고
  • 도구 설명 무결성 확인 (Tool Poisoning 방어 — 클라이언트 책임)

4. 망 구성별 사용 가능 범위

사용자위협 인텔기관 확정 판정결론
경기도 내부망공유폴더 자동 반입내부 레지스트리 직접완전 사용
경기도 인터넷망GitHub 자동반입 절차로 파일 배포 필요조건부
타 기관·오픈소스 사용자GitHub 자동대상 아님(내부 정책이므로)정상 사용
설계 원칙 — 이 한 줄만 지키면 됩니다 "레지스트리는 API가 아니라 파일을 배포한다." 파일은 승인 절차로 망을 건널 수 있지만 API는 건널 수 없습니다. 이 원칙을 지키면 외부 오픈소스 사용자는 기관 파일이 없어도 정상 동작하고, 망이 몇 개로 갈려도 동일한 메커니즘으로 연결됩니다.
