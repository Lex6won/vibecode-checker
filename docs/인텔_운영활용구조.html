01전체 구조 한눈에

핵심 원칙 두 가지입니다. ① 데이터와 지식을 분리해 배포 — 판정에 쓰는 데이터(캐시)는 매일 자동 배포되지만, 검사 룰(지식)은 사람이 검토·승인해야 집행됩니다. ② 자동 소싱은 하되 자동 집행은 하지 않음 — 자동화는 신선도를, 사람 게이트는 오탐·오차단 방지를 책임집니다.

02무엇을 수집하나 — 피드 4종

피드내용검사에서의 용도
OSV.dev 악성 피드오픈소스 생태계의 악성 패키지(MAL-) 권고. 기본 PyPI, 옵션으로 npm(GVSKB_OSV_INCLUDE_NPM=1)패키지 악성 여부 판정의 1차 근거
CISA KEV미국 CISA가 실제 악용을 확인한 취약점 카탈로그패키지명이 벤더·제품과 일치할 때 보조 경고 신호 + 초안 룰 자동 생성
NVD최근 CVE의 상세·CVSS 3.1 점수KEV 신호에 심각도 점수 병기
FIRST EPSSCVE별 악용 관측 확률(0~1)·백분위KEV 신호에 악용 가능성 병기 — 패치 우선순위 근거

외부로 나가는 데이터

수집은 전부 공개 데이터 수신이며, 온라인 검사 시 외부로 전송되는 것은 패키지명·버전·생태계(OSV 조회)뿐입니다. 소스코드는 어떤 경우에도 전송되지 않습니다. 오프라인 모드에서는 외부 통신 자체가 차단됩니다.

04갱신된 데이터는 어디에 쓰이나 — 활용 5지점

활용 지점동작
① 패키지 악성 판정의존성 검사(scan --check-deps·check_package)가 osv-malicious 캐시를 조회해 판정. 온라인 모드는 캐시 대신 OSV.dev를 실시간 조회합니다(캐시는 망분리 전용 판정 근거).
② 우선순위 점수 병기KEV 등재 취약점 신호에 EPSS 악용확률·백분위 + CVSS 3.1 점수·심각도를 자동 병기 — 보안팀이 별도 조회 없이 "무엇부터 패치할지"를 정할 수 있습니다.
③ 리포트 기준일 표기오프라인 검사 리포트 배너에 피드별 캐시 기준일이 자동 표기됩니다 — "며칠 데이터 기준의 판정인지"를 문서가 스스로 밝힙니다.
④ 초안 룰 → 지식 검색KEV 초안 룰은 search_rules·get_rule로 조회 가능한 자문 정보로 노출됩니다(빈 패턴 — 코드 매칭용이 아니라 SBOM·자산 점검 지침). 보안팀 승인(approved) 후에만 집행 대상이 됩니다.
⑤ 환경 진단gvskb doctor --offline·MCP server_status가 캐시 존재·건수·경과일을 보여줍니다 — 반입 담당자가 갱신 필요 여부를 즉시 확인.

판정 결과의 의미 (의존성 검사)

판정의미처리
malicious캐시(또는 OSV 실시간)에 악성으로 등재된 패키지즉시 제거·차단
checked_clean신선한 캐시 기준 이상 없음통과
checked_stale캐시가 30일 초과 — '이상 없음'을 확정할 수 없음번들 재반입 후 재검사
unknown캐시 없음·해당 생태계 미수록 — 검사되지 않음'안전' 아님 — 검토 필요(exit≠0)

정직성 원칙

이 도구는 "판정 불가"를 절대 "안전"으로 바꿔 말하지 않습니다. 캐시가 없거나, 오래됐거나, 해당 생태계를 안 담았으면 그 사실이 판정·리포트·종료코드에 그대로 드러납니다.

05어떻게 믿을 수 있나 — 7겹 검증 장치

#장치차단하는 위협
1게시 sha256 사이드카다운로드 과정의 손상·변조 — 외부망 PC에서 sha256sum -c로 대조
2번들 manifest 전수 검증USB 이동 중 변조 — 반입 시 파일별 sha256 재계산, 하나라도 불일치면 전체 거부(부분 반입 금지)
3캐시 로드 시 재검증반입 후 디스크에서의 변조 — 읽을 때마다 envelope sha256 재확인, 불일치 캐시는 자동 무시
4신선도 30일 정책묵은 캐시의 거짓 안심 — 초과 시 '이상 없음'을 판정 보류로 승격(악성 발견은 오래돼도 유효)
5생태계 커버리지 기록PyPI만 담은 캐시로 npm 패키지를 '깨끗함' 판정하는 오류 — 미수록 생태계는 판정 불가 처리
6룰 status 게이트자동 생성 룰의 무검토 집행 — proposed는 승인 전 발화 금지, deprecated는 영구 금지
7감사로그(옵트인)이력 부재 — 인텔 갱신·번들 반입·검사·차단이 월별 JSONL로 기록(원본 코드·개인정보 미저장)

실행으로 검증됨

위 장치들은 문서상 주장이 아니라 자동화 테스트 471개(악성 판정·변조 거부· 신선도 승격·커버리지·게이트 시나리오 포함)로 상시 검증되며, 저장소에서 pytest -q로 누구나 재현할 수 있습니다.

06운영 방법 — 역할·주기·절차

역할 분담

역할하는 일
담당 공무원(사용 부서)코드 검사 실행, 리포트 확인, 보안팀 제출. 인텔 운영에 관여할 필요 없음.
반입 담당(전산·보안)주기적으로 번들 다운로드 → 해시 확인 → 반입(intel-bundle import) → doctor --offline 확인.
보안팀리포트 검토·배포 승인, 예외(.gvskb-exceptions.yaml) 승인, proposed 초안 룰 검토·승격.

망분리 기관 반입 절차 (권장 주기: 주 1회 이상)

# 1) 외부망 PC — 다운로드 + 무결성 확인
curl -LO https://github.com/Lex6won/vibecode-checker/releases/download/intel-latest/gvskb-intel-bundle.zip
curl -LO https://github.com/Lex6won/vibecode-checker/releases/download/intel-latest/gvskb-intel-bundle.zip.sha256
sha256sum -c gvskb-intel-bundle.zip.sha256          # "OK" 확인 후 USB 복사

# 2) 망분리 PC — 전수 검증 반입 + 상태 확인
gvskb intel-bundle import gvskb-intel-bundle.zip     # sha256 불일치 시 전체 거부
gvskb doctor --offline                               # 캐시 존재·건수·경과일 점검

# 3) 평소처럼 검사 — 갱신된 캐시가 자동으로 판정에 사용됨
gvskb scan ./내프로젝트 --check-deps --format html

주기를 놓쳐도 위험하지 않습니다 — 30일이 지나면 도구가 스스로 '이상 없음' 판정을 보류로 승격하고 리포트에 기준일을 표기하므로, 오래된 데이터가 최신처럼 보이는 일이 없습니다. 온라인 기관은 반입 절차가 아예 불필요합니다(실시간 조회).

질문답
갱신을 오래 안 하면 검사가 멈추나?아니요. 코드 정적 분석(216룰)은 캐시와 무관하게 동작합니다. 의존성 검사만 checked_stale(검토 필요)로 강등됩니다.
번들이 변조되면?반입 단계에서 파일별 sha256 불일치로 전체 거부되고, 설령 반입 후 변조돼도 로드 시 재검증으로 해당 캐시가 무시됩니다.
새 KEV 취약점이 바로 검사에 반영되나?데이터(캐시)로는 즉시 반영됩니다(KEV 신호·EPSS 병기). 룰로는 보안 담당자가 초안 PR을 검토·승인한 뒤에만 집행됩니다.
GitHub Actions가 실패한 날은?릴리스에는 마지막 성공본이 그대로 남아 있어 반입에 지장이 없습니다. 신선도는 번들 안의 수집 시각 기준으로 판정됩니다.
