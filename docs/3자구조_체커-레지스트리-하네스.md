# 세 시스템의 구조 — 체커 · 레지스트리 · 하네스

> **성격**: 세 시스템의 역할·경계·흐름을 한 장으로 정리한 문서.
> 상세 계약은 `연동합의_gg-trusted-registry.md`(체커↔레지스트리)와
> `하네스_집행계약.md`(하네스)에 있고, 이 문서는 **셋을 함께 볼 때의 그림**이다.
> **작성일**: 2026-08-02

---

## 1. 한 문장씩

| 시스템 | 한 문장 | 산출물 |
|---|---|---|
| **vibecode-checker (gvskb)** | 코드와 패키지를 **검사해서 사실을 말한다** | 관측 — "이 패키지는 이렇다" |
| **gg-trusted-registry** | 사람이 **판정을 내리고 그것을 보관한다** | 판정 — "경기도가 이렇게 정했다" |
| **vibe_harness** | 개발 현장에서 **실제로 막고 돕는다** | 집행 — 설치를 거부하거나 통과시킨다 |

셋을 나눈 이유는 **책임의 성격이 다르기 때문**이다. 관측은 누구나 재현할 수 있어야
하고, 판정은 기관이 책임져야 하며, 집행은 현장에서 일어난다. 하나로 합치면
도구가 기관을 대신해 결정하게 되거나, 기관 서비스가 소스 코드를 보관하게 된다.

## 2. 사용자가 겪는 흐름

### 2-1. 개발 중 (하네스가 상시 작동)

```
공무원이 AI로 코딩
   │
   ├─ 하네스: 개발 언어를 Python·JavaScript 로 제한
   │          (그 밖의 언어는 정식 정보화사업 절차로 이관)
   │
   ├─ 패키지를 설치하려 함
   │     │
   │     ├─ 하네스가 gvskb 를 호출해 판정을 받는다
   │     │     └─ gvskb: 실재·취약점·악성·쿨다운·라이선스 검사
   │     │              + (연동 시) 레지스트리 조회
   │     │
   │     └─ 하네스가 §집행계약 규칙으로 결정
   │           차단 / 경고 / 통과
   │
   └─ 완성된 코드를 gvskb 로 전체 점검 → 보고서
```

### 2-2. 점검 결과가 레지스트리로 가는 경로

```
gvskb 검사 결과
   │
   ├─【온라인】자동 제출 (submit-batch)
   │
   └─【폐쇄망】반입 번들 파일 → 사람이 USB 로 반출 → 레지스트리에 반입
        (보고서와 함께 나가되, 번들에는 코드·경로·개인정보가 없다)
   │
   ▼
레지스트리에 **관측 데이터**로 적재
   │
   ├─ source_scope = single·manifest  → 보안담당자 **심사 대기열에 오름**
   └─ source_scope = lockfile·installed → 관측으로만 저장, 큐에 올리지 않음
   │
   ▼
보안담당자가 **심사** → APPROVED / REJECTED
   │
   ▼
다음 검사부터 gvskb 가 그 판정을 조회해 반영
   │
   ▼
하네스가 그 판정으로 집행
```

## 3. 누가 누구를 부르는가 ★

**이 방향이 구조의 핵심이다.**

```
   ┌──────────┐   ①판정 요청    ┌──────────┐   ②조회      ┌──────────────┐
   │ 하네스   │ ─────────────▶ │  gvskb   │ ───────────▶ │  레지스트리   │
   │(집행)    │ ◀───────────── │ (관측)   │ ◀─────────── │  (판정)       │
   └──────────┘   판정 결과      └──────────┘   판정        └──────────────┘
                                      │                          ▲
                                      └──────③제출(관측)─────────┘
```

- **하네스는 레지스트리를 직접 부르지 않는다.** gvskb 를 통한다.
- **레지스트리는 코드를 보지 않는다.** 패키지 이름·버전·판정만 받는다.
- **gvskb 는 승인 권한이 없다.** 조회해서 옮길 뿐이다.

### 왜 하네스가 레지스트리를 직접 부르지 않는가

| 이유 | 설명 |
|---|---|
| 로컬 안전망을 건너뛸 수 없게 | 레지스트리 승인만 보고 설치하면 로컬 악성·KEV 대조가 생략된다. gvskb 를 거치면 그 대조가 **반드시** 수행된다(합의 원칙 4) |
| fail-open 로직이 한 곳에 | 조회 실패·캐시·강등 처리가 두 곳에 흩어지면 규칙이 갈라진다 |
| 캐시 공유 | 같은 패키지를 두 시스템이 각자 조회하지 않는다 |
| 토큰이 한 곳에 | 레지스트리 API 키를 하네스에도 두면 유출면이 두 배가 된다 |

## 4. 역할 경계 — 각자 **하지 않는** 것

경계를 흐리면 셋으로 나눈 의미가 없어진다.

| | 하는 것 | **하지 않는 것** |
|---|---|---|
| **gvskb** | 검사·판정 조회·관측 제출 | 승인/거절 결정 · 설치 차단 · 언어 통제 |
| **레지스트리** | 승인/거절·이력 보관·심사 큐 | 코드 열람 · 검사 수행 · 설치 개입 |
| **하네스** | 언어 통제·설치 차단·개발 지원 | 자체 취약점 판정 · 레지스트리 직접 조회 |

## 5. 정정 — 말씀하신 이해와 다른 점 3가지

### 5-1. "그 결과 리스트를 하네스가 이용한다" → **하네스는 레지스트리를 직접 보지 않는다**

하네스가 레지스트리에서 승인 목록을 받아 쓰는 구조가 아니다. **하네스는 gvskb 를
호출하고, gvskb 가 레지스트리를 조회해 합쳐진 판정을 돌려준다**(§3).

결과적으로 하네스가 기관 판정을 쓰는 것은 맞지만, **경로가 다르다.** 이 차이가
중요한 이유는 §3 표에 적은 대로다 — 직결하면 로컬 악성 대조를 건너뛸 수 있다.

### 5-2. "보안담당자가 레지스트리에 입력한다" → **입력이 아니라 심사다**

데이터는 **자동으로 들어간다**(온라인은 API 제출, 폐쇄망은 번들 반입). 보안담당자가
패키지 이름을 타이핑하는 절차가 아니다.

사람이 하는 일은 **판정**이다 — 쌓인 관측을 보고 승인할지 거절할지 정한다.
그래서 "무엇을 심사 대기열에 올릴지"가 중요한 설계 지점이 됐다(§5-3).

### 5-3. "점검 결과를 제출하면" → **전부 심사 대상이 되지는 않는다**

락파일 하나에 패키지가 수백~수천 건이다. 전부 심사 큐에 올리면 담당자 일이
폭증해서 **레지스트리 도입 목적(중복 심사 제거)과 정반대**가 된다.

| 유래 | 관측 저장 | 심사 큐 |
|---|---|---|
| `single` — 사람이 직접 물어본 것 | ○ | **올림** |
| `manifest` — 매니페스트에 적힌 직접 의존성 | ○ | 올림 |
| `lockfile` · `installed` — 딸려온 전이 의존성 | ○ | **올리지 않음** |

전이 의존성도 **저장은 된다** — 다음 사람이 같은 패키지를 물어보면 즉답할 수 있는
캐시가 된다. 다만 사람의 심사 대기열에는 올리지 않는다.

## 6. 나머지는 말씀하신 대로다

- ✅ 체커가 Python·JavaScript 패키지(전이 의존성 포함) 점검 결과를 **별도 섹션으로 리포팅**한다
- ✅ 하네스가 **개발 언어를 통제**한다 (Python·JavaScript 로 제한)
- ✅ 하네스가 **안전한 패키지를 쓰도록 돕는다**
- ✅ **패키지가 충분히 등록되지 않았거나**(`unknown`) **시간이 지나 낡았을 때**
  (`stale`·`checked_stale`) **정책에 따라 판단**한다

마지막 항목이 하네스 집행계약 §4(모드별 결정표)와 §5(시스템 열화)의 내용이다.
"충분하지 않다"는 `unknown`, "시간이 많이 지났다"는 인텔 캐시 낡음·차단 강등에
해당한다.

## 7. 언어 통제 — 세 시스템이 같은 선을 긋는가

| | 대상 언어 |
|---|---|
| 하네스 | Python · JavaScript 로 **제한**(정책) |
| gvskb | Python · JavaScript **검사 가능**(C/C++·Java 는 범위 외) |
| 레지스트리 | `pypi` · `npm` 생태계 |

**셋이 일치한다.** 이건 우연이 아니라 같은 판단에서 나왔다 — 바이브 코딩으로
공무원이 다룰 수 있는 범위가 그 둘이고, 그 밖은 정식 정보화사업 절차로 이관한다.

다만 **경계 사례**가 있다: 사용자가 Python 프로젝트 안에서 다른 언어 파일을
만들면? 하네스가 막는가, gvskb 가 "범위 외"로 표시만 하는가. §8-4 참조.

## 8. 아직 정해지지 않은 것

### 8-1. 판정의 신선도 — 언제 검사한 결과로 집행하는가

하네스가 설치를 막을 때 쓰는 판정이 **언제 검사한 것인가**가 정해지지 않았다.

- 설치 직전에 매번 gvskb 를 호출하면 정확하지만 느리다
- 사전 스캔 결과를 재사용하면 빠르지만, 어제 판정으로 오늘 설치를 막게 된다

하네스 집행계약 §7 은 "gvskb 판정 시각과 집행 시각의 간격을 기록하라"고만 했고
**허용 간격을 정하지 않았다.**

> **제안**: 설치 시점 판정은 **1시간 이내**의 것만 쓰고, 그보다 낡으면 다시
> 호출한다. 레지스트리 `APPROVED` 캐시 TTL 과 같은 값이라 운영 감각이 맞는다.

**결정 필요** — 하네스.

### 8-2. 심사 큐 용량 — 담당자가 감당할 수 있는가

`single`·`manifest` 만 올려도 초기에는 상당량이 쌓인다. 담당자 1인이 하루 몇 건을
심사할 수 있는지 모른 채 설계했다.

이 숫자가 §하네스계약 §9-1 의 **ENFORCE 전환 기준(직접 의존성 `unknown` 10%)**
달성 시점을 결정한다. 심사 속도가 유입보다 느리면 비율이 내려가지 않는다.

> **제안**: MONITOR 2주 구간에서 **유입 건수와 심사 처리 건수를 함께 측정**한다.
> 처리가 유입을 못 따라가면 전환 기준을 비율이 아니라 "직접 의존성 상위 N개 등록"
> 같은 절대량으로 바꾼다.

**결정 필요** — 레지스트리 + 기관.

### 8-3. 번들 반입 주기 — 폐쇄망 운영 절차

반입 번들을 만들었지만 **누가 언제 반출·반입하는지**가 절차로 정해지지 않았다.
인텔 번들(외부→내부)은 매일 자동인데, 관측 번들(내부→레지스트리)은 사람 손이다.

> **제안**: 점검 보고서를 제출하는 기존 절차에 얹는다. 별도 절차를 만들면
> 아무도 안 한다.

**결정 필요** — 기관.

### 8-4. 언어 경계 사례

Python 프로젝트 안의 `.java`·`.c` 파일을 하네스가 막는가, gvskb 가 "범위 외"로
표시만 하는가.

> **제안**: 하네스가 **경고**하되 막지는 않는다. 정식 사업으로 이관해야 할
> 신호이지 그 자체가 보안 위험은 아니다. gvskb 는 지금처럼 "범위 외"로 정직하게
> 표시한다.

**결정 필요** — 기관.

### 8-5. 우회 정책 (진행 중)

하네스 집행계약 §10 에 제안이 있고 **3자 합의 대기 중**이다. 그중 하나는
레지스트리 수용이 필요하다 — 우회 사실을 알릴 경로(`override` 봉투 필드)가
현재 합의서에 없다.

## 9. 전달용 요약 — 세 팀에 무엇을 물을 것인가

| # | 항목 | 받는 곳 | 무엇을 정해야 하나 |
|---|---|---|---|
| 1 | **`source_scope` 에 `installed` 추가** | 레지스트리 | enum 반영. 안 하면 배치 전체 422 |
| 2 | **반입 번들 형식 확인** | 레지스트리 | `gvskb-registry-bundle/1` 수용 여부 |
| 3 | **`override` 봉투 필드 + §5-D 예외** | 레지스트리 | 우회 통보 경로 |
| 4 | **심사 처리 용량 측정** | 레지스트리 | 하루 몇 건? ENFORCE 전환 기준과 직결 |
| 5 | **판정 신선도 허용 간격** | 하네스 | §8-1 — 1시간 제안 |
| 6 | **하네스가 레지스트리를 직접 조회하지 않는다** | 하네스 | §3 구조 확인 |
| 7 | **우회 정책 6건** | 3자 | 하네스 집행계약 §10-7 |
| 8 | **번들 반입 절차** | 기관 | §8-3 |
| 9 | **언어 경계 사례** | 기관 | §8-4 |

1~3 은 레지스트리가 코드를 고쳐야 하는 것, 4~6 은 값·구조 확인, 7~9 는 정책이다.
