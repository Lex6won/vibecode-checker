# 하네스 집행 계약 — vibe_harness 가 지켜야 할 것

> **성격**: gvskb ↔ gg-trusted-registry 연동합의(`연동합의_gg-trusted-registry.md`)의 §10.
> 두 시스템이 판정을 만들고 저장하지만 **실제로 설치를 막는 곳은 하네스**다.
> 이 문서가 비어 있으면 앞의 계약 전부가 정보 제공에 그친다.
> **작성일**: 2026-08-02 · **상태**: 정책 4/5 확정(§9), 우회 정책은 3자 합의 대기(§10)

---

## 1. 왜 하네스가 계약에 들어와야 하는가

```
gvskb        판정을 낸다        "이 패키지는 악성이다"
레지스트리    판정을 저장한다     "경기도가 이 패키지를 차단했다"
하네스        ← 실제로 막는다    설치 명령을 가로채 거부한다
```

앞의 둘은 **말할 뿐**이다. 하네스가 그 말을 무시하면 `malicious` 판정이 나와도
`pip install` 은 성공한다. 지금까지의 합의는 전부 이 마지막 칸이 채워진다는
전제 위에 서 있었고, 그 칸은 비어 있었다.

특히 위험한 조합이 하나 있다. 연동합의 §4-5 는 "레지스트리 조회를 방해하는
것만으로 차단을 우회할 수 있다"는 문제를 캐시로 막았다. 그런데 **하네스가 낡은
차단(§3-2)을 경고로만 다루면 그 우회가 7일 뒤에 그대로 성립한다.** 캐시는
시간을 벌어 줄 뿐이고, 벌어 준 시간에 무엇을 하는지는 하네스가 정한다.

---

## 2. 하네스가 받는 신호

gvskb 의 `PackageCheckResult`(패키지 1건) 및 `audit_manifest` 결과(매니페스트 1건)
에서 다음 필드를 읽는다. **모두 이미 존재하는 필드이며 새로 만들 것은 없다.**

### 2-1. 패키지 단위

| 필드 | 값 | 하네스가 알아야 할 것 |
|---|---|---|
| `verdict` | 아래 §3 표의 10종 | 판정의 종류 |
| `verdict_severity` | info·low·medium·high·critical | 심각도 |
| `requires_review` | bool | 사람 확인이 필요한가 |
| `checked` | bool | **취약점 검사를 실제로 수행했는가.** `false` 는 '안전'이 아니라 '판정 못 함' |
| `is_malicious_package` | bool | 악성 확인 |
| `in_kev` | bool | 실제 악용 중(CISA KEV). **단 `cache_sources_used` 가 비어 있으면 `false` 는 '대조 못 함'** |
| `max_cve` | NONE·LOW·MEDIUM·HIGH·CRITICAL·UNKNOWN | `UNKNOWN` 은 '취약점은 있으나 심각도 미상' — 안전이 아님 |
| `cooldown.ok` | true·false·**null** | `null` 은 판정 불가(발행일 미확인) |
| `registry_status` | ok·unreachable·unauthorized·disabled | 기관 판정을 물어봤는가 |
| `registry_decision` | dict 또는 null | 원본 판정. `stale: true` 면 §3-2 참조 |
| `heuristics.typosquat_warning` | str 또는 없음 | 이름 유사성 **휴리스틱**(확정 아님) |

### 2-2. 매니페스트 단위 — 개별 패키지가 아니라 검사 전체의 상태

| 필드 | 하네스가 알아야 할 것 |
|---|---|
| `truncated_count` | **limit 로 잘려 검사되지 않은 패키지 수.** 0 이 아니면 그만큼은 판정이 없다 |
| `unchecked_count` | 판정 불가 수 |
| `intel_cache.state` | ok·stale·**missing**·not_used — 로컬 안전망의 상태 |
| `registry_status` | 매니페스트 전체의 레지스트리 도달 여부 |
| `source_kind` | manifest·lockfile — 전이 의존성까지 봤는가 |

## 3. 절대 규칙 — 모드와 무관하게 항상 차단

아래는 **정책이 아니라 사실**이므로 운영 모드를 타지 않는다.

| 조건 | 이유 |
|---|---|
| `verdict == "malicious"` | 악성으로 확인됨 |
| `verdict == "registry_rejected"` | 기관이 명시적으로 차단함 |
| `verdict == "not_found"` | 저장소에 **존재하지 않는** 패키지. AI 가 지어낸 이름(슬롭스쿼팅)일 가능성이 가장 높고, 설치 시도 자체가 공격자에게 이름을 선점할 기회를 준다 |
| `in_kev == true` | 실제로 악용 중인 취약점 |

### 3-1. 왜 `not_found` 가 절대 규칙인가

이건 휴리스틱이 아니라 **사실 확인**이다. 공식 저장소에 없다는 것은 조회로
확정된다. 그리고 과거에 이 항목이 가장 위험했다 — OSV 가 빈 응답을 주므로
"취약점 0건"으로 **가장 깨끗해 보였다**.

### 3-2. 낡은 차단(`stale`)도 차단이다 ★

레지스트리에 닿지 못하는 동안 gvskb 는 마지막 차단 판정을 로컬 캐시에서 꺼내
쓴다. TTL(7일)이 지나면 그 항목을 **삭제하지 않고 `stale: true` 를 붙여** 계속
돌려준다(연동합의 §4-5).

**하네스는 낡은 차단도 차단으로 다뤄야 한다.** 근거는 셋이다.

1. **차단은 패키지에 대한 진술이지 네트워크에 대한 진술이 아니다.** 레지스트리에
   닿지 못한다고 해서 그 패키지가 안전해진 것이 아니다. 바뀐 것은 우리의
   최신성 확신뿐이다.
2. **비대칭이 분명하다.** 차단이 풀리는 일(차단 → 승인)은 드물고, 잘못 통과시킨
   비용은 크다.
3. **경고로 떨어뜨리면 §4-5 가 무의미해진다.** 조회를 7일간 방해하면 차단이
   사실상 해제된다 — 캐시로 막으려던 우회가 그대로 성립한다.

다만 사용자에게는 **낡았다는 사실을 알려야** 한다: "8일 전 기관이 차단한
패키지입니다. 현재 레지스트리에 연결되지 않아 최신 상태는 확인하지 못했습니다."

> **gvskb 측 보완 필요**: 현재 `apply_registry_decision` 이 `stale` 표식을 읽지
> 않아 낡은 차단과 신선한 차단의 안내 문구가 같다. 판정(차단)은 옳으나 표시가
> 부족하다 — 수정 예정.

## 4. 모드별 결정표 — 정책 영역

절대 규칙 밖의 항목은 기관이 운영 모드로 정한다. 단계적 진입을 권한다.

| `verdict` / 조건 | MONITOR | WARN | ENFORCE |
|---|---|---|---|
| `vulnerable` · max_cve CRITICAL·HIGH | 경고 | **차단** | **차단** |
| `vulnerable` · max_cve MEDIUM·LOW | 기록 | 경고 | **차단** |
| `vulnerable` · max_cve **UNKNOWN** | 경고 | 경고 | **차단** |
| `cooldown_hold` | 기록 | 경고 | **차단** |
| `checked_stale` | 기록 | 경고 | 경고 |
| `unknown` · `error` | 기록 | 경고 | **차단** |
| `registry_approved` · `checked=true` | 통과 | 통과 | 통과 |
| `registry_approved` · `checked=false` | 통과 | 경고 | 경고 |
| `checked_clean` | 통과 | 통과 | 통과 |
| `heuristics.typosquat_warning` (실재하는 패키지) | 경고 | 경고 | **차단** |

**모드 정의**

- **MONITOR** — 아무것도 막지 않고 전부 기록한다. 도입 초기 커버리지·오탐률
  실측용. 이 구간의 목적은 "무엇을 막게 될지 미리 보는 것"이다.
- **WARN** — 고위험만 막고 나머지는 경고. 실무 기본값으로 권한다.
- **ENFORCE** — 판정 불가까지 막는다. **커버리지가 확보된 뒤에만** 켠다.

### 4-0. `unknown` 차단은 **직접 의존성에만** 적용한다 ★

`unknown`(미등록)을 ENFORCE 에서 차단하기로 하면, 그대로는 **ENFORCE 에 도달할 수
없다.**

락파일 하나에 전이 의존성이 수백~수천 건이다. 이걸 전부 차단하지 않으려면 전부
레지스트리에 등록돼야 하는데, 그건 심사 큐가 감당하지 못한다 — 그리고 그건 이미
합의 §5-C 에서 "락파일 유래는 심사 큐에 올리지 않는다"고 정한 것과 정면으로
어긋난다. 큐에 올리지 않기로 해 놓고 등록되기를 기다릴 수는 없다.

**그래서 `unknown` 차단은 사람이 고른 것에만 적용한다.**

| `source_scope` | 성격 | ENFORCE 에서 `unknown` |
|---|---|---|
| `single` · `manifest` | **사람이 직접 고른** 의존성 | **차단** |
| `lockfile` · `installed` | 고른 것의 **결과로 딸려온** 것 | 차단하지 않음 |

전이 의존성에도 **악성·기관차단·미존재·KEV 는 그대로 적용**된다(§3 절대 규칙).
빠지는 것은 "등록되지 않았다"는 이유만의 차단뿐이다.

근거: 전이 의존성은 사람의 선택이 아니라 직접 의존성의 결과다. 직접 의존성이
승인됐다면 그 트리는 암묵적으로 함께 수용된 것에 가깝고, 정말 위험한 것은
절대 규칙이 잡는다.

이 구분이 없으면 §4-1 의 전환 기준이 영원히 충족되지 않는다.

### 4-1. `unknown` 을 언제 막을 것인가 — 가장 신중해야 할 결정

미등록·판정 불가를 처음부터 막으면 도입 초기에 아무도 개발을 못 한다(레지스트리
등록이 거의 없는 구간). 반대로 끝까지 안 막으면 슬롭스쿼팅이 그대로 통과한다.

**단계적 진입을 권하는 이유**가 여기 있다. MONITOR 구간에서 `unknown` 비율이
실측되고, 그 비율이 충분히 떨어졌을 때 ENFORCE 로 올린다. 숫자 없이 ENFORCE 를
켜면 곧 우회 문화가 생기고, 우회가 습관이 되면 하네스 전체가 무력해진다.

### 4-2. 타이포스쿼팅은 절대 규칙이 아니다 — 레지스트리 제안과 다른 판단

레지스트리 측은 타이포스쿼팅 의심을 전 모드 차단으로 제안했다. **동의하지
않는다.**

`not_found`(존재하지 않음)와 달리 타이포스쿼팅 경고는 **편집거리 기반 휴리스틱**
이고 오탐이 실재한다. 특히 기준 코퍼스를 키우면 오탐도 함께 커진다 — 정상
패키지끼리 이웃이 되기 때문이다. MONITOR 구간에서 휴리스틱으로 차단하면
"하네스는 멀쩡한 걸 막는다"는 인상이 먼저 생기고, 그 뒤로는 진짜 차단도 우회
대상이 된다.

**단, 둘이 겹치면 확정이다** — 실재하지 않으면서 유명 패키지와 이름이 비슷하면
그건 슬롭스쿼팅이 거의 확실하며, 이미 `not_found` 절대 규칙에 걸린다.

## 5. 시스템 열화 — 개별 패키지가 아니라 환경의 문제

연동합의 §2 원칙 5: **알림 단위는 조치 단위를 따른다.** 조치가 한 건이면 알림도
한 건이다. 패키지 수백 건에 같은 깃발을 꽂으면 담당자는 그것을 무시하게 되고,
무시가 습관이 되면 그 사이의 진짜 위험도 함께 묻힌다.

| 상태 | 의미 | 하네스 동작 |
|---|---|---|
| `registry_status = unreachable` | 기관 판정을 **물어보지 못함** | 개별 차단 아님. **세션당 1회 배너**. 단 캐시된 차단은 §3-2 대로 여전히 차단 |
| `registry_status = unauthorized` | 토큰 만료·권한 변경 | 위와 같음 + 운영 담당자 알림(사용자가 고칠 수 없는 문제) |
| `intel_cache.state = stale` | 로컬 위협 정보가 낡음 | 세션당 1회 배너 — "인텔 번들을 반입하세요" |
| `intel_cache.state = missing` | **로컬 안전망이 0** | MONITOR·WARN: 강한 배너. **ENFORCE: 설치 차단** |
| `truncated_count > 0` | 일부 패키지가 **검사되지 않음** | 미검사 패키지를 '통과'로 다루지 않는다. 최소한 경고, ENFORCE 에서는 차단 |

### 5-1. `intel_cache = missing` 이 왜 ENFORCE 에서 차단인가

이 상태에서는 로컬 악성·KEV 대조가 **한 번도 수행되지 않는다.** 연동합의 원칙 4
("로컬 탐지가 최종 안전망")가 정확히 무력화되는 구간이고, 특히 **첫 배포일**에
자연스럽게 발생한다 — 캐시 0, 로컬 검증 0, 기관 승인 건은 전부 통과.

조치가 명확하다는 점도 중요하다. `gvskb update-intel` 한 번(폐쇄망은 번들 반입
한 번)으로 해소되므로, 막아도 사용자가 무엇을 해야 할지 안다.

### 5-2. `truncated_count` 를 무시하면 안 되는 이유

락파일 800건 중 500건만 검사됐다면 300건은 **판정이 없는 것**이지 통과가 아니다.
하네스가 "차단 목록에 없으니 통과"로 다루면 검사 범위가 조용히 줄어든다.

## 6. 기존 카탈로그와의 우선순위

하네스에는 이미 `package-catalog.yaml` 이 있고 레지스트리 조회가 새로 들어온다.
어느 쪽이 이기는지 정하지 않으면 같은 패키지가 경로에 따라 다르게 판정된다.

### 6-0. 형식과 무관한 불변식 ★

> **로컬 카탈로그는 레지스트리의 `REJECTED` 를 덮을 수 없다.**
> 카탈로그가 허용목록이든 차단목록이든, 어떤 항목에 무엇이 적혀 있든 예외 없다.

근거: 카탈로그는 파일이고 레지스트리는 사람이 관리하는 최신 판정이다. 카탈로그
항목은 한 번 적히면 아무도 지우지 않는 경향이 있어, 이 불변식이 없으면 **과거에
허용했던 파일 한 줄이 현재의 기관 차단을 무력화**한다.

나머지는 카탈로그 형식에 따라 갈린다. 아래 두 경우를 모두 명세하므로 형식만
확인하면 바로 적용할 수 있다.

### 6-1. 카탈로그가 **차단목록**(deny list)인 경우

"이건 쓰지 마라" 목록. 규칙이 단순하다.

| 카탈로그 | 레지스트리 | 결과 |
|---|---|---|
| 차단 | 무엇이든 | **차단** |
| 없음 | `REJECTED` | **차단** |
| 없음 | `APPROVED` | 통과 |
| 없음 | `UNDER_REVIEW`·`UNKNOWN`·미조회 | §4 모드 표를 따름 |

**차단 신호는 합집합** — 어느 한쪽이라도 막으면 막는다.

### 6-2. 카탈로그가 **허용목록**(allow list)인 경우

"이것만 써라" 목록. 여기서 순진하게 "허용은 교집합"을 적용하면 **카탈로그에 없는
모든 패키지가 차단**되어 사실상 즉시 ENFORCE 가 된다. 도입 초기에 이걸 켜면
개발이 멈추고, 곧 하네스를 끄는 문화가 생긴다.

그래서 **레지스트리를 카탈로그의 대체가 아니라 확장으로** 다룬다. 레지스트리도
사람이 승인한 목록이므로 카탈로그와 성격이 같고, 더 최신이기 때문이다.

| 카탈로그 | 레지스트리 | 결과 |
|---|---|---|
| 허용 | `REJECTED` | **차단** ← §6-0 불변식 |
| 허용 | 그 외 | 통과 |
| 없음 | `APPROVED` | **통과** ← 레지스트리가 카탈로그를 확장한다 |
| 없음 | `REJECTED` | **차단** |
| 없음 | `UNDER_REVIEW`·`UNKNOWN`·미조회 | §4 모드 표를 따름 |

마지막 줄이 핵심이다. "카탈로그에 없음"을 곧바로 차단으로 보지 않고 **`unknown`
으로 넘겨** §4 의 모드가 정하게 한다. 그러면 MONITOR 로 시작해 커버리지를 실측한
뒤 ENFORCE 로 올리는 §4-1 의 경로가 그대로 성립한다.

### 6-3. 둘 다 있는 경우(deny + allow 혼재)

실무에서 흔하다. 평가 순서를 고정한다.

```
① 카탈로그 deny        → 차단 (즉시 확정)
② 레지스트리 REJECTED  → 차단 (§6-0)
③ 카탈로그 allow       → 통과
④ 레지스트리 APPROVED  → 통과
⑤ 나머지               → §4 모드 표
```

차단 두 개를 먼저 평가하는 것이 요점이다. 허용을 먼저 보면 ①과 ②가 가려진다.

## 7. 하네스가 남겨야 할 기록

gvskb 의 감사로그(`GVSKB_AUDIT_DIR`)는 **gvskb 가 판정한 시점**만 남긴다.
하네스가 그 판정을 무시하고 설치했다면 그 사실은 어디에도 없다.

하네스는 **자기 결정**을 남겨야 감사가 성립한다.

| 항목 | 이유 |
|---|---|
| 하네스의 결정 (차단·경고·통과) | 판정과 집행은 다르다 |
| 결정의 근거가 된 `verdict` 와 `registry_status` | 왜 그렇게 정했는지 |
| 운영 모드 (MONITOR·WARN·ENFORCE) | 같은 판정도 모드에 따라 결과가 다르다 |
| **사용자 우회 여부** | 가장 중요한 감사 항목 |
| gvskb 판정 시각과 집행 시각의 간격 | 캐시된 판정으로 집행했는지 |

개인 식별자는 남기지 않는다(연동합의 §3). `caller` 규칙과 같은 형식을 쓴다:
`<출처>:<모드>[:부서코드]`.

## 8. 근본 한계 — 명시해 두어야 할 것

하네스는 **자기를 거치는 설치만** 막을 수 있다.

| 우회 경로 | 하네스가 막을 수 있는가 |
|---|---|
| 터미널에서 직접 `pip install` | ❌ |
| 이미 설치된 패키지 | ❌ (`scan_installed_packages` 로 사후 발견은 가능) |
| IDE·에이전트가 자체 경로로 설치 | ❌ |
| 하네스 설정 파일을 사용자가 수정 | ❌ |

이건 결함이 아니라 **경계**다. 하네스는 사고를 줄이는 장치이지 통제 수단이
아니며, 그렇게 소개해야 한다. 통제가 필요하면 별도 수단(사설 미러·프록시)이
있어야 하고 그건 이 계약의 범위 밖이다.

## 9. 기관 결정 — 확정분

2026-08-02 결정. 나머지 절은 이 결정을 전제로 읽는다.

| # | 항목 | 결정 |
|---|---|---|
| 1 | 도입 시작 모드 | **MONITOR** |
| 2 | ENFORCE 전환 기준 | **`unknown` 비율 기준** — 아래 §9-1 |
| 3 | `unknown` 취급 | §4 표 + **§4-0 직접/전이 구분** |
| 4 | 카탈로그 우선순위 | `package-catalog.yaml` 에 allow·deny **둘 다 존재** → **§6-3 평가 순서 적용** |
| 5 | 우회 허용 여부와 절차 | **미정** — 3자 합의 필요(§11) |

### 9-1. 전환 기준의 구체값

> **직접 의존성**(`source_scope` 가 `single`·`manifest`)의 `unknown` 비율이
> **10% 이하**로 3주 연속 유지되면 WARN → ENFORCE 로 올린다.

- **분모를 직접 의존성으로 한정**하는 이유는 §4-0 과 같다. 전이 의존성을 넣으면
  분모가 수천 건이 되어 비율이 내려가지 않고, 기준이 영원히 충족되지 않는다.
- **3주 연속**을 붙인 이유: 특정 주에 우연히 낮게 나온 값으로 전환하면 다음 주에
  차단이 쏟아진다.
- MONITOR → WARN 은 더 가볍게 본다. **2주 운영 후** 올린다 — WARN 이 막는 것은
  이미 절대 규칙에 가까운 고위험뿐이라 실무 마찰이 작다.

숫자는 MONITOR 구간 실측치를 보고 조정한다. 지금은 **관측 없이 정한 초기값**이며,
그 사실을 남겨 둔다.

### 9-2. 카탈로그 — §6-3 적용

allow 와 deny 가 함께 있으므로 평가 순서를 그대로 쓴다.

```
① 카탈로그 deny        → 차단 (즉시 확정)
② 레지스트리 REJECTED  → 차단 (§6-0 불변식)
③ 카탈로그 allow       → 통과
④ 레지스트리 APPROVED  → 통과
⑤ 나머지               → §4 모드 표 (§4-0 직접/전이 구분 포함)
```

**차단 두 개를 먼저 평가하는 것이 요점이다.** 허용을 먼저 보면 ①과 ②가 가려진다.

## 10. 【제안】 우회 정책 — 3자 합의 필요

미정 항목이다. **하네스·레지스트리·gvskb 세 쪽에 모두 걸리므로** 한쪽이 정할 수
없다. 아래는 gvskb 측 제안이며 세 팀이 합의하면 §9-5 로 확정한다.

### 10-1. 출발점 — 우회는 없앨 수 없다

§8 에 적었듯 하네스는 **자기를 거치는 설치만** 막는다. 터미널에서 직접
`pip install` 하면 그만이다.

> **그러므로 목표는 우회를 없애는 것이 아니라 보이게 만드는 것이다.**

우회를 금지하면 우회가 사라지는 게 아니라 **보이지 않는 곳으로 간다.** 하네스를
끄고 설치한 것은 아무 기록도 남지 않는다. 사유를 적고 통과시킨 것은 기록이 남는다.
후자가 낫다.

### 10-2. 제안 — 차단 사유마다 우회 경로를 다르게

전부에 같은 정책을 적용하는 것이 문제다. 근거의 강도가 다르기 때문이다.

| 차단 사유 | 우회 | 이유 |
|---|---|---|
| `malicious` · `in_kev` | **불가** | 근거가 확정적이고, 이걸 우회해야 할 정당한 업무 사유가 없다 |
| `registry_rejected` (신선) | **승인자 필요** | 기관이 명시적으로 막은 것을 개인이 뒤집을 수 없다 |
| `registry_rejected` (강등·낡음) | 사유 기록 + **레지스트리 통보** | 최신 확인이 안 된 상태이므로 개인이 판단하되 기관이 알아야 한다 |
| `not_found` | 사유 기록 | **오탐이 구조적으로 발생한다** — 아래 §10-3 |
| 취약점 · 쿨다운 · `unknown` | 사유 기록 | 업무 사정으로 감수할 수 있는 위험 |

### 10-3. `not_found` 를 우회 가능으로 둔 이유

§3 절대 규칙에 넣었지만, **사설 저장소 환경에서는 구조적 오탐이 발생한다.**
기관 내부 패키지나 사내 미러의 패키지는 공개 저장소(PyPI·npm)에 없으므로
`not_found` 가 된다. 실재하는데 "존재하지 않음"으로 잡히는 것이다.

차단은 유지하되(기본값이 안전해야 하므로) 사유 기록으로 풀 수 있게 한다.
사설 저장소를 쓰는 기관이라면 하네스 설정에 **내부 패키지 접두사 목록**을 두어
아예 제외하는 편이 낫다 — 매번 우회하게 만들면 우회가 습관이 된다.

### 10-4. 우회 기록에 남길 것

| 항목 | 비고 |
|---|---|
| 대상 | `pkg:pypi/name@version` |
| 차단 사유 | `verdict` + `registry_status` |
| 사유 텍스트 | 사람이 적은 것 |
| 시각 · 하네스 모드 | |
| 호출 주체 | `caller` 규칙 그대로 — **개인 식별자 금지** |

개인을 특정하지 않는다(합의 §3). "누가 우회했나"가 아니라 "무엇이 몇 번
우회됐나"가 필요한 정보다.

### 10-5. 우회는 만료된다

**기본 7일**을 제안한다. 그 뒤에는 다시 묻는다.

- 차단 사유가 해소됐을 수 있다(취약점 패치·기관 승인). 그러면 우회가 불필요해진다
- 여전하다면 다시 판단하게 하는 것이 맞다
- 7일은 `REJECTED` 캐시 TTL(합의 §4-5)과 같은 값이라 운영 감각이 일치한다

승인 단위는 **프로젝트**로 한다. 팀이 같은 의존성을 쓰므로 개인 단위로 두면
같은 우회를 팀원 수만큼 반복하게 된다.

### 10-6. ⚠ 레지스트리 통보 경로가 합의서에 없다

이 제안을 쓰다 발견한 공백이다.

**기관이 차단한 패키지가 우회로 설치됐다면 레지스트리가 그 사실을 알아야 한다.**
심사 대기열의 어떤 항목보다 우선하는 정보다 — 차단 사유가 더 이상 유효하지
않다는 신호일 수도 있고, 차단이 조직적으로 무시되고 있다는 신호일 수도 있다.
어느 쪽이든 기관이 알아야 한다.

그런데 현재 합의서에 **우회를 알리는 경로가 없다.**

**제안**: 새 엔드포인트를 요구하지 않고 기존 제출 봉투에 `override` 를 얹는다.

```json
{
  "result":       { "...PackageCheckResult 원본..." },
  "caller":       "harness:auto",
  "source_scope": "single",
  "override": {
    "reason":     "사내 미러 패키지 — 공개 저장소에 없음",
    "expires_at": "2026-08-09",
    "mode":       "WARN"
  }
}
```

**합의 §5-D 에 예외가 하나 필요하다.** 현재 `registry_rejected` 는 제출 필터에
걸린다(레지스트리가 준 답이 되돌아가는 echo 라서). 그러나 **우회 통보는 echo 가
아니라 새 사실**이다 — "당신 판정이 우회됐다"는 정보는 레지스트리에게 없다.

> `override` 필드가 있으면 `registry_rejected` 도 제출한다.

### 10-7. 합의가 필요한 항목

| # | 항목 | 누가 |
|---|---|---|
| 1 | §10-2 등급별 우회 경로 채택 여부 | 3자 |
| 2 | `malicious` 우회 불가에 동의하는가 | 3자 |
| 3 | 승인자 지정 대상(`registry_rejected` 신선) | 기관 |
| 4 | `override` 봉투 필드 수용 + §5-D 예외 | **레지스트리** |
| 5 | 우회 만료 7일 · 프로젝트 단위 | 3자 |
| 6 | 사설 저장소 내부 패키지 접두사 목록 | 기관 |

## 11. gvskb 가 보장하는 것 / 보장하지 않는 것

| 보장한다 | 보장하지 않는다 |
|---|---|
| 위 §2 필드를 항상 채워 반환한다 | 판정이 완전하다는 것 |
| `checked=false` 를 '안전'으로 표시하지 않는다 | 미검사 패키지가 안전하다는 것 |
| 로컬 악성·KEV 대조를 어떤 경로에서도 생략하지 않는다 | 로컬 캐시가 최신이라는 것 |
| 레지스트리 조회 실패를 `registry_status` 로 드러낸다 | 레지스트리가 응답한다는 것 |
| 잘린 검사를 `truncated_count` 로 드러낸다 | 전부 검사했다는 것 |

**하네스는 오른쪽 열을 전제하면 안 된다.** 왼쪽 열은 필드가 정직하다는 약속이지
결과가 완전하다는 약속이 아니다.
