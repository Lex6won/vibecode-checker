## 0. 결론 세 줄

1. **귀측 §8-1(라이선스 민간 SI 경로) 미결이 해소됐습니다.** LICENSE에 수급사업자 사용 추가 허가를 부기했습니다. 동시에 **저희가 2라운드에 쓴 문장 하나를 정정합니다**(§1).
2. **착수 전에 합의가 필요한 신규 요구가 1건 생겼습니다 — 배치 조회·제출 API**(§2). 귀측 §6에서 P1-4(락파일)를 2순위로 올렸는데, 단건 조회 전제로 만들면 양쪽 다 다시 갈아엎어야 합니다.
3. **저희가 2라운드 §2-2에서 낸 해법을 스스로 수정합니다**(§3). 원칙은 그대로이고 전달 방식만 바꿉니다. 그대로 만들면 **보안담당자 일이 폭증해 레지스트리 도입 목적과 정반대**가 됩니다.

이번 라운드의 판단 기준을 밝혀 둡니다. 세 가지를 동시에 만족하는 안만 제안했습니다.

- **공무원·보안담당자의 일이 늘지 않을 것**
- **보안 점검 성능이 지금보다 떨어지지 않을 것**
- **연동 시 양쪽 사용자 모두에게 이득일 것**

## 1. 라이선스 — 귀측 §8-1 해소 + 저희 문장 정정

### 1-1. 먼저 정정합니다

2라운드 §1-10-1에 저희가 이렇게 썼습니다.

> 막히는 것은 상업적 판매·**납품**입니다.

**이 문장의 "납품" 부분은 이제 사실이 아닙니다.** 쓸 당시에는 맞았습니다만, 귀측 §3-10-1 지적을 받아 라이선스에 예외를 부기했기 때문입니다.

| 항목 | 2라운드에 쓴 것 | 현재 사실 |
|---|---|---|
| 공공기관·교육기관·연구기관 직접 사용 | 허용 | 허용 (변동 없음) |
| **용역사·수급사업자가 계약 이행 목적으로 사용·납품** | **막힘** | **허용 — 변경됨** |
| 자기 명의 제품으로의 판매·번들 | 막힘 | 막힘 (변동 없음) |

### 1-2. 부기한 내용

`LICENSE` 파일에 **PolyForm Noncommercial License 1.0.0 본문 위**로 추가 허가를 넣었습니다. PolyForm 본문은 정본 그대로 보존했고, 추가 허가는 본문을 수정·재해석하지 않고 권리를 더하기만 합니다.

**허용** — 라이선스가 허용하는 조직(공공기관 등)의 계약·공공조달을 **수행하기 위해**, **계약 기간 동안**, 용역사·하수급사업자가 소프트웨어를 사용·수정·배포할 수 있습니다. 수정본을 발주기관에 납품하는 것도 포함됩니다.

**불허**

- 용역사가 **자기 명의로** 소프트웨어·파생물을 제품·서비스로 판매·라이선스·구독·번들 제공하는 것
- 계약 종료 후의 사용(기록 보존·감사 목적 보관은 예외)
- 라이선스가 허용하지 않는 조직을 위한 사용

### 1-3. 전달 시 주의 — 귀측 운영에 영향 있습니다

`Required Notice:` 행을 하나 추가했습니다.

PolyForm 규정상 수령자에게는 "약관 사본 **또는 URL**"만 주면 됩니다. 그런데 **URL만 전달하면 이 추가 허가는 따라가지 않습니다** — PolyForm 원문에는 없는 내용이기 때문입니다.

레지스트리가 이 도구를 내부 배포하거나 용역사에 안내하실 때는 **`LICENSE` 파일 전체를 함께 전달**해 주십시오. URL만 안내하면 용역사가 받는 권리가 달라집니다.

### 1-4. 귀측 §8-1 처리

미결 항목을 닫으셔도 됩니다. 계약·법무 확인이 여전히 필요하시면 그건 귀측 판단이지만, **저희 쪽 라이선스가 SI 경로를 막고 있던 상태는 해소**됐습니다.

행안부·국정원·NIA 워킹그룹 실증 사례 제안 건은 저희도 유의하겠습니다. 다만 이건 저희 라이선스 선택의 문제이므로 귀측 진행에 조건을 걸지 마십시오.

> 참고: 귀측이 지적하신 "PolyForm NC가 `vcps-rules.yaml`의 라이선스 목록 어디에도 없어 `unknown`이 된다"는 건은 저희가 **`license_review_required`에 등재**하는 방향으로 처리합니다. `license_allowlist`가 아닌 이유는, 그 목록의 정의가 "공공 활용 제약 적음"인데 PolyForm NC에는 상업 사용 제약이 실재하기 때문입니다. 자기 라이선스에만 관대한 목록은 저희가 §2-2에서 지적한 것과 같은 이중잣대가 됩니다.

## 2. 【신규 요구】 배치 조회·제출 API — 착수 전 합의 필요

### 2-1. 문제 — 두 문서가 각각은 맞는데 결합하면 성립하지 않습니다

귀측 §6에서 **P1-4(락파일)를 2순위로** 올리기로 합의했습니다. 그런데:

- 락파일의 패키지는 **수백~수천 건**입니다(그래서 커버리지 가치가 큰 것입니다)
- P0-1 조회는 v1 §4.3 기준 **패키지 1건당 GET 1회**입니다
- 귀측 §7-C는 **`UNDER_REVIEW`/`UNKNOWN`은 캐시하지 않음** — 도입 초기에는 대부분이 여기 해당합니다

`package-lock.json` 800건이면 레지스트리 GET 800회 + OSV 조회 800회입니다. 타임아웃 3초에 재시도까지 겹치면 검사 한 번이 분 단위가 되고, 그동안 귀측 서비스는 한 사용자의 검사 한 번으로 800요청을 받습니다.

참고로 저희 현재 `audit_manifest`의 `limit` 기본값은 **20**, 상한 **100**입니다(`src/gvskb/tools/check_package.py:457,480`). 락파일 지원은 이 상한 자체를 다시 설계하는 일입니다.

### 2-2. 요청

```http
POST /api/v1/packages/check-batch
POST /api/v1/packages/submit-batch
```

- 요청당 최대 건수를 정해 주십시오(저희 제안: 200건). 초과분은 저희가 나눠 보냅니다.
- 응답은 요청 순서와 무관하게 `purl` 로 대조할 수 있게 해 주십시오.
- 부분 실패를 허용해 주십시오 — 일부 항목이 실패해도 나머지는 반환. 전체 실패로 처리하면 fail-open이 통째로 발동해 조회 가치가 사라집니다.

### 2-3. 이것이 막지 않는 것 — 저희는 P1-4를 지금 시작합니다

락파일 **파싱**과 규모 처리는 배치 API에 막히지 않습니다(OSV 조회 800회는 저희 쪽 문제이기도 합니다). 그래서 착수는 하되, **내부 인터페이스를 처음부터 배치 형태로 설계**하겠습니다. 그러면 나중에 배치 API가 드롭인으로 붙습니다.

단건 반복 구조로 만들어 두고 나중에 고치는 상황만 피하면 됩니다.

### 2-4. 부수 협의 — rate limit

저희가 조회와 자체 분석을 **병렬로** 돌릴 계획입니다(§9). 직렬이면 지연이 조회+분석의 합이 되어 "조회가 자체 분석보다 느리면 의미 없다"는 v1 §4.2의 취지에 어긋납니다.

병렬화로 동시 요청 수가 늘어나므로, **클라이언트 1대당 동시 요청 상한과 rate limit 값**을 알려 주십시오. 저희가 그 값에 맞춰 조절하겠습니다.

## 3. 【정정】 저희 2라운드 §2-2 해법을 수정합니다

### 3-1. 원칙은 그대로입니다

귀측이 저희 문장을 내부 문서에 인용하시겠다고 했습니다.

> `unreachable`을 조용히 넘기면 '레지스트리가 승인했다'와 '물어보지 못했다'가 화면에서 구분되지 않는다

**이 원칙은 유지합니다.** 바꾸는 것은 **전달 방식**이지 조용히 넘기겠다는 뜻이 아닙니다.

### 3-2. 문제 — 저희 해법이 담당자 일을 폭증시킵니다

저희가 제안한 "조회 실패 시 `requires_review=True`"를 그대로 만들면, 레지스트리 장애 중에 락파일 800건을 검사할 때 **검토 항목 800개**가 한꺼번에 생깁니다. 사유는 전부 같은 하나("레지스트리가 안 됨")인데 화면에는 800줄로 나타납니다.

담당자는 곧 이걸 무시하게 되고, 무시가 습관이 되면 **그 사이에 낀 진짜 위험도 함께 묻힙니다.** 경고 피로는 그 자체로 탐지력 저하입니다. 레지스트리 도입 목적이 "중복 심사를 없애 담당자 일을 줄이는 것"인데 정반대가 됩니다.

### 3-3. 수정안 — 열화 신호의 계층 분리

> **시스템 수준 열화는 시스템 수준으로 한 번만 말하고, 패키지 수준 판정만 패키지별로 말한다.**

| 열화 | 2라운드 합의안 | 수정안 |
|---|---|---|
| 레지스트리 도달 실패 | 패키지마다 `requires_review=True` | **보고서 배너 1개** + 패키지는 자체 분석 결과 그대로 |
| 인텔 캐시 낡음 | (미정) | **보고서 배너 1개** + `checked=False` 표시 |
| 개별 패키지 판정 불가 | `requires_review=True` | **유지** — 이건 진짜 패키지 문제 |

`registry_status: "ok" | "unreachable" | "unauthorized" | "disabled"` 필드는 **합의대로 그대로 둡니다.** 다만 그 값이 자동으로 `requires_review`를 켜지 않게 합니다. 담당자가 받는 조치는 "레지스트리 복구" 1건이지 800건이 아닙니다.

이 논리는 저희가 인텔 갱신 워크플로 상태 게이트에서 이미 쓰고 있습니다 — 사용자가 매일 받는 번들 배포 실패만 빨간불, 룰 PR 처리 실패는 경고 한 줄. **조치 단위가 다르면 알림 단위도 달라야 합니다.**

## 4. `registry_approved` 부여 규칙 확정 — 캐시 신선도 분기

### 4-1. 합의한 조건에 구멍이 있습니다

2라운드에서 저희가 걸고 귀측이 수용한 조건은 "로컬 인텔 캐시 대조를 통과하면"이었습니다. 그런데 **캐시가 비었거나 낡았으면 '통과'가 아니라 '판정 불가'** 입니다.

저희 오프라인 경로는 이미 이걸 구분합니다 — 캐시가 비면 `verdict=unknown`, `requires_review=True`로 두고 "`gvskb update-intel`을 먼저 실행하라"고 안내합니다(`check_package.py:300` 부근).

캐시가 빈 상태에서 `registry_approved` + `requires_review=False`를 주면, **저희가 §2-1에서 지적한 조용한 초록불이 그대로 재현됩니다.**

### 4-2. 3분기 규칙

```
레지스트리 APPROVED
 ├ 인텔 캐시 신선 + 악성·KEV 미적중
 │    → registry_approved / checked=True  / requires_review=False
 │
 ├ 인텔 캐시 신선 + 적중
 │    → malicious · vulnerable 이 이김 (합의된 사다리)
 │
 └ 인텔 캐시 낡음·없음
      → registry_approved / checked=False / requires_review=False
        + 보고서 배너 "인텔 캐시 N일 경과 — 번들 반입 필요"
        + cache_stale_sources 에 근거 기록
        + 경과가 임계(저희 제안: 30일) 초과 시 requires_review=True
```

세 번째 분기가 절충점입니다. 캐시가 낡은 것은 **번들 반입 한 번으로 풀리는 시스템 문제**라 패키지 수백 건을 개인 검토로 올릴 일이 아닙니다. 대신 `checked=False`로 정직하게 표시하고, 무한정 봐주지 않도록 상한을 둡니다.

임계값 30일은 저희 제안이며, 귀측 운영 기준이 있으면 맞추겠습니다.

### 4-3. `checked` 값 — v1 합의를 정정해야 합니다

v1 §4.4는 `registry_approved`일 때 `checked: False`("이번에 검사하지 않았음") 고정이었습니다. 그런데 새 조건에서는 **로컬 대조를 실제로 수행**하므로 그 고정은 사실과 다릅니다.

`checked`는 저희 도구가 사용자에게 "검사함 vs 안 함"을 구분해 보여주는 축이라 틀리면 안 됩니다. 위 3분기대로 캐시가 신선하면 `True`, 아니면 `False`로 갈립니다.

**귀측 확인 요청**: `checked`를 조건으로 쓰는 로직이 레지스트리 쪽에 있으면 함께 조정이 필요합니다. 저장 스키마 자체는 그대로입니다.

## 5. 제출에 `source_scope` 추가 — 귀측 심사 대기열 보호

### 5-1. 문제

락파일 지원이 들어가면 한 번 검사에 수백~수천 건이 제출됩니다. 그게 그대로 심사 대기열에 쌓이면 **보안담당자 일이 폭증**합니다. 귀측 §1이 내건 "N명이 같은 패키지를 재심사하지 않게 한다"는 목적과 정반대 방향입니다.

v1 §4.6의 필터(`unknown`/`error`/`version is None` 제외)는 유효하지만, 락파일 유래는 **버전이 정확히 고정돼 있어 필터를 통과합니다.** 24시간 중복 억제도 첫 스캔에는 효과가 없습니다.

### 5-2. 요청

봉투에 필드 하나를 추가하겠습니다.

```json
{
  "result":       { "...PackageCheckResult.model_dump(mode=\"json\") 그대로..." },
  "caller":       "harness:auto",
  "submitted_at": "2026-08-01T05:00:00Z",
  "client":       "gvskb/0.3.0",
  "source_scope": "single" | "manifest" | "lockfile"
}
```

| 값 | 의미 | 레지스트리 처리 제안 |
|---|---|---|
| `single` | 사람이 `check_package`로 직접 물어봄 | **심사 큐에 투입** |
| `manifest` | 매니페스트 검사 유래 | 관측 데이터로 적재, 큐 투입은 정책에 따라 |
| `lockfile` | 락파일 전수 검사 유래 | **관측 데이터로만 적재, 큐 자동 투입 금지** |

"사람이 실제로 물어본 것"만 심사 대기열에 올라가면 담당자의 큐가 의미를 유지합니다. 저희 쪽에서도 로컬 제출 이력으로 동일 결과 재제출을 억제하겠습니다.

## 6. `REJECTED` 캐시 — 만료를 삭제가 아니라 강등으로

귀측 §7-C의 TTL 권고를 두 가지 조정 제안합니다.

| 상태 | 귀측 권고 | 저희 제안 | 근거 |
|---|---|---|---|
| `REJECTED` | 24시간 | **7일 + 만료 시 삭제하지 않고 강등** | 24시간 넘긴 장애에서 차단이 조용히 풀립니다 |
| `APPROVED` | 1시간 | **그대로 1시간** | 철회 전파 지연을 줄이려는 취지에 동의합니다 |
| `UNDER_REVIEW`/`UNKNOWN` | 캐시 안 함 | **그대로** | 자체 분석으로 진행하면 됩니다 |

**만료 = 삭제가 아니라 강등**이라는 게 핵심입니다. TTL이 지나도 "이전에 차단됐던 패키지"라는 사실은 지우지 않고 신선도만 낮춰 계속 표시합니다. 차단 사실이 사라지는 것과 오래된 것은 다릅니다.

귀측 §8-3(TTL을 응답 헤더로 내려줄지 검토)이 도입되면 헤더 값을 따르겠습니다. 그때까지는 위 값을 클라이언트 기본값으로 쓰겠습니다.

## 7. `engine_commit` 위치 — 확정 필요

귀측 §7-B는 "`result` **안에** `engine_version`과 별도로 `engine_commit`을 실어 달라"고 하셨습니다. 두 가지를 짚습니다.

**(a) 위치.** `result`는 §7-A에서 "변환 없이 원본"으로 정했습니다. `result` 안에 새 필드를 넣으려면 `PackageCheckResult` **스키마 변경**이 필요합니다. `caller`를 봉투로 뺀 논리를 그대로 적용하면 `engine_commit`도 봉투(`client` 옆)가 자연스럽습니다. 다만 `engine_version`이 이미 모델 필드라 모델에 두자는 주장도 성립합니다. **저희는 봉투를 선호하나 귀측 판단에 따르겠습니다.**

**(b) 값을 어떻게 얻는가 — 이게 더 중요합니다.** 저희 버전은 `src/gvskb/__init__.py`의 정적 상수이고 **배포본에는 git 메타데이터가 없습니다.** 빌드 시점 주입 장치를 만들지 않으면 대부분의 설치본에서 `engine_commit`이 `null`이 되어, 재현성이라는 목적을 달성하지 못합니다.

- 당분간 **`null` 허용**(값이 확정되는 환경에서만 채움)으로 두고,
- 빌드 시점 주입은 별도 과제로 진행하겠습니다.

`null`이 감사 요건상 허용되지 않는다면 알려 주십시오 — 그러면 주입 장치를 선행 과제로 올리겠습니다.

## 8. 귀측 자진 보고에 대하여

귀측 §2-1에서 서버의 `expires_at` 미검증과 철회 경로 부재를 스스로 밝히셨습니다. 지적을 방어하지 않고 자기 코드를 확인해 공개하신 판단에 감사드립니다.

다만 저희는 그 저장소에 접근할 수 없으므로, **검증한 사실이 아니라 귀측 보고로 기록**합니다. 저희 작업 원칙상 원본에서 확인하지 않은 것을 판정으로 적지 않습니다. 귀측 문서를 그대로 인용할 때도 같은 표기를 유지하겠습니다.

§4-1 결론(양쪽 다 검사)에 동의합니다. **클라이언트 검사를 유지하라**는 권고를 받아들여 저희 쪽 `expires_at` 검증을 구현하겠습니다.

| 7 | verdict 2종 + 3분기 규칙 | 대기 | §4 합의 후 |
| 8 | 플러그인 본체 | 대기 | 배치 API 개설 후 |

### 시크릿 패턴 — 확인해 보니 실제 구멍이 있었습니다

귀측이 §4-2에서 API 키 형식(`sk_ggtrust_[A-Za-z0-9]{32}`)을 주셔서 저희 룰을 대조했습니다.

- 현재 패턴은 `sk-[A-Za-z0-9_-]{20,}` — **하이픈**이라 `sk_ggtrust_…`(**언더스코어**)를 잡지 못합니다.
- 더 문제인 것은 **마스킹 함수**입니다. `sk-`만 가리므로, **귀측 토큰이 로그나 오류 메시지에 섞이면 마스킹되지 않고 그대로 출력됩니다.**

`sk[-_][A-Za-z0-9_-]{20,}`로 **일반화**하겠습니다. 기관 특정 문자열(`sk_ggtrust_`)을 내장 룰에 박지 않는 이유는 범용 도구 성격을 지키기 위함이며, 일반화하면 Stripe·OpenAI의 `sk-`, 귀측의 `sk_`, 다른 `sk_` 계열을 함께 덮습니다.

### `caller` 값 규칙 — 수용, 단서 한 줄

`<출처>:<모드>[:부서코드]`, 개인 식별자 금지 — 좋은 기준입니다. 그대로 안내 문구에 쓰겠습니다.

다만 **소규모 부서에서는 부서코드 + 시각 + 패키지 조합이 개인으로 좁혀질 수 있습니다.** 부서코드는 선택 항목으로 두고, 안내에 이 점을 적겠습니다.
