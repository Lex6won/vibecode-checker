1. 도구의 주장을 그대로 옮기지 말 것 — **원본에서 확인한 것만 판정으로 기록**

4. 실패는 올바른 곳에서 — **조용한 초록불이 빨간불보다 위험하다**

## 이 프로젝트가 반복해서 배운 것

연혁을 관통하는 실패 유형입니다. 새 결함을 만나면 먼저 여기에 해당하는지 봅니다.

| 유형 | 사례 | 왜 위험한가 |
|---|---|---|
| **조용한 초록불** | BOM 결함(AST 엔진이 꺼짐) · KEV 캐시 의존 은폐 · 결론 박스가 의존성 무시 | 도구는 정상으로 보이고 사용자는 안전하다고 믿는다. 빨간불보다 위험 |
| **오탐 방지가 탐지를 죽임** | `*.min.js` 제외가 `xlsx` CVE 를 가림 | 노이즈를 줄이려는 조치는 항상 "무엇을 못 보게 되는가"를 함께 물어야 한다 |
| **부분 완료로 닫은 백로그** | "wheel·venv·min.js" 중 앞 둘만 | 복합 항목은 쪼개고, 항목마다 검증 케이스를 건다 |
| **알림 단위 ≠ 조치 단위** | 컴포넌트 중복 계상 · 캐시 열화를 패키지마다 표시 | 경고 피로가 진짜 위험을 묻는다 |
| **주석·문서에만 있는 안전장치** | `_kev_cve_hits` 주석 · 3자구조 문서의 신선도 규칙 | 코드가 강제하지 않으면 없는 것과 같다 |
| **도구 결함이 사용자 잘못처럼 보임** | npm `unparsed` → "형식을 확인하세요" | 사용자가 고칠 수 없는 것을 고치라고 하면 신뢰를 잃는다 |

## 갱신 방법

1. **커밋할 때 함께 갱신합니다**(작업 원칙 8). 작업이 끝날 때가 아닙니다.
2. 국면이 바뀔 만한 전환(목표·구조·관계의 변화)이 있으면 새 절을 엽니다.
   개별 변경은 `CHANGELOG.md`, 검증 라운드는 `검증이력_상용툴비교.md` 로 갑니다.
3. **틀렸던 판단을 지우지 않습니다.** 정정할 때는 원래 기록을 남기고 그 아래에
   무엇이 어떻게 틀렸는지 적습니다(예: 라운드1의 `app.py:892` 줄번호 정정).
4. 머리말 표(문서 버전·최종 갱신·커밋·테스트 수)를 함께 고칩니다.
