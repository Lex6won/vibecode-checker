## 0. 고정 범위 (변하지 않는 것)

- 지원 언어: Python · JavaScript · TypeScript. 생태계: PyPI · npm.
- 검사 대상: 개발 소스와 그 소스의 PyPI/npm 의존성. 서버·호스트·네트워크 장비·운영 제품·컨테이너·OS 패키지·다른 생태계·CPE 자산 검색은 **추가하지 않았다**.
- 역할 구분: **OSV 가 주 근거**(패키지·영향 버전). NVD·KNVD 는 정확한 CVE 번호가 일치할 때만 보조 정보. 이름·제품명 유사도, 부분 문자열, CPE 변환 매칭은 없다.
- NVD·KNVD 로 verdict·severity·requires_review·게이트 판정은 바뀌지 않는다. 외부 인텔로 탐지 규칙을 자동 생성·활성화하지 않는다.
- scan · check-package · 보고서 생성 중에는 NVD·KNVD 에 접속하지 않는다. GitHub Actions 가 미리 받아 검증된 로컬 캐시만 읽는다.

## 1. 변경 전 문제와 재현

### 1-2. GitHub Actions 누적 실패 (P0)

`.github/workflows/update-intel.yml` 이 매 실행 `${{ github.workspace }}/.gvskb-cache` 빈 폴더에서 시작했다. 이전 `intel-latest` 번들을 내려받아 반입하는 단계가 없었으므로 `update.py` 의 `merge()` 가 있어도 `prev` 는 항상 `None` 이었다. NVD(7일 창)·EPSS(1일 창)의 "누적" 은 코드에만 존재했고 배포본에는 한 번도 반영되지 않았다. KNVD 피드가 최신 10건만 주므로 같은 구조로는 과거 공지가 매일 사라진다.

## 2. 구현

### 2-1. NVD 전 페이지 수집 (`nvd.py`)

- `startIndex=0` 부터 순차 순회. 매 페이지 `resultsPerPage`·`startIndex`·`totalResults` 를 음이 아닌 정수로 검증하고, 응답 `startIndex` 가 요청과 다르면 실패.
- 순회 중 `totalResults` 가 바뀌면 실패(이번 실행 미저장, 다음 날 재시도). 같은 `startIndex` 반복·빈 페이지·`resultsPerPage`≠실제 항목 수·페이지 상한(200) 초과도 실패.
- 마지막 페이지까지 끝나고 수집 건수 == `totalResults` 일 때만 반환. 그 전의 어떤 실패도 `NvdFetchError` → 오케스트레이터가 이전 캐시를 그대로 둔다(부분 저장 없음).
- 429: `Retry-After`(상한 120초) 또는 제한 지수 백오프(6·12·24초). 5xx·네트워크 예외: 최대 3회 재시도. 그 외 4xx: 즉시 실패.
- 간격: 키 없음 6초, 키 있음 0.6초(공식 안내 5회/30초 · 50회/30초 기준). `NVD_API_KEY` 는 `apiKey` 헤더로만 보내고 URL·로그·예외 문구에서 마스킹.
- 정규화 범위: CVE ID · published · lastModified · vulnStatus · CWE · CVSS 3.1(점수·등급·**제공 주체 `cvss31_source`**, NIST Primary 우선). 설명문(600자)·CPE·configurations 는 담지 않는다(소비자 없음, 번들 크기). CVSS v4·SSVC 는 이번에 넣지 않았다.
- 중복 CVE 는 `lastModified` 최신 항목. `merge_nvd` 도 같은 규칙 — 나중에 Rejected 로 바뀐 CVE 는 새 `lastModified` 로 들어와 상태가 갱신된다. 소비자(`_enrich_with_epss_nvd`)는 `is_rejected()` 인 항목의 점수를 병기하지 않는다.

공식 API 제한 재확인: `https://nvd.nist.gov/developers/start-here` 는 자동화 요청에 403/빈 페이지(JS 렌더링)로 응답해 이번 작업에서 **원문을 직접 다시 읽지 못했다**. 적용한 값(페이지 상한 2,000 · 창 최대 120일 · 키 없음 5요청/30초 · 키 있음 50요청/30초 · 요청 간 6초 권고)은 NVD 가 공개해 온 값이며, 실제 응답(`resultsPerPage=1` 요청이 그대로 반영됨, 2,000 상한)과 모순되지 않았다. 운영자는 브라우저로 한 번 대조하기 바란다.

### 2-2. KNVD 공식 RSS (`knvd.py`)

| source_id | URL | 실접속(2026-09-13) |
|---|---|---|
| `knvd-security-notice` | https://knvd.krcert.or.kr/rss/security/notice | HTTP 200, text/xml;charset=UTF-8, 143,989B, item 10건 |
| `knvd-public-vuln` | https://knvd.krcert.or.kr/rss/security/info | HTTP 200, text/xml;charset=UTF-8, 17,193B, item 10건 |

- 저장: 제목·공식 링크·guid·게시 시각(UTC ISO)·정확히 추출한 CVE ID(`CVE-\d{4}-\d{4,7}` 완전 일치)·CWE ID·500자 이내 일반 텍스트 요약·원본 피드 URL.
- 보안: 응답 5MB 상한, `<!DOCTYPE`/`<!ENTITY` 포함 XML 거부, 최종 URL 이 `https://knvd.krcert.or.kr` 이 아니면 실패(3xx 도 실패 — 리다이렉트를 따라가지 않음), 링크가 공식 호스트가 아닌 항목은 저장하지 않음, 제목·설명은 태그·마크다운 링크를 벗긴 일반 텍스트(보고서는 `_esc` 로 이스케이프), 링크 기준 중복 제거, 캐시 상한 5,000건(최신 게시물 우선).
- 금지 준수: SPA 스크래핑·JS 번들 분석·비공개 API·우회·화면 셀렉터 없음.
- **한계**: 각 피드는 현재 최신 10건만 제공한다. 캐시는 누적분이며 **KNVD 전체 DB 가 아니다**. 누적 시작 이전 공지는 없다. 이 문구를 어댑터 설명·Job Summary·릴리스 노트·README 에 적었다.
- 실제 피드 원본은 `tests/fixtures/knvd_public_vuln_2026-09-13.xml` 로 고정해 형식 변화를 감지한다.

### 2-3. KNVD 를 판정에 연결하는 방법 (`check_package.py`, `intel/lookup.py`)

조건 세 가지가 모두 맞을 때만 OSV advisory 행에 붙는다: ① OSV 가 PyPI/npm 패키지의 취약점·영향 버전을 확인했고 ② 그 항목에 정확한 CVE alias 가 있고 ③ KNVD 항목에 같은 CVE ID 가 있다. `match_method` 는 `exact_cve` 하나.

증적 구조(advisory 행의 `knvd_notices[]`, 키는 항상 존재·없으면 빈 목록):

```json
{"source": "KNVD", "source_id": "knvd-public-vuln", "source_url": "https://knvd.krcert.or.kr/…",
 "cve_id": "CVE-2026-11111", "title": "…", "published_at": "2026-09-07T01:00:00+00:00",
 "fetched_at": "2026-09-13T…", "match_method": "exact_cve"}
```

온라인·오프라인 두 경로 모두 `_advisory_rows()` 직후 `_attach_knvd_evidence()` 를 부른다. 사용된 KNVD source_id 는 `cache_sources_used` 에 기록된다. 보고서(HTML/MD)는 advisory 아래 "↳ KISA 보안공지(CVE, 날짜): 제목" 줄과 HTTPS 링크만 싣는다(advisory 당 2건 상한).

인덱스: `intel/lookup.py` 가 NVD·EPSS·KNVD 의 CVE 인덱스를 캐시 파일의 `(source_id, sha256)` 별로 한 번만 만든다. 조회는 dict. 예전 `_enrich_with_epss_nvd` 는 호출마다 NVD 전체로 dict 를 새로 만들었다(5만 건 × 패키지 수).

### 2-4. 이전 번들 복원 (`update-intel.yml`)

순서: checkout → 설치 → **이전 intel-latest 다운로드 → `sha256sum -c` → `gvskb intel-bundle import`** → 수집(`--json` 결과 파일, 종료 코드 보존) → `scripts/intel_summary.py` 로 소스별 상태표(Job Summary) → export → artifact → rolling release(노트에 상태표 포함) → 룰 PR → 최종 게이트.

| 상황 | 동작 |
|---|---|
| 이전 릴리스/자산 없음 | `state=bootstrap` 으로 명시하고 빈 캐시에서 시작 |
| sha256 불일치 또는 반입 거부 | `state=corrupt`, 잡 중단, **새 번들 미게시** |
| NVD 페이지 일부 실패 | 어댑터 예외 → 이전 NVD 캐시 보존(warn) |
| 한 소스 실패 | 그 소스만 마지막 정상본 유지, 나머지 정상 갱신, 번들 게시, 경고 |
| 정상본 없는 실패(error) | 번들 게시 후 게이트 빨간불 |
| 같은 소스 연속 실패 | 캐시 나이 > `MAX_SOURCE_AGE_DAYS`(3일) 이면 게이트 빨간불 |
| 스케줄·수동 동시 실행 | `concurrency: update-intel`, 취소 없이 직렬화 |

cron `17 18 * * *`(03:17 KST, 정각 회피). 권한: 워크플로 기본 `contents: read`, refresh 잡만 `contents: write`(릴리스 자산). PR 은 `INTEL_PR_TOKEN`(PAT)이 만들므로 `pull-requests: write` 는 제거. Actions cache 는 쓰지 않는다(보존 수단 = 릴리스 자산 + 실행별 artifact 30일).

커버리지 기록: `intel_summary.py` 가 소스별 항목 수·수집 시각·나이·커버리지 범위(NVD `lastModified`, EPSS `date`, KEV `dateAdded`, OSV `modified`, KNVD `published_at` 의 min~max)를 표로 남긴다. 누적 시작일은 별도 상태로 저장하지 않는다 — 범위 최솟값이 캐시에 남은 가장 오래된 데이터다.

부수 수정: `intel/bundle.py` 가 압축 스트림 손상(`zlib.error` 등)을 예외로 흘렸다. 테스트에서 번들 중간 바이트를 뒤집자 `import_bundle` 이 크래시했고, 같은 경로가 사용자 PC 의 자동 당김(autopull)에서 서버 기동을 멈출 수 있었다. 이제 "손상 — 반입 전체 중단" 으로 거부한다.

- `test_knvd_cache_adds_link_but_never_changes_verdict_or_gate` — KNVD 캐시 전/후로 `verdict · verdict_severity · requires_review · max_cve · in_kev · vulnerability_count · recommended_version · is_malicious_package · checked` 가 같고, `gate_status()` 결과 dict 전체가 같다. 링크는 정확히 1건 붙는다.
- `test_unrelated_knvd_notices_do_not_attach_or_affect_result` — Gitea·ipTIME 공지(다른 CVE)는 붙지 않고 판정도 같다.
- `test_osv_entry_without_cve_alias_never_gets_knvd_notice` — 제목에 패키지명이 있어도 CVE alias 가 없으면 붙지 않는다.
- `test_scan_and_offline_check_never_touch_network` — `httpx.Client`/`AsyncClient` 생성을 예외로 만들어도 scan·offline check-package 가 동작한다.
- `test_rejected_nvd_cve_is_not_used_as_cvss_evidence`.

## 6. 실패 시 동작 요약

- NVD: 페이지 하나라도 실패 → 이번 실행 미저장, 이전 캐시 유지, `warn`(정상본 있음) / `error`(정상본 없음).
- KNVD: HTTP≠200·비공식 최종 URL·DTD·크기 초과·XML 오류 → 미저장, 이전 캐시 유지.
- 잡: 이전 번들 손상 → 게시 안 함. 소스 warn → 게시 + 경고. error 또는 나이 초과 → 게시 + 빨간불.
- 사용자 PC: `import_bundle` 은 manifest·파일 sha256 전수 검증 + 압축 손상 거부. 실패해도 검사는 계속되고 결과에 낡음이 표시된다.

## 7. 운영자 설정

- `NVD_API_KEY` (repository secret): 없어도 동작하지만 페이지 간 6초 대기 → 7일 창 4페이지 기준 약 20초. 키가 있으면 0.6초. 키는 헤더로만 전송되고 로그에 남지 않는다. 발급: https://nvd.nist.gov/developers/request-an-api-key
- `INTEL_PR_TOKEN` (기존): KEV proposed 룰 PR 용 PAT. 없으면 번들은 정상, 룰 PR 만 경고.
- `MAX_SOURCE_AGE_DAYS` (workflow env, 기본 3): 연속 실패 승격 기준.

## 8. 병합 후 workflow_dispatch 확인 절차

Scheduled workflow 는 기본 브랜치에서만 돈다. 로컬 테스트는 GitHub 위의 실행을 증명하지 못한다.

1. 브랜치를 `main` 에 병합한다.
2. Actions → update-intel → Run workflow(sources=all).
3. Job Summary 에서 확인: "복원한 이전 번들" 표(첫 실행이면 `bootstrap`), "이번 실행 후 인텔 소스 상태" 표에서 `nvd-recent` 항목 수가 이전보다 커졌는지(7일 창 ≈ 7천 건), `knvd-*` 각 10건, 모든 소스 `✅ ok`.
4. 릴리스 `intel-latest` 노트에 상태표와 "누적 방식: … 복원(restored)" 문구가 있는지.
5. 다음 날 스케줄 실행 후 `nvd-recent` 커버리지 범위 최솟값이 유지되고 항목 수가 증가했는지(누적 확인).
6. 실패 시나리오 점검(선택): 시크릿 `NVD_API_KEY` 를 잠시 비우고 수동 실행 → 6초 간격으로도 전 페이지 수집되는지.

## 9. 남은 한계

- KNVD 는 최신 10건 피드의 누적분이다. 과거 공지·전체 DB 를 대체하지 않는다.
- NVD 순회 중 `totalResults` 가 바뀌면 그날 갱신을 건너뛴다(다음 날 재시도). 7일 창이라 누락 위험은 낮다.
- NVD 캐시 상한 5만 건(약 7주). 그 이전 CVE 의 CVSS 는 캐시에 없다 — 판정은 OSV 가 하므로 영향은 "점수 병기 없음" 뿐이다.
- CVSS v4·SSVC 미수집. 필요해지면 보고용 보조 필드로만 추가한다.
- NVD 개발자 문서 원문을 자동화로 재확인하지 못했다(2-1 참조).
- GitHub 실운영(복원·게시·PR)은 병합 후 수동 실행으로 확인해야 한다.
- 포털 골든 fixture 는 의존성 감사 데이터를 고정 입력으로 쓰므로 이번 `knvd_notices` 추가에 영향받지 않았다(재생성 대조 통과, dirty 항목만 예상대로 실패). 포털이 체커 핀을 올릴 때는 기존 절차대로 fixture 를 재생성한다.
