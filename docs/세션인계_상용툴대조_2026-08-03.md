## 검증해야 할 단서 (★ 가설 — 확인 전까지 결론으로 쓰지 말 것)

### ★★ 1순위: 우리가 오탐 방지로 제외한 파일에서 Sparrow가 실제 취약점을 찾았다

gvskb 리포트 "빌드 산출물 제외" 항목:
```
> 압축/번들·빌드 출력 디렉터리는 원본 소스가 아니므로 검사하지 않습니다 (오탐 방지).
- disaster-response/static/qrcode.min.js
- disaster-response/static/xlsx.full.min.js
```

Sparrow가 **정확히 이 두 파일에서** 찾은 것:
- `static/xlsx.full.min.js` → 컴포넌트 `xlsx 0.18.5`
  - `CVE-2023-30533` Prototype Pollution (HIGH/HIGH/HIGH)
  - `CVE-2024-22363` ReDoS
  - `GHSA-4r6h-8v6p-xvw6`, `GHSA-5pgg-2g8v-p4x9`
  - 조치방안: "검색된 조치 방안이 없습니다" — **npm에 패치 버전이 없음**(SheetJS가 npm 배포 중단)
- `static/qrcode.min.js` → `Cuckoo` 컴포넌트 다수, **GPL-3.0-only (매우 높음)** 라이선스

**확인할 것**: 이 두 파일이 실제로 벤더 라이브러리인지(파일 크기 881KB/19KB, 수정일 동일),
그리고 우리 제외 규칙이 어디서 걸었는지(`scanner.py` 의 빌드 산출물 판정).

**함의(가설)**: 우리 도구에는 **벤더링된 프런트엔드 JS 의 컴포넌트 식별(SCA) 경로가 없다.**
`--check-deps` 는 매니페스트·설치본만 본다. `static/` 에 직접 떨궈진 min.js 는
"빌드 산출물"로 제외돼 **아무도 안 본다** → 작업원칙 4 의 조용한 초록불.
오탐을 피하려던 규칙이 진짜 취약 컴포넌트를 가렸다면 이건 **설계 결함**이다.

### 2순위: Sparrow 오탐 후보 — 원본을 열어 확인할 것

우리 도구의 오탐과 **같은 기준**으로 판정할 것(작업원칙 2).

- `app.py:809, 892` "하드코드된 중요정보" → 리포트에 실린 소스는 `pw = ''`(빈 문자열 초기화).
  **빈 문자열을 하드코딩 비밀번호로 본 것이라면 오탐.** 원본 확인 필수.
- `app.py:638, 657, 1242` "신뢰되지 않은 URL 자동접속" → 전부 `redirect(url_for('응소완료', ...))`.
  `url_for()` 는 내부 엔드포인트명을 받는다. **사용자 입력이 URL로 흐르지 않으면 오탐.**
- `make_test_data.py:9` "적절하지 않은 난수값" → `import random` 자체를 잡았다.
  같은 파일 10행에 `import secrets` 도 있다. **테스트 데이터 생성 스크립트**이며
  보안 결정에 쓰이는지 확인할 것.
- nssm-2.24 C/C++ 45건 → **서드파티 설치 프로그램**. 우리가 고칠 코드가 아니다.
  "적용 범위" 문제이지 탐지력 문제가 아니라는 점을 기록할 것.

### 3순위: 우리가 찾고 Sparrow가 못 찾은 것

- `ssl/STAR.siheung.go.kr_key.pem` **RSA 개인키** — Sparrow 리포트 전체에서
  이 파일에 대한 발견이 보이지 않는다(확인할 것). 사실이라면 **기관 도메인 인증서
  개인키 유출**을 상용툴이 놓치고 우리만 잡은 것 — 공공 특화 룰의 실증.
- `.secret_key` (Flask 세션 키 평문)
- `.pem` 파일 자체를 검사 대상으로 삼는지

## 작업 원칙 (계속 적용)

1. 도구의 주장을 그대로 옮기지 말 것. **원본에서 확인한 것만 판정으로 기록**.
   접근할 수 없는 곳의 보고는 '그쪽 보고'로 표기
2. **우리 도구의 오탐도 상용 도구와 같은 기준으로 기록**
3. 과잉 교정 경계
4. 실패는 올바른 곳에서 — **조용한 초록불이 빨간불보다 위험**
5. **커밋·푸시는 명시적으로 요청할 때만**
6. 경고 피로는 탐지력 저하 — 조치 단위가 다르면 알림 단위도 다르게
7. 새 가드는 **변이 검사로 실제 실패하는지** 확인할 것
8. 기록은 작업 끝날 때가 아니라 **커밋할 때 같이** 갱신

추가로 이번 세션부터 적용 중인 원칙:

> **도구가 정하고 사용자는 코딩한다.** 개선안을 낼 때 사용자에게 판단을 넘기는
> 방향(옵션 추가·경고 증가)으로 가지 말 것. 규칙으로 정해 조용히 처리하고,
> 차단할 때만 "무엇을 하면 되는지" 한 줄로 말한다.
> 안 쓰이는 보안 도구는 보안 효과가 0이다.
