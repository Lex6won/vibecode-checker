# vibe_harness 변경 통지 — gvskb 신호 변경 (2026-08-03)

> **수신**: vibe_harness 개발
> **발신**: vibecode-checker(gvskb) 개발
> **작성일**: 2026-08-03
> **근거**: `하네스_집행계약.md`(합의서 §10) · `연동회신_gg-trusted-registry_2026-08-03_r6.md`
> **성격**: 집행계약 §2 가 정한 **신호 변경 통지**입니다.

**그쪽에서 고쳐야 할 것은 하나입니다**(§2). 나머지는 저희가 기본값을 정해
보내므로 읽고 넘기시면 됩니다.

## 1. 먼저 — 이 변경으로 사용자 화면이 복잡해지면 안 됩니다

필드가 늘었다고 사용자에게 보여 줄 것이 늘어나는 것은 아닙니다. **오히려
반대여야 합니다.**

공무원 사용자는 보안 판정을 읽으러 온 것이 아니라 코드를 만들러 왔습니다.
선택지와 설명이 늘면 어려워하고, 어려우면 도구를 끕니다. **안 쓰이는 보안 도구는
보안 효과가 0입니다.** 타이포스쿼팅을 절대 규칙에서 뺀 것(집행계약 §4-2)과 같은
이유입니다 — "하네스는 멀쩡한 걸 막는다"는 인상이 먼저 생기면 진짜 차단도 우회
대상이 됩니다.

아래 필드는 전부 **하네스가 판단하기 위한 값**이지 사용자에게 전달할 값이
아닙니다.

| | 사용자에게 |
|---|---|
| 통과 | **아무 말도 하지 않는다** |
| 차단 | **한 줄**: 무엇을 하면 되는지. 판정 근거·필드명·캐시 상태는 넣지 않는다 |
| 시스템 문제(레지스트리 도달 실패·인텔 캐시 없음) | **사용자에게 알리지 않는다** — 담당자 경로로 |
| 판정 불가(`unknown`·`item_failed`) | 모드에 따라 조용히 통과 또는 차단. **묻지 않는다** |

사용자에게 선택을 주는 지점은 **우회(override) 하나**로 좁혀 주십시오.

예시 — `kev_checked=false` 인 패키지를 차단할 때:

```
✗ "CISA KEV 캐시가 없어 in_kev=false 를 신뢰할 수 없습니다(kev_checked=false).
   intel_cache.state=missing 이며 …"
✓ "이 패키지는 지금 확인할 수 없어 설치를 보류했습니다. 담당자에게 문의하거나
   다른 패키지를 쓰세요."
```

## 2. ★ 고쳐야 할 것 하나 — 집행계약 §2-1 의 `in_kev` 규칙

계약 본문에 이렇게 적혀 있습니다.

> `in_kev` | bool | 단 **`cache_sources_used` 가 비어 있으면** `false` 는 '대조 못 함'

**의도는 옳지만 술어가 틀렸습니다.** gvskb 는 인텔 소스마다 따로 기록합니다.

```python
if osv_entry is not None:  cache_sources_used.append("osv-malicious")
if kev_entry is not None:  cache_sources_used.append("cisa-kev")
```

즉 **`["osv-malicious"]` — 비어 있지 않은데 KEV 대조는 되지 않은 상태**가 있습니다.
악성 피드는 반입했고 KEV 캐시는 아직 없는 경우이고, 망분리에서 인텔 번들을 부분
반입하면 드물지 않습니다.

| 실제 상태 | 계약 규칙대로면 | 옳은 판단 |
|---|---|---|
| KEV 캐시 없음 + 악성 피드 있음 | "대조했고 악용 없음" → **통과** | **대조 못 함** |

실제 악용 중인 패키지가 KEV 대조 없이 통과합니다. `intel_cache=missing` 이 아니라
'부분 반입'이라 §5-1 의 차단 규칙에도 걸리지 않습니다.

### 조치

```diff
- in_kev | bool | 단 `cache_sources_used` 가 비어 있으면 `false` 는 '대조 못 함'
+ in_kev      | bool | KEV 교차 일치 여부
+ kev_checked | bool | **false 면 in_kev=false 는 '악용 없음'이 아니라 '대조 못 함'**
```

레지스트리에도 같은 정정을 요청했습니다(회신 C-1).

## 3. 저희가 정해서 보내는 것 — 하네스는 읽기만 하면 됩니다

집행계약 §2 는 "새로 만들 것은 없다"고 적었는데 그 문장이 오늘부로 사실이
아닙니다. 늘어난 값은 아래 넷이며, **판단 규칙까지 저희가 붙여 보냅니다.**

| 필드 | 값 | 하네스의 처리 |
|---|---|---|
| `kev_checked` | bool | §2 |
| `version_exact` | bool | **`false` 면 차단 근거로 쓰지 않는다** — 아래 3-1 |
| `source_scope` | single·manifest·lockfile·installed | §4-0 의 근거값. **이제 모든 판정에 붙습니다** — 아래 3-2 |
| `registry_stale` | bool | `true` 면 낡은 차단(§3-2). 판정은 그대로 차단 |

`registry_status` enum 도 넓어졌습니다: `ok`·`unreachable`·**`rejected`**·
**`item_failed`**·`unauthorized`·`disabled`.

> **규칙**: `ok` 가 **아니면** 기관 판정 없음으로 처리하십시오. 값을 하나씩 나열해
> 다루면, 저희나 레지스트리가 값을 늘릴 때마다 모르는 값이 통과로 떨어집니다.

### 3-1. `version_exact` — 경계값만으로는 차단하지 않습니다

gvskb 파서가 매니페스트 제약 연산자를 버리고 있었습니다. `requests>=2.28` 을
**2.28 로 판정**했고, 실제로는 2.31.0 이 깔려 있어도 2.28 기준 취약점이 보고됐습니다.

경계값 검사 자체는 남깁니다 — "이 제약이 취약한 버전을 허용한다"도 실제 신호입니다.
다만 그것은 **관측이 아니라 가정**이므로 `version_exact=false` 로 표시합니다.

**규칙(저희가 정합니다)**: `version_exact=false` 인 판정만으로 설치를 막지 않습니다.
`pip`·`npm` 은 하한 제약에서 최신을 설치하므로 경계값이 실제로 깔리는 일은 드물고,
오탐 차단은 §4-2 가 경계한 그 인상("멀쩡한 걸 막는다")을 그대로 만듭니다.

절대 규칙(§3)은 그대로 적용해도 됩니다 — `not_found`(이름이 실재하지 않음)와
`malicious`(패키지 자체가 악성)는 버전과 무관한 진술입니다.

### 3-2. `source_scope` — §4-0 이 이제 실제로 동작합니다

집행계약 §4-0 은 `unknown` 차단을 `source_scope` 로 가릅니다(`single`·`manifest`는
차단, `lockfile`·`installed`는 차단하지 않음).

**그런데 이 필드는 어제까지 판정 결과에 없었습니다.** 레지스트리 제출 봉투를
만들 때 인자로만 존재했고, 하네스가 읽는 `PackageCheckResult` 에는 붙지 않았습니다.
계약대로 구현하려 하셨다면 읽을 값을 못 찾으셨을 것입니다.

오늘부로 **모든 판정에** 붙습니다. 그리고 설치본 인벤토리 안에서도 직접 의존성과
전이 의존성을 나눕니다(레지스트리 요청 §3).

```
설치 흔적 중 매니페스트에 이름이 있는 것 → manifest    ← §4-0 상 차단 대상
그 밖의 전이 의존성                      → installed
```

**하네스 입장에서는 ENFORCE 시 차단 대상이 늘어납니다.** 계약 §4-0 이 원래 의도한
범위이지 정책 변경은 아닙니다.

> **예외 하나**: MCP `scan_installed_packages` 를 단독 호출하면 전부 `installed` 로
> 옵니다. 그 도구는 매니페스트를 읽지 않아 직접 의존성을 가려낼 수 없습니다.
> 구분이 필요하면 `scan_path --check-deps --include-installed` 를 쓰십시오.

### 3-3. 판정 신선도 — 비대칭입니다

`3자구조` §8-1 이 통과·차단을 구분하지 않고 "1시간 이내의 것만 쓴다"고만 적어
충돌로 읽혔습니다. 비대칭으로 정정했습니다.

| 방향 | 신선도 미달 시 | 재호출이 실패하면 |
|---|---|---|
| **통과** | 재호출 | **통과시키지 않는다** |
| **차단** | 재호출 | **오래된 차단을 그대로 유지** |

느슨해지는 방향에는 신선도를 요구하고 엄격해지는 방향에는 요구하지 않습니다.
**집행계약 §3-2 가 우선이며, 기준값은 통과 방향 1시간입니다.** 운영해 보시고
맞지 않으면 그때 알려 주십시오 — 지금 정하실 필요 없습니다.

### 3-4. 집행계약 §3-2 의 'gvskb 측 보완 필요' — 해소됐습니다

낡은 차단(`stale`)의 안내가 신선한 차단과 같았던 문제입니다. 판정은 그대로
차단이고 안내만 갈립니다. `registry_stale` 로 읽을 수 있습니다.

사용자에게 보이는 문구는 **§1 의 원칙대로 한 줄**로 두십시오. "8일 전 차단",
"보관 기한 초과" 같은 내부 사정은 담당자 경로로 보내면 됩니다.

## 4. 알아만 두시면 되는 것 — npm 전이 의존성이 빠져 있었습니다

`--include-installed` 의 npm 경로가 깨져 있었습니다. 설치 목록을
`express==4.17.0`(requirements 형식)으로 만들어 놓고 npm(JSON)으로 파싱하려다 실패해
`verdict="unparsed"`·`parsed_count=0` 을 냈습니다(실측 확인).

**node_modules 에서 수집한 전이 의존성이 한 건도 검사되지 않았습니다.** 파이썬
쪽(`.venv`)은 정상이었습니다. 고쳤습니다.

**함의**: 지금까지 npm 프로젝트에서 전이 의존성 취약점이 보고된 적이 없습니다.
"전이 의존성까지 본다"는 적용 범위 주장이 npm 에서는 사실이 아니었습니다.
앞으로 npm 프로젝트의 판정 건수가 늘어납니다.

MONITOR 통계를 쌓고 계셨다면 §9-1 전환 기준(직접 의존성 `unknown` 비율)의 분모가
바뀝니다. 다만 **저희 쪽에서는 그쪽이 그동안 `source_scope` 를 어떻게 얻으셨는지
알 수 없으므로**, 재시작이 필요한지는 그쪽 데이터를 보고 판단해 주십시오.

## 5. 3자 확정 대기 — `override`

레지스트리가 구조화된 형식을 제안했고 저희도 동의했습니다.

```jsonc
"override": {
  "reason_code": "EMERGENCY_PATCH",   // 허용목록
  "approval_ref": "보안-2026-0173",   // 문서번호 — 사람 이름 아님
  "mode": "ENFORCE"
}
```

자유 문자열이면 "보안팀 ◯◯◯ 과장 승인"이 들어오고, 받은 뒤 개인정보만 골라내려
하면 탐지 규칙과의 술래잡기가 됩니다. **문법으로 막는 편이 확실합니다** —
`caller` 에서 저희가 겪은 것과 같습니다.

`reason_code` 목록 초안은 레지스트리가 만들기로 했습니다. **이 필드를 채우는 것은
하네스**이므로 집행계약 §10-4(우회 기록)와 맞춰 주십시오.

§1 에서 적었듯 **우회는 사용자에게 선택을 주는 유일한 지점**입니다. 그만큼 그
화면은 짧고 분명해야 합니다 — 사유를 자유 입력으로 받지 말고 목록에서 고르게
하십시오. 그러면 개인정보도 안 들어가고 사용자도 덜 고민합니다.

## 6. 확인 요청 — 하나뿐입니다

**§3-2 관련**: 그동안 §4-0(직접/전이 구분)을 어떻게 구현하고 계셨습니까?
`source_scope` 가 판정 결과에 없었으므로 다른 값으로 추론하셨을 텐데, 그 방법에
따라 오늘 변경이 기존 동작과 어긋날 수 있습니다.

(직결 구조 확인 — "하네스는 레지스트리를 직접 조회하지 않는다" — 은 `3자구조` §9-6
으로 이미 요청드린 상태이며 아직 회신 전입니다.)

## 7. 계약 본문에 미치는 영향

| 집행계약 절 | 변경 |
|---|---|
| §2 머리말 | "새로 만들 것은 없다" → 필드 4개 신설·enum 확장 |
| §2-1 | `in_kev` 행 **정정 필요**(§2) · 필드 4개 추가 · `registry_status` enum 확장 |
| §3-2 | 'gvskb 측 보완 필요' 각주 **해소** |
| §4-0 | 표는 그대로. **이제 실제로 동작합니다**(어제까지 근거값이 없었음) |
| §9-1 | 전환 기준 분모가 바뀜(§4) |

본문 개정은 3자 확인 후 일괄로 하겠습니다. 이견은 이 문서의 절 번호로 지목해
주십시오.
