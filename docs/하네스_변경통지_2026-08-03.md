# vibe_harness 변경 통지 — gvskb 신호 변경 (2026-08-03)

> **수신**: vibe_harness 개발
> **발신**: vibecode-checker(gvskb) 개발
> **작성일**: 2026-08-03
> **근거 문서**: `하네스_집행계약.md`(합의서 §10) · `연동회신_gg-trusted-registry_2026-08-03_r6.md`
> **성격**: 집행계약 §2 가 정한 **신호 변경 통지**입니다. 계약 개정 협상이 아닙니다.

집행계약 §2 는 "**모두 이미 존재하는 필드이며 새로 만들 것은 없다**"고 적었습니다.
그 문장이 오늘부로 사실이 아닙니다 — **필드 4개가 늘었고 enum 2개가 넓어졌으며,
계약 본문의 판단 규칙 하나가 틀렸습니다.**

읽는 순서: **§1(깨지는 것) → §2(넓어진 차단 범위) → §3(추가 필드) → §4(그동안
잘못 쌓인 통계) → §5(할 일)**

---

## 1. ★ 계약 본문의 판단 규칙 하나가 틀렸습니다 — 지금 고쳐야 합니다

### 집행계약 §2-1 의 `in_kev` 행

> `in_kev` | bool | 실제 악용 중(CISA KEV). **단 `cache_sources_used` 가 비어 있으면
> `false` 는 '대조 못 함'**

**규칙의 의도는 옳지만 술어가 틀렸습니다.** gvskb 는 인텔 소스마다 따로 기록합니다.

```python
if osv_entry is not None:  cache_sources_used.append("osv-malicious")
if kev_entry is not None:  cache_sources_used.append("cisa-kev")
```

즉 **`["osv-malicious"]` — 비어 있지 않은데 KEV 대조는 되지 않은 상태**가 있습니다.
악성 피드는 반입했고 KEV 캐시는 아직 없는 경우이고, 망분리에서 인텔 번들을 부분
반입하면 드물지 않습니다.

**하네스가 지금 규칙대로 판단하면 이렇게 됩니다.**

| 실제 상태 | 계약 §2-1 규칙의 판단 | 옳은 판단 |
|---|---|---|
| KEV 캐시 없음 + 악성 피드 있음 | "대조했고 악용 없음" → **통과** | **대조 못 함** |

실제 악용 중인 패키지가 KEV 대조 없이 통과합니다. **집행계약 §5-1 이
`intel_cache=missing` 을 ENFORCE 에서 차단하기로 한 것과 같은 위험**인데, 이쪽은
`missing` 이 아니라 '부분 반입'이라 그 규칙에 걸리지 않습니다.

### 조치 — `kev_checked` 를 보십시오

```diff
- in_kev | bool | 단 `cache_sources_used` 가 비어 있으면 `false` 는 '대조 못 함'
+ in_kev | bool | KEV 교차 일치 여부
+ kev_checked | bool | **`false` 면 `in_kev=false` 는 '악용 없음'이 아니라 '대조 못 함'**
```

| 상황 | `kev_checked` |
|---|---|
| KEV 캐시를 실제로 읽음(신선·낡음 무관) | `true` |
| KEV 캐시 없음 | **`false`** |
| 취약점 0건이라 대조할 대상이 없었음 | `true` — KEV 는 CVE 기반이라 `in_kev=false` 가 사실 |

낡음 여부는 `cache_stale_sources` 에 그대로 있습니다. **`kev_checked` 는 '읽었는가',
`cache_stale_sources` 는 '얼마나 최신인가'** 로 나눠 보십시오.

레지스트리에도 같은 정정을 요청했습니다(회신 C-1).

## 2. ⚠ `unknown` 차단 범위가 **실질적으로 넓어집니다**

집행계약 §4-0 은 `unknown` 차단을 `source_scope` 로 가릅니다.

| `source_scope` | ENFORCE 에서 `unknown` |
|---|---|
| `single` · `manifest` | **차단** |
| `lockfile` · `installed` | 차단하지 않음 |

**이 표는 그동안 의도대로 동작하지 않았습니다.** `--include-installed` 로 잡힌
패키지는 직접 의존성이든 전이 의존성이든 **전부 `installed`** 였습니다. 즉
`requirements.txt` 에 사람이 직접 적은 패키지도 설치본 경로로 들어오면
`installed` 가 되어 **차단 대상에서 빠졌습니다.**

2026-08-03 부로 gvskb 가 매니페스트와 설치본을 대조해 항목마다 나눕니다.

```
설치 흔적 중 매니페스트에 이름이 있는 것 → source_scope = manifest    ← 이제 차단 대상
그 밖의 전이 의존성                      → source_scope = installed
```

**하네스 입장에서는 ENFORCE 시 차단되는 패키지가 늘어납니다.** 계약 §4-0 이 원래
의도한 범위로 돌아온 것이지 정책 변경은 아니지만, MONITOR 통계로 잡히는 수치가
바뀌므로 **§9-1 전환 기준을 판단하기 전에 알고 계셔야 합니다**(§4 참조).

### 부수 변경 — `source_scope` 가 이제 **모든 판정에** 붙습니다

이전에는 설치본 유래 판정에만 붙었습니다. 지금은 매니페스트·락파일 유래에도
붙습니다(`manifest`·`lockfile`). §4-0 을 구현하려면 이 값이 항상 있어야 합니다.

**한 가지 예외를 알려 드립니다** — MCP `scan_installed_packages` 도구만 단독으로
호출하면 **전부 `installed`** 로 옵니다. 그 도구는 매니페스트를 읽지 않아 직접
의존성을 가려낼 수 없기 때문입니다. **직접/전이 구분이 필요하면
`scan_path --check-deps --include-installed` 경로를 쓰십시오.** 임의로 `manifest` 를
붙이면 근거 없이 차단 범위가 넓어지므로 보수적인 쪽으로 두었습니다.

## 3. 추가·변경된 필드

### 3-1. 집행계약 §2-1(패키지 단위) 갱신분

| 필드 | 상태 | 하네스가 알아야 할 것 |
|---|---|---|
| `kev_checked` | **신설** | §1 참조. `false` 면 `in_kev=false` 는 '대조 못 함' |
| `version_exact` | **신설** | `false` 면 이 버전은 **매니페스트 제약의 경계값**이지 실제 설치 버전이 아니다 |
| `source_scope` | **모든 판정에 부여** | `single`·`manifest`·`lockfile`·`installed`. §4-0 의 근거값 |
| `registry_stale` | **신설** | `true` 면 낡은 차단(§3-2). `registry_decision.stale` 과 같은 값을 최상위에 |
| `registry_status` | **enum 확장** | `ok`·`unreachable`·**`rejected`**·**`item_failed`**·`unauthorized`·`disabled` |

### 3-2. `version_exact` — 오탐으로 설치를 막지 않으려면

gvskb 파서가 매니페스트 제약 연산자를 버리고 있었습니다. `requests>=2.28` 을
**2.28 로 판정**했고, 실제로는 2.31.0 이 깔려 있어도 2.28 기준 취약점이 보고됐습니다.

고쳤지만 **경계값 검사 자체는 남깁니다** — "이 제약이 취약한 버전을 허용한다"는
것도 실제 신호이기 때문입니다. 다만 그것은 **관측이 아니라 가정**입니다.

> **권고**: `version_exact=false` 인 판정만으로 설치를 차단하지 마십시오.
> 그 버전이 실제로 설치될 버전이라는 근거가 없습니다. 경고로 두고, 확정 판정이
> 필요하면 락파일이나 `--include-installed` 결과를 쓰십시오.

절대 규칙(§3)에는 그대로 적용해도 됩니다 — `not_found`(이름이 실재하지 않음)와
`malicious`(패키지 자체가 악성)는 버전과 무관한 진술이기 때문입니다.

### 3-3. `registry_status` 새 값 둘

| 값 | 의미 | 하네스 처리 권고 |
|---|---|---|
| `rejected` | 레지스트리가 **요청 형식을 거부**(재시도 무의미) | `unreachable` 과 같게 — 기관 판정 없음 |
| `item_failed` | 배치는 성공했으나 **이 항목만** 판정 못 받음 | `unreachable` 과 같게 — **`ok` 로 읽지 마십시오** |

`item_failed` 는 레지스트리가 배치 부분 실패를 허용하도록 고치면서 생긴 경로입니다.
**배치가 200 이라고 모든 항목이 답을 받은 것은 아닙니다.**

> **권고**: 계약 §2-1 의 `registry_status` 행을 "`ok` 가 아니면 기관 판정 없음"으로
> 읽으십시오. 값을 하나씩 나열해 처리하면, 저희나 레지스트리가 값을 늘릴 때마다
> **모르는 값이 통과로 떨어지는 조용한 초록불**이 생깁니다.

### 3-4. 집행계약 §3-2 의 'gvskb 측 보완 필요' — 해소됐습니다

> 현재 `apply_registry_decision` 이 `stale` 표식을 읽지 않아 낡은 차단과 신선한
> 차단의 안내 문구가 같다 — 수정 예정

2026-08-02 자로 처리했습니다. 판정은 그대로 차단(critical·requires_review)이고
안내만 갈립니다.

```
기관 레지스트리가 이 패키지를 차단했습니다 (사유: …). 사용하지 마세요.
⚠ 이 차단은 로컬 캐시에 남아 있던 것이며 최근 레지스트리에서 다시 확인하지
못했습니다(보관 기한 초과). 차단은 그대로 유지됩니다 — 조회에 실패했다고 차단이
풀리지는 않습니다. 해제 여부는 레지스트리 복구 후 재검사로 확인하세요.
```

`registry_stale` 로도 읽을 수 있으니 §3-2 의 사용자 안내를 이 문구로 채우시면
됩니다.

## 4. ⚠ 그동안 쌓인 MONITOR 통계가 왜곡돼 있습니다

MONITOR 로 데이터를 쌓고 계셨다면 아래 둘을 감안해 주십시오. **§9-1 전환 기준
(직접 의존성 `unknown` 비율 10% 이하 3주 연속)을 판단하기 전에 필요합니다.**

### 4-1. npm 전이 의존성이 통째로 빠져 있었습니다

`--include-installed` 의 npm 경로가 깨져 있었습니다. 설치 목록을
`express==4.17.0`(requirements 형식)으로 만들어 놓고 npm(JSON)으로 파싱하려다 실패해
`verdict="unparsed"`·`parsed_count=0` 을 냈습니다.

**즉 node_modules 에서 수집한 전이 의존성이 한 건도 검사되지 않았습니다.** 파이썬
쪽(.venv)은 정상이었습니다.

- **영향이 작은 곳**: §9-1 전환 기준은 **직접 의존성** 기준이고 npm 직접 의존성은
  `package.json` 경로로 정상 처리됐습니다. 비율 자체는 크게 틀어지지 않았을 것입니다.
- **영향이 큰 곳**: "우리는 전이 의존성까지 본다"는 **적용 범위 주장이 npm 에서는
  사실이 아니었습니다.** npm 프로젝트의 전이 의존성 취약점은 보고된 적이 없습니다.

고쳤습니다. 앞으로 npm 프로젝트에서 판정 건수가 늘어납니다.

### 4-2. 직접 의존성이 `installed` 로 분류돼 왔습니다

§2 참조. `--include-installed` 를 쓴 프로젝트에서는 직접 의존성도 `installed` 로
잡혀 **`unknown` 차단 대상 집계에서 빠졌습니다.** 전환 기준을 "직접 의존성의
`unknown` 비율"로 정하셨으므로, 그 분모가 실제보다 작았을 가능성이 있습니다.

> **권고**: 3주 연속 카운트를 이미 시작하셨다면 **오늘부터 다시 시작**하시는 편이
> 안전합니다. 분모가 바뀐 채 이어서 세면 기준을 충족했는지 판단할 수 없습니다.

## 6. 확인이 필요한 것 — 저희가 답을 못 가진 것

### 6-1. 판정 신선도 — 기준값이 운영상 맞습니까

`3자구조` §8-1 을 **비대칭으로 정정**했습니다. 이전 판은 통과·차단을 구분하지 않고
"1시간 이내의 것만 쓴다"고만 적어, 그대로 읽으면 차단 판정도 1시간이면 만료되고
재호출 실패 시 통과하게 됩니다 — **합의 §4-5 가 TTL 을 7일로 늘린 이유가 1시간
단위로 되살아납니다.** 레지스트리가 지적했습니다.

| 방향 | 신선도 미달 시 | 재호출이 실패하면 |
|---|---|---|
| **통과**(`registry_approved`·`checked_clean`) | 재호출 | **통과시키지 않는다** |
| **차단**(`malicious`·`registry_rejected`·`vulnerable`·KEV) | 재호출 | **오래된 차단을 그대로 유지** |

**집행계약 §3-2 가 우선입니다.** 남은 결정은 통과 방향 기준값(1시간 제안)이
운영상 맞는지뿐입니다.

### 6-2. 구조 확인 — 레지스트리를 직접 조회하지 않는다

`3자구조` §9-6 으로 물었던 항목이며 아직 회신을 받지 못했습니다. **직결을 설계
중이시면 지금 맞춰야 합니다.**

레지스트리가 같은 질문에 저희보다 정확한 근거를 들었기에 옮깁니다 — 저희는 토큰
유출면·중복 로직을 들었는데, 레지스트리는 **"레지스트리 승인만 보고 설치하면 로컬
악성·KEV 대조가 생략된다"** 를 첫 번째로 들었습니다. 이쪽이 본질입니다. 이 구조의
목적은 편의가 아니라 **합의 원칙 4(로컬 탐지가 최종 안전망)를 우회 불가능하게
만드는 것**입니다.

### 6-3. `override` — 형식은 정해졌고 채우는 주체는 하네스입니다

레지스트리가 구조화된 형식을 제안했고 저희도 동의했습니다.

```jsonc
"override": {
  "reason_code": "EMERGENCY_PATCH",   // 허용목록
  "approval_ref": "보안-2026-0173",   // 문서번호 — 사람 이름 아님
  "mode": "ENFORCE"
}
```

자유 문자열이면 "보안팀 ◯◯◯ 과장 승인"이 들어오고, 받은 뒤 개인정보만 골라내려
하면 탐지 규칙과의 술래잡기가 됩니다. **문법으로 막는 편이 확실합니다** —
`caller` 에서 저희가 겪은 것과 같습니다.

`reason_code` 목록은 기관 결정이며 레지스트리가 초안을 만들기로 했습니다.
**이 필드를 채우는 것은 하네스**이므로 집행계약 §10-4(우회 기록)와 맞춰 주십시오.

## 7. 이 통지가 계약에 미치는 영향

| 집행계약 절 | 변경 |
|---|---|
| §2 머리말 | "새로 만들 것은 없다" → **필드 4개 신설·enum 2개 확장** |
| §2-1 | `in_kev` 행 정정 · `kev_checked`·`version_exact`·`source_scope`·`registry_stale` 추가 · `registry_status` enum 확장 |
